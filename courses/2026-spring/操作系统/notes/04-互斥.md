## 一句话总结

实现互斥的演进路径是：关中断（单核可用，多核失效）→ 软件标志（test 和 set 非原子，有竞态）→ Peterson 算法（纯软件正确，但依赖 SC 内存模型）→ 硬件原子指令（LOCK cmpxchg/LL-SC，现代 OS 的基石）。

## 知识地图

```
竞态条件: 多个线程同时进临界区 → 不确定结果
        │
        ▼
临界区解决方案需要满足:
  ├── 互斥 (Mutual Exclusion) — Safety: 最多一个线程在临界区
  ├── 行进 (Progress) — Liveness: 有人想进且临界区空 → 最终有人进入
  ├── 有界等待 (Bounded Waiting) — Fairness: 等的时间有限
  └── 性能: lock/unlock 开销应尽可能小

演进路径:
  关中断 → 软件标志 → Peterson算法 → 硬件原子指令 (TAS/CAS)
  [单核]   [有竞态]   [SC模型下正确]  [现代OS方案]
```

## 核心概念

### 1. 术语定义

| 术语 | 含义 |
|------|------|
| **临界区 (Critical Section)** | 访问共享资源的代码段 |
| **竞态条件 (Race Condition)** | 多线程同时进临界区，结果不确定 |
| **互斥 (Mutual Exclusion)** | 最多一个线程在临界区内 |
| **安全性 (Safety)** | "没有坏事发生"——任何有限步骤内保持 |
| **活性 (Liveness)** | "好事终将发生"——最终会达到预期状态 |

**经验法则**：设计并发算法时，优先保证安全性，但别忘了活性和性能。

### 2. 尝试一：关中断（单处理器方案）

**原理**：`lock() = cli`（关中断），`unlock() = sti`（开中断）。单处理器中，唯一能打断当前执行的就是中断。

**问题**：
- 临界区死循环 → 整个系统卡死（连 NMI 看门狗都未必救得回来）
- 关中断太久 → 丢失重要 I/O 事件
- **多处理器无效**：每个核有独立的中断状态
- 关中断是特权指令 → 用户态不能用

> 但操作系统内核中关中断仍然是常用操作。

### 3. 尝试二：软件标志

```c
int flag = 0;
void lock() { while (flag == 1); flag = 1; }
void unlock() { flag = 0; }
```

**为什么失败？** test 和 set 是两条独立指令：
```
Thread 1: test flag==0 ✓ → [中断/并行] → set flag=1
Thread 2: test flag==0 ✓ → set flag=1
→ 两个都进了临界区！
```

两个线程同时发现 flag=0，同时设 flag=1。根源：**test-and-set 不是原子的**。

### 4. 尝试三：差异判定 + 严格轮转

让线程 1 等 `flag==1`，线程 2 等 `flag==0`（判定条件不同，保证了互斥）。**问题**：严格轮转——一个线程不进临界区，另一个最多进一次，之后就永远等不到。违背**行进性**。

### 5. Peterson 算法（纯软件的正确方案）

```c
int intents[2] = {0, 0};  // 每个线程的进入意愿
int flag = 0;             // 轮到谁

void lock() {
    int self = tid;       // 当前线程 ID (0 or 1)
    intents[self] = 1;    // "我想进"
    flag = self;          // "轮到你了"（让步）
    while (intents[(self+1)%2] == 1 && flag == self)
        ;                 // 对方想进 且 正轮到对方 → 等待
}
void unlock() {
    intents[self] = 0;    // "我出来了"
}
```

**核心思路**：flag 和 intents 配合——flag 决定"冲突时谁优先"（先设 flag 的让步给对方）。

**正确性证明（三性）：**
- **互斥**（反证+状态机遍历）：两个线程同时进临界区无法由合法状态迁移得到
- **行进**：对方无意进 → `intents[other]==0` → 直接通过 while 循环
- **有界等待**（2 线程）：最多等对方一轮

**致命问题**：Peterson 依赖**顺序一致性（SC）内存模型**——现代 CPU（x86 TSO、ARM Relaxed）上，store/load 可能被重排，算法失效。

**Model Checking** 可以自动化验证算法正确性：`python3 mosaic.py -c peterson.py | grep "cs" | sort | uniq`

### 6. 硬件原子指令——真正的解决方案

既然 test-and-set 需要原子化，那就让硬件直接提供：

**x86: LOCK cmpxchg（Compare-and-Swap）**
```asm
lock cmpxchg %2, %1
; if (dst == %ax) { dst = src; ZF=1; }
; else { %ax = dst; ZF=0; }
```

**自旋锁 (Spin Lock) 实现：**
```c
void lock() {
    int expected;
    do {
        expected = 0;
        asm volatile ("lock cmpxchg %2, %1"
            : "+a" (expected) : "m" (flag), "r" (1)
            : "memory", "cc");
    } while (expected != 0);  // CAS 失败 → 自旋重试
}
void unlock() { flag = 0; }
```

**LOCK 前缀原理**：锁住特定内存地址，阻止其他系统总线读取/修改该地址。以下指令都支持 LOCK：ADD, ADC, AND, CMPXCHG, INC, DEC, OR, XOR, XADD, XCHG…

**其他架构：**
- ARM/MIPS/RISC-V 使用 **LL/SC**（Load-Linked / Store-Conditional）：
  - LL 读一个内存位置的值
  - SC 仅在该位置自 LL 以来没被修改过时才写入成功

## 难点突破

### 难点 1：为什么 Peterson 在现代硬件上是错的？

核心在于 **store/load 重排**。TSO 模型允许"先读后写"被重排为"先写后读"：

```c
// Thread 1 期望的执行顺序：
intents[1] = 1;  // store
flag = 1;        // store
while (intents[0] == 1 && flag == 1);  // load + load

// 但 CPU 可能重排为：
flag = 1;        // 这个 store 先被其他核可见！
// Thread 0 此时看到 flag=1 && intents[1]=0 → 直接进临界区
// Thread 1 随后 intents[1]=1 → 也进临界区 → 互斥失效！
```

需要 `__sync_synchronize()` (mfence/dmb/fence) 插入内存屏障——但仅靠屏障不够，还需要有系统性的方案（第 5 章）。

### 难点 2：Safety vs Liveness 的界限

> "有界等待"的上限如果指定数字 → Safety（任何有限步骤内等待次数超过上限 = 坏事发生）
> 如果只要求"最终进入"不指定上限 → Liveness

这个区分很微妙：**Liveness 可以无限等待**，"最终"没有时间限制；**Safety** 加了上限后就变成了"有限步骤内必须满足"，违反即 safety violation。

- 第 3 章提出三大挑战（原子性/顺序性/一致性丧失）→ 本章用硬件原子指令解决了原子性丧失

## 记忆卡片

**Q1: 临界区解决方案需要满足哪三个条件？**
A: 互斥（最多一个线程在临界区）、行进（有人想进且为空→最终有人进）、有界等待（等待时间有限）

**Q2: 关中断方案的两个致命问题？**
A: 临界区死循环→系统卡死；多处理器无效（每核独立中断状态）

**Q3: Peterson 算法的核心思路？**
A: intents 表达"我想进"，flag 决定"冲突时谁让步"——先设 flag 的把优先权给对方

**Q4: x86 硬件原子指令的核心机制？**
A: LOCK 前缀锁定内存地址，阻止其他系统总线访问。CMPXCHG/CAS 实现原子 test-and-set。

**Q5: 为什么自旋锁叫"自旋"？**
A: CAS 失败后不停重试（while 循环），线程在 CPU 上"空转"，不进入睡眠。

## 期末简答题 Q&A

**Q1: 什么是竞态条件？什么是临界区？它们的关系是什么？**

A:
- **竞态条件**：多个线程并发访问共享资源，最终结果取决于线程的**相对执行顺序**，结果不确定。
- **临界区**：访问共享资源的那段代码。
- **关系**：临界区是"地点"，竞态条件是"现象"——多个线程**同时**进入临界区就触发竞态条件。解决方案是互斥：同一时刻最多一个线程在临界区内。

> 判断方法：两个线程能否同时修改同一变量 → 能 → 有竞态条件 → 需要保护。

---

**Q2: 临界区解决方案需满足哪三个条件？各属什么性质？**

A:
| 条件 | 含义 | 性质 |
|------|------|------|
| 互斥 (Mutual Exclusion) | 最多一个线程在临界区内 | Safety — "没有坏事发生" |
| 行进 (Progress) | 有人想进且临界区为空 → 最终必有人进入 | Liveness — "好事终将发生" |
| 有界等待 (Bounded Waiting) | 一个线程等待进入的时间有上限 | Fairness — 不能无限排队 |

> Safety 可在有限步骤内判定违反，Liveness 不能。比如"等不到锁"在有限步骤内无法判定是否死等。

---

**Q3: 列出实现互斥的四种方案，逐一说明其缺陷。**

A:
| 方案 | 缺陷 |
|------|------|
| 关中断 (cli/sti) | ① 多处理器无效（每核独立中断状态）；② 关中断太久丢 I/O；③ 临界区死循环 → 系统卡死；④ 用户态不可用 |
| 软件标志 (flag 变量) | test 和 set 是两条指令，不原子 → 两个线程同时读 flag=0 同时设 flag=1 → 都进临界区 |
| 差异判定 + 严格轮转 | thread 0 等 flag=0，thread 1 等 flag=1 → 一个线程不进，另一个最多进一次后永远阻塞。违背**行进性** |
| Peterson 算法 | 两个线程的纯软件正确方案，但**依赖 SC 内存模型**。现代 CPU (x86 TSO / ARM Relaxed) 的 store/load 重排会破坏互斥 |

> 最终方案：硬件原子指令（LOCK cmpxchg / LL-SC），信任硬件。

**Q4: 写出 Peterson 算法的核心代码和设计思路。**

A:
```c
int intents[2] = {0, 0};
int flag = 0;

void lock() {
    int self = tid;
    intents[self] = 1;       // "我想进"
    flag = self;             // "先轮到你"（让步给对方）
    while (intents[(self+1)%2] == 1 && flag == self)
        ;                    // 对方也想进 且 轮到对方 → 我等待
}

void unlock() {
    intents[self] = 0;       // "我出来了"
}
```

**设计思路**：
- `intents[]` 表达"谁想进"
- `flag` 解决冲突：先设置 flag 的那个线程让步（flag 被后者覆盖）
- 等待条件：**对方也想进 AND 轮到对方** → 我才等。对方不想进 → 直接通过。

---

**Q5: 为什么 Peterson 算法在现代硬件上会失效？用具体例子说明。**

A:
**根因：CPU 的 store/load 重排。**

Thread 1 期望两行 store 按顺序对其他核可见：
```
intents[1] = 1;  // Store A
flag = 1;        // Store B
```

但 CPU 可能将 Store B 先于 Store A 对其他核可见：
```
// Thread 0 看到的顺序：
flag = 1, intents[1] = 0
→ while (intents[1]==1 && flag==0) → intents[1] 还是 0 → 条件不满足 → 直接进临界区！
// Thread 1 随后 intents[1]=1 对其他核可见 → 也进临界区 → 互斥失效！！
```

**解决方向**：加内存屏障 (mfence/dmb/fence)，但仅靠屏障不够——需要系统性方案（详见第 5 章）。

---

**Q6: x86 上如何用 CAS 实现自旋锁？解释 LOCK 前缀的作用。**

A:
**实现：**
```c
void lock() {
    int expected;
    do {
        expected = 0;
        asm volatile ("lock cmpxchg %2, %1"
            : "+a" (expected) : "m" (flag), "r" (1)
            : "memory", "cc");
    } while (expected != 0);  // 没拿到 → 自旋重试
}

void unlock() {
    flag = 0;
}
```

**CAS 语义**：`if (flag == expected) { flag = 1; } else { expected = flag; }`——原子完成。

**LOCK 前缀作用**：锁定内存总线（或通过 cache coherence 协议独占 cache line），保证**全系统范围内**只有一个核能同时读写那个内存地址。没有 LOCK → 多核同时 cmpxchg 都会"成功"。

---

**Q7: 自旋锁的适用场景和代价分别是什么？**

A:
**适用场景**：临界区**极短**（几条指令），锁很快会被释放。
- 优点：避免了线程睡眠/唤醒的上下文切换开销（~几微秒）。

**代价**：
- CPU 空转（忙等待），临界区长 → 浪费严重。
- 持有自旋锁期间**不能睡眠**——其他自旋的线程全在浪费 CPU。

> 经验规则：临界区执行时间 < 上下文切换开销 → 用自旋锁；否则用互斥锁（mutex）。

---

**Q8: Safety 和 Liveness 有何本质区别？"有界等待"属于哪个？**

A:
| | Safety | Liveness |
|------|--------|---------|
| 定义 | "坏事永远不会发生" | "好事终将发生" |
| 可判定性 | 有限步骤内可判定违反 | 有限步骤内无法判定（可以是无限等待） |
| 例子 | 互斥——两个线程同时进临界区 | 行进——等锁的人最终一定拿到 |

**有界等待的归属**：
- 给出具体上限数字（如"最多等 N 轮"）→ **Safety**（超上限 = 坏事发生）
- 只说"最终会等到"不指定上限 → **Liveness**

> 考试重点：互斥 = Safety，行进 = Liveness，别写反。

---

**Q9: LL/SC 和 CAS 的区别是什么？各自用在哪些架构？**

A:
| | CAS (Compare-and-Swap) | LL/SC (Load-Linked / Store-Conditional) |
|------|----------------------|--------------------------------------|
| 原理 | 一条指令完成"比较+交换" | 两条指令配对：LL 读 + SC 写，SC 仅在未被修改过时才成功 |
| 架构 | x86 | ARM, MIPS, RISC-V |
| 伪 ABA | 存在 ABA 问题 | 硬件自动监控地址，天然免疫 ABA |

> LL/SC 不比较值，而是监控地址是否被写过——更优雅，但程序员需要适应两指令配对模式。

---

**Q10: 什么是 ABA 问题？为什么 CAS 会遇到而 LL/SC 不会？**

A:
**ABA 问题**：CAS 只看"值还是不是 A"，不关心"这个 A 还是原来的 A 吗"。值相同不代表中间没被动过。

**经典场景**（无锁栈 pop）：
```
初始栈：A → B → C

Thread 1 想 pop A（改栈顶 A→B）
  → 读栈顶 = A，还没执行 CAS...

Thread 2 抢先执行：pop A, pop B, push A
  → 栈变成 A → C（注意：顶还是 A，但 C 丢了！）

Thread 1 继续：CAS(栈顶, A, B) → 值一样是 A，成功！
  → 栈变成 B → C
  → 但 B 已经被 pop 掉了，这次 CAS 不该成功！
```

**本质**：CAS 比较的是值，不是身份。"值相同" ≠ "状态未变"。

**LL/SC 为什么免疫**：LL/SC 不比较值，而是硬件监控地址。从 LL 到 SC 之间该地址只要被写过——不管写回了什么值——SC 都失败。

**解决方案**：双宽 CAS（如 `cmpxchg16b`，同时比较值 + 版本号），每次修改递增版本号，ABA 就不可能了。

> 类比：你在桌上放书做标记，回来书还在→以为是原来的样子。实际上有人拿走翻完又放了本一样的。CAS 只看封面，LL/SC 看监控录像。
