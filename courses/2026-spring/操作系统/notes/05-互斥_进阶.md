## 一句话总结

自旋锁只是互斥的起点——实际系统中还要解决有界等待（排号锁）、内核中断死锁（push_off/pop_off）、用户态长临界区空转浪费（futex 两阶段锁），以及并发数据结构的性能瓶颈（细粒度锁 + 层级化方案）。

## 知识地图

```
自旋锁的三个进阶问题
  ├── 公平性：可能饿死 → Ticket Lock（排号锁，fetch-and-add）
  ├── 内核中断：中断处理程序抢同一把锁 → 死锁
  │     └── xv6 方案：push_off/pop_off + 中断状态计数
  └── 用户态性能：长临界区空转浪费 CPU
        ├── yield 方案：让出 CPU 但反复上下文切换开销大
        ├── 阻塞方案：OS 维护等待队列，wait/wakeup
        │     └── 核心难题：lost wakeup（唤醒丢失）
        └── Linux Futex：两阶段锁
              ├── Fast Path：用户态 CAS，无竞争直接进
              └── Slow Path：futex_wait 系统调用阻塞
```

## 核心概念

### 1. Ticket Lock（排号自旋锁）

普通自旋锁的问题：不保证有界等待——线程可能永远抢不到锁（其他线程一直优先调度）。

**解决**：排队叫号。每次尝试加锁领一张票（ticket），等叫到自己的号（turn）才能进。

```c
typedef struct {
    int ticket;  // 当前发放的最大票号
    int turn;    // 当前应该进入的票号
} lock_t;

void lock() {
    int myturn = __sync_fetch_and_add(&flag.ticket, 1);  // 原子领号
    while (flag.turn != myturn);  // 自旋等叫号
}
void unlock() {
    flag.turn++;  // 叫下一个号
}
```

关键：`fetch_and_add` 是一条原子指令（GCC builtin: `__sync_fetch_and_add`），保证每个线程领到唯一且递增的票号。这样谁先领号谁先进，有界等待自然满足。

### 2. 细粒度锁 vs 一把大锁

并不是所有线程都需要互斥——应该给不同的共享资源配不同的锁：

```c
// 把锁做成参数，而不是全局变量
void lock(lock_t *lk);    // 锁住 lk 指向的锁
void unlock(lock_t *lk);  // 解锁 lk 指向的锁
```

细粒度锁提高并发度：访问资源 A 的线程不阻塞访问资源 B 的线程。

**但互斥锁的正确性依赖于大家都是"理智的合作者"**：如果有人访问共享资源时不先 lock，一切全废。锁只是约定，不是强制。

### 3. 内核中自旋锁的中断问题

内核中自旋锁的特殊麻烦——中断处理程序可能和系统调用抢同一把锁：

```
Thread A (syscall)         Interrupt Handler
  spin_lock(&lk) ─────────→  spin_lock(&lk)  // 发现 lk 已被持有
  ...临界区中...               while(spin);    // 死等！
                              // A 被中断了，没法释放锁
                              // 中断优先级又高于 A
                              // → 永远等不到，死锁！
```

**错误方案**：lock 前关中断，unlock 后开中断。问题：如果拿锁前就已经关中断了，unlock 开中断就破坏了之前的中断状态。

### 4. xv6 的方案：push_off / pop_off

核心思路：**保存中断状态，用计数器追踪嵌套**。

```c
void push_off(void) {
    int old = ienabled();   // 记住关中断前的状态
    iset(false);            // 关中断
    if (c->noff == 0)       // 只在第一次关中断时记录旧状态
        c->intena = old;
    c->noff += 1;           // 嵌套计数 +1
}

void pop_off(void) {
    c->noff -= 1;           // 嵌套计数 -1
    if (c->noff == 0 && c->intena)  // 所有锁都释放了，且之前是开中断的
        iset(true);         // 才真正开中断
}
```

`noff` 计数器让嵌套的 lock/unlock 正确工作（两把锁嵌套需要两次 pop_off 才真正开中断）。

### 5. 用户态互斥：从自旋到阻塞

自旋锁在用户态的问题：临界区可能很长，其他核空转浪费 CPU。更糟的是，中断可能把持有锁的线程切走——其他线程全在空转等待一个没在运行的线程。

**yield 方案**：抢不到锁就 `sched_yield()` 让出 CPU。问题：线程还在就绪队列，可能被反复调度→反复 yield→大量不必要的上下文切换。

**正确的方案**：OS 参与——抢不到锁就**阻塞**（移出就绪队列，放入等待队列），释放锁时**唤醒**一个等待者。

操作系统需要为每把锁维护一个等待队列（队列操作本身需要内核自旋锁保护）。

### 6. Lost Wakeup 问题

实现 wait/wakeup 的经典 race condition：

```
Thread 1 (unlock)              Thread 2 (lock)
  atomic_xchg(lk, UNLOCKED)      got != UNLOCK → 准备 wait
  if (!empty(wait_list))         此时队列为空，wakeup 不执行
    wakeup(...)                  wait(lk->wait_list)  // 永远等下去！
```

**wakeup 丢失了**：unlock 时队列还是空的，wakeup 无事发生；然后 lock 的线程把自己加入队列并阻塞——再也没人唤醒它。

### 7. Linux Futex：两阶段锁

为解决 lost wakeup，Linux 提供了 `futex_wait` 和 `futex_wake` 系统调用：

- `futex_wait(int *addr, int expected)`：**原子地**检查 `*addr == expected`，相等才阻塞；不等则立即返回（避免了 lost wakeup！）
- `futex_wake(int *addr)`：唤醒一个等待 addr 的线程

Futex 锁的三状态机：
- `UNLOCK(0)` → `ONE_HOLD(1)`：无竞争，一条 CAS 搞定（fast path）
- `ONE_HOLD(1)` → `WAITERS(2)`：有竞争，CAS 设为 WAITERS 并 futex_wait（slow path）
- unlock 时如果状态是 WAITERS → futex_wake；如果只是 ONE_HOLD → 直接设回 UNLOCK（fast path unlock）

**核心洞察**：Futex 在**无竞争时完全是用户态操作**（一条原子指令），避免了系统调用开销；有竞争时才陷入内核。

### 8. 并发数据结构

线程安全的数据结构 = 多线程可以并发访问的数据结构。

**并发 Counter 的优化层级**：
- Level 1：一把大锁保护整个 counter（简单，性能差）
- Level 2：每个 CPU 一个本地 counter（本地锁），定期汇总到全局 counter（全局锁）——大幅提高并发度

层级化思想贯穿整个并发体系：
```
用户态   并发程序（使用 pthread_mutex 等）
  ↑
库      glibc 封装的并发 API
  ↑
内核态   futex_wait/futex_wake 等并发原语
  ↑
硬件     LOCK cmpxchg / LL-SC 等原子指令
```

## 难点突破

### 难点 1：Lost Wakeup 为什么那么难解决？

核心矛盾：unlock 时的"检查队列 + 唤醒"和 lock 时的"检查锁 + 入队等待"这两组操作各自需要原子化，但它们跨了用户态和内核态。

futex 的解决思路：不追求"检查+入队"原子化，而是在 `futex_wait` 内部**二次检查**锁的值——如果锁在入队期间被释放了，futex_wait 发现值变了就不阻塞。这是一种乐观策略：先假设没事，出问题了再补救。

### 难点 2：Futex 为什么是"两阶段"？

**第一阶段（用户态 CAS）**：假设无竞争。一条原子指令尝试拿锁，成了直接进临界区，零系统调用。

**第二阶段（内核 futex_wait）**：有竞争。陷入内核，把自己阻塞在等待队列上。

大多数真实 workload 中多线程抢同一把锁的频率并不高——所以 fast path 命中的概率很大。这就是 futex 高性能的秘密：为常见情况（无竞争）优化。

## 记忆卡片

**Q1: 普通自旋锁的公平性问题是什么？怎么解决？**
A: 不保证有界等待，线程可能饿死。用 Ticket Lock：fetch_and_add 原子领号，按号进入。

**Q2: 内核自旋锁为什么会有中断死锁？**
A: 线程持有锁后发生中断，中断处理程序尝试拿同一把锁→自旋等待→线程无法恢复执行释放锁→死锁。

**Q3: xv6 的 push_off/pop_off 核心思路？**
A: 关中断前保存旧中断状态；用 noff 计数器追踪嵌套层数；只有最外层 pop_off 且之前是开中断时才真正恢复中断。

**Q4: Lost wakeup 是怎么发生的？**
A: unlock 检查队列（空）→ lock 入队→ unlock 唤醒（队列空，无事发生）→ lock 阻塞（没人唤醒了）。唤醒信号在入队之前就发出了。

**Q5: Futex 的 fast path 和 slow path 分别是什么？**
A: Fast path = 用户态 CAS（无竞争，零 syscall）；Slow path = futex_wait 系统调用阻塞（有竞争时）。futex_wait 会二次检查值，避免 lost wakeup。

## 补充：对话深化

### 内核中断死锁的直观理解

```
你（syscall 线程）拿刀切菜
  → 消防检查员（中断）推门，你必须停下
  → 检查员也要那把刀
  → 刀在你手里，你回不去放不下
  → 检查员原地等，永远拿不到
  → 死锁
```

本质：低优先级持有锁，高优先级等待低优先级释放，但低优先级的被"冻结"了根本没机会跑完。

### 天真方案（cli/sti）的嵌套问题

```c
// 危险方案：
lock()   { cli(); CAS(...); }
unlock() { sti(); ...; }

// 嵌套场景炸了：
cli();           // 外层已关中断
lock(&A);        // 内层又 cli（重复，没影响）
unlock(&A);      // 内层 sti → 开了！！但外层以为还关着
// 中断被意外打开了！
```

问题：`cli/sti` 不配对，内层 lock/unlock 不知道调用者的中断状态。

### push_off/pop_off 一句话解释

进门时：看一眼灯是亮是灭 → 记纸条上 → 开灯 → 计数器+1
出门时：计数器-1 → 归零了？看纸条决定恢复原状

`noff` 计数器让嵌套 lock/unlock 像括号配对，只有最外层右括号才恢复中断。

### Lost Wakeup 代码级还原

```c
// Thread B (lock)                     // Thread A (unlock)
got = atomic_xchg(&status, LOCKED);     
// got = LOCKED, 没抢到               
                                        atomic_xchg(&status, UNLOCKED);
                                        is_empty(wait_list) → true
                                        // 队列空，不 wakeup！
wait(wait_list);  // B 入队、阻塞
// 但 wakeup 已经发出过了，B 永远不会被唤醒！
```

根因："检查锁失败"和"加入等待队列"是两条用户态指令，中间有缝。unlock 恰好在缝里发生。

### Futex 如何修复

`futex_wait(addr, expected)` 在内核中**原子地**完成：检查 `*addr == expected` → 相等才入队阻塞。检查和入队在一次内核调用、一把内核锁保护下完成，中间没有缝。

### pthread mutex 实现思路

```
lock:   用户态 CAS → 成功？拿锁（0 syscall）
                    → 失败？futex_wait 阻塞（进内核）

unlock: atomic_xchg → 返回 LOCKED？没人等，结束
                    → 返回 WAITERS？futex_wake 唤醒
```

**优秀四点**：
1. 无竞争 = 零系统调用（一条原子指令）
2. 有竞争 = 不浪费 CPU（阻塞而非自旋）
3. 自适应：futex_wait 前先短自旋，避免刚睡即醒
4. API 干净，边界条件（lost wakeup、内存屏障、嵌套）全处理好

## 期末简答题 Q&A

**Q1: 普通自旋锁有哪些工程缺陷？各自如何解决？**

A:
| 缺陷 | 问题 | 解决方案 |
|------|------|---------|
| 不公平 | 不保证有界等待，线程可能饿死 | Ticket Lock：fetch_and_add 领号排队 |
| 内核中断死锁 | 中断抢同一锁 → 持有者被冻结 → 永久死锁 | push_off/pop_off：持锁前关中断并保存状态 |
| 用户态长临界区 | 自旋空转浪费 CPU，持有者还可能被切走 | futex 两阶段锁：无竞争用户态 CAS，有竞争阻塞 |

---

**Q2: 画出内核中断死锁的形成环路，并说明为什么 push_off 能解决。**

A:
**死锁环路**：syscall 持锁 → 中断到达、CPU 强制转向 → 中断处理抢同一锁 → 自旋等待 → 但 syscall 没机会跑完释放锁 → 永久卡死。

**push_off 思路**：持锁前关中断 → 持锁期间中断不会来 → 没有死锁。关键技巧是保存旧中断状态 + noff 嵌套计数，保证 lock/unlock 配对后恢复原状。

---

**Q3: 写出 push_off 和 pop_off 的关键逻辑，并说明 noff 计数器存在的意义。**

A:
```c
push_off():
    old = ienabled();        // 1. 保存旧状态
    iset(false);             // 2. 关中断
    if (noff == 0)           // 3. 只有第一层记录旧状态
        intena = old;
    noff++;                  // 4. 嵌套计数+1

pop_off():
    noff--;                  // 1. 嵌套计数-1
    if (noff == 0 && intena) // 2. 最外层 且 原来是开的
        iset(true);          // 3. 才真正开中断
```

**noff 意义**：处理嵌套锁。两把锁嵌套 → 两次 push_off、两次 pop_off → 只有最外层 pop_off（noff 归零）才真正恢复中断。保证 lock/unlock 括号配对。

---

**Q4: Lost Wakeup 是怎么发生的？用代码交织说明。**

A:
```
B: got = atomic_xchg(→LOCKED)  // 没抢到
A: atomic_xchg(→UNLOCKED)      // 释放锁
A: is_empty → true, 不 wakeup  // 队列还空着！
B: wait(wait_list)             // B 入队、阻塞，但 wakeup 已错过
```

唤醒信号在入队之前发出，B 永远等不到唤醒。根因：检查锁失败和加入等待队列不是原子操作。

---

**Q5: Futex 是如何解决 Lost Wakeup 的？为什么叫"两阶段锁"？**

A:
**解决**：`futex_wait(addr, expected)` 在内核中先二次检查 `*addr` 的值——如果锁在入队期间已被释放（值变了），立即返回重试，不阻塞。检查+入队+阻塞在内核同一临界区内完成，中间无法插入 unlock。

**两阶段**：
- Fast Path：无竞争，用户态 CAS 拿锁，零系统调用
- Slow Path：有竞争，futex_wait 进内核阻塞

大多数场景无竞争 → fast path 命中率高 → 整体近乎零开销。

---

**Q6: 简述 pthread mutex 的实现原理和优势。**

A:
**原理**：底层基于 Linux futex，采用"先用户态 CAS，失败再 futex_wait"的两阶段策略。unlock 时 futex_wake 唤醒等待者。glibc 在 futex_wait 前还会短自旋（自适应）。

**优势**：
1. 无竞争零 syscall（一条原子指令）
2. 有竞争不浪费 CPU（阻塞而非自旋）
3. 自适应自旋避免刚睡即醒
4. lost wakeup、内存屏障、中断等边界条件已处理好
5. API 简洁，用户只需 lock/unlock

> 除非写内核或无 OS 环境，不需要自己实现锁。
