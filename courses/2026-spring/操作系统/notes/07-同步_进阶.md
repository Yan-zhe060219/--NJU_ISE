## 一句话总结

本章解决三个问题——读写锁（允许并发读，三种策略各有取舍）、RCU（读完全不阻塞，更新分 removal + reclamation 两阶段）、哲学家就餐（死锁的四类经典解法），最终引出死锁≠饿死的本质区分。

## 知识地图

```
同步进阶三大问题
  │
  ├── 读者-写者问题 (Readers-Writers)
  │     ├── 读者优先：读者一直来→写者饿死
  │     ├── 写者优先：写者一直来→读者饿死
  │     └── 公平方案：Ticket Lock 排队
  │           └── POSIX: pthread_rwlock_*
  │
  ├── RCU (Read-Copy-Update) — 无锁同步
  │     ├── 适用场景: read-mostly（路由表、用户信息）
  │     ├── 核心: 更新 = removal(并发读) + reclamation(等旧读者结束)
  │     ├── 发布-订阅: rcu_assign_pointer / rcu_dereference (含内存屏障)
  │     ├── 宽限期 (Grace Period): synchronize_rcu() / call_rcu()
  │     └── 经典实现: 读者侧关中断 → 写者检测所有 CPU 上下文切换
  │
  └── 哲学家就餐问题 (Dining Philosophers)
        ├── 方案1: 全先拿左边 → 死锁
        ├── 方案2: 拿不到右边就放下 + 随机睡眠 → 概率正确
        ├── 方案3: N-1 个同时上桌（鸽巢原理）→ 正确且并发度可接受
        └── 方案4: 给筷子编号，总是先拿小的 → 简单完美
```

## 核心概念

### 1. 互斥锁、条件变量、信号量的关系

三者的表达能力层级：

```
条件变量 + 互斥锁: 最灵活，可表达任意同步条件
信号量: 自带上整数状态，用起来简单但不能表达所有条件
互斥锁: 只解决"不能同时进"
```

- 信号量可实现互斥锁（初值=1），但不太能实现条件变量
- 条件变量 + 互斥锁可实现信号量（第 6 章已展示）
- **小心泛化**（Lampson 警告）：不是所有问题都该用信号量

### 2. 读者-写者问题（Readers-Writers Problem）

**需求**：读者之间不互斥（读不改变数据），写者与所有人互斥。

**实现 1 — 读者优先**：
- 第一个读者抢 `rwlk`（进临界区的锁），最后一个读者释放 `rwlk`
- 读者只要看到临界区有其他读者就直接进
- **问题**：读者连绵不断 → 写者永远等不到 `rwlk` → **写者饿死**

**实现 2 — 写者优先**：
- 增加 `tryRead` 信号量，写者到达时先 P(tryRead) 阻止后续读者
- 最后一个写者才 V(tryRead) 放行读者
- **问题**：写者连绵不断 → **读者饿死**

**实现 3 — 公平排队（Ticket Lock）**：
- 读者和写者进入时都先领号排队
- 按顺序依次尝试进入（读者批处理：连续读者可同时进）
- 没有人能插队 → 公平，不会饿死

**POSIX 接口**：`pthread_rwlock_rdlock/wrlock/unlock`。Linux 默认读者优先。

### 3. RCU（Read-Copy-Update）— 无锁同步

**动机**：锁本身有开销（比普通指令多一个数量级）。短临界区下，锁成了性能瓶颈。对于读多写少的场景（内核路由表、用户权限信息），能否让读者完全不阻塞？

**核心思想**：更新的两阶段
1. **Removal（移除）**：删去旧数据的引用，指向新数据。**完全并发于读者**。
2. **Reclamation（回收）**：真正释放旧数据。需等待所有旧读者结束。

```
head ──→ a ──→ c ──→ d ──→ f ──→ k
                      │
                      d' (新数据)
                      
Removal 后: d 的引用被移除，新读者看到 d'
但旧读者可能还在读 d → d 不能立即释放
→ 等所有旧读者结束 (Grace Period) → Reclamation 释放 d
```

**发布-订阅机制**：写者更新指针和读者读取指针需要内存屏障保证顺序。
```c
// 写者：发布更新（含内存屏障）
rcu_assign_pointer(gp, new_gp);

// 读者：订阅数据（含内存屏障）
foo *p = rcu_dereference(gp);
```

**宽限期（Grace Period）**：
- `rcu_read_lock()` / `rcu_read_unlock()` 标记读者临界区
- `synchronize_rcu()`：写者阻塞直到所有旧读者退出
- `call_rcu(callback)`：注册回调，非阻塞等待

**经典 RCU 实现**（简化）：
- 读者侧：`rcu_read_lock` = 关中断，`rcu_read_unlock` = 开中断
- 写者侧：侦测所有 CPU 都做了一次上下文切换 → 旧读者一定结束了 → 安全释放

RCU 在 Linux 内核中广泛应用（10% 以上的锁基于 RCU，2002 年引入 2.5 内核）。

### 4. 哲学家就餐问题（Dining Philosophers）

Dijkstra 1965 年提出（Hoare 修改描述）。5 位哲学家围坐圆桌，每人左右各有一只筷子，必须同时拿到两只才能吃饭。

**方案 1 — 全先拿左边**：
```c
P(forks[left]);  // 拿左边
P(forks[right]); // 拿右边
```
所有人同时拿左边 → 等待环形成 → **死锁**。

**方案 2 — 拿不到右边就放下，随机等**：
```c
P(forks[left]);
if (tryP(forks[right]) != 0) {  // 非阻塞尝试
    V(forks[left]);             // 放下左边
    sleep(random);              // 随机等待
}
```
打破等待环的概率方案。大多数场景够用，但**不是 100% 可靠**（安全攸关场景不行）。

**方案 3 — 限制 N-1 人上桌**：
```c
sem_t capacity = N - 1;
P(capacity);  // 最多 N-1 个哲学家同时尝试
// ...拿筷子吃饭...
V(capacity);
```
**鸽巢原理**：5 只筷子，4 个人抢 → 至少一人能拿到两只。正确且并发度可接受。

**方案 4 — 给筷子编号，总先拿小的**：
```c
if (left < right) {
    P(forks[left]);  P(forks[right]);
} else {
    P(forks[right]); P(forks[left]);
}
```
打破了"环形等待"——编号最大的筷子不会被两个哲学家同时争抢。最简单优雅。

### 5. 死锁 vs 饿死

| | 死锁 (Deadlock) | 饿死 (Starvation) |
|---|---|---|
| 定义 | 多个线程形成等待环 | 线程在有限时间内无法行进 |
| 原因 | 环中每个线程都在等别人释放资源 | 调度不公平，资源一直被抢走 |
| 能否自行解除 | 不能 | 可能（运气好的时候） |
| 关系 | 死锁一定导致饿死 | 饿死不一定是死锁 |

死锁四条件（Coffman 条件）：
1. 互斥：资源不能共享
2. 持有并等待：持有资源的同时等待其他资源
3. 不可抢占：资源不能被强制拿走
4. 循环等待：存在等待环

破坏任何一个即可预防死锁。方案 4 破坏了条件 4（循环等待），方案 2 破坏了条件 2（持有并等待）。

## 难点突破

### 难点 1：RCU 为什么不是"读者优先读写锁"的简单优化？

读写锁中读者也要对 `rwlock` 结构做原子操作（P/V 信号量），这在多核下有 cache line 竞争（多个读者同时修改 `readers` 计数器 → cache coherence 协议导致的延迟）。

RCU 的读者完全不修改任何共享状态（`rcu_read_lock` = 关中断，不写内存），因此可以**线性扩展**——读者数量增加不影响性能。

代价是写者更复杂（两阶段更新 + 宽限期等待）和内存开销（多版本数据并存）。这就是 trade-off：读极致快 vs 写略慢。

### 难点 2：哲学家方案 4 为什么正确？

关键观察：筷子 i 和 i+1 中间是哲学家 i。如果不按编号规则，哲学家可能拿到 i（左手）和 i+1（右手），形成环。

方案 4 强制"先拿编号小的"：哲学家 4 的左手是筷子 4，右手是筷子 0。按规则它必须先拿 0（小的），再拿 4。而筷子 0 也是哲学家 0 的左筷子——哲学家 0 也会先拿 0。两者不可能同时持有筷子 0，因此不可能出现所有人持有一支筷子等另一支的环路。

## 记忆卡片

**Q1: 读者优先和写者优先各有什么问题？**
A: 读者优先 → 写者可能饿死；写者优先 → 读者可能饿死。公平方案用 Ticket Lock 排队。

**Q2: RCU 更新的两个阶段是什么？**
A: Removal（移除旧引用，与读者并发）和 Reclamation（等宽限期后真正释放旧数据）。

**Q3: RCU 宽限期（Grace Period）的作用？**
A: 确保所有还在读旧数据的读者都结束了，才能安全释放旧数据。避免释放读者正在用的内存。

**Q4: 哲学家就餐问题，方案 4 为什么正确？**
A: 强制总先拿编号小的筷子。编号最大的筷子不会被两个哲学家同时争抢，打破循环等待。

**Q5: 死锁和饿死的本质区别？**
A: 死锁 = 等待环，永远无法自行解除；饿死 = 一直没轮到，但理论上有机会。死锁一定饿死，饿死不一定是死锁。

**Q6: 条件变量、信号量、互斥锁的表达能力排序？**
A: 条件变量 + 互斥锁 > 信号量 > 互斥锁。信号量可实现互斥锁但不擅长条件变量；条件变量 + 互斥锁可实现信号量。

## 期末简答题整理

**Q7: 读者-写者问题的三种策略及其优缺点？**

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 读者优先 | 第一个读者抢写锁，最后一个释放 | 读者并发度高 | 读者连绵不断 → 写者饿死 |
| 写者优先 | 写者到达时设 tryRead 信号量阻止后续读者 | 写者不会被饿死 | 写者连绵不断 → 读者饿死 |
| 公平排队 | Ticket Lock 统一排队，连续读者批处理 | 无人饿死 | 实现最复杂 |

**Q8: RCU 为什么要分 Removal 和 Reclamation 两阶段？直接释放旧数据会怎样？**

Removal 阶段删去旧数据引用，新读者只能看到新数据。但此时可能还有旧读者持有旧数据的引用——如果直接 free，那些读者会访问已释放内存（use-after-free）。必须等宽限期（所有旧读者都 rcu_read_unlock）之后，Reclamation 阶段才安全释放。两阶段分离了"不再有新读者"和"旧读者都走了"这两个时刻。

**Q9: RCU 宽限期检测的原理是什么？为什么"所有 CPU 做过上下文切换"就安全了？**

读者在 `rcu_read_lock` 期间禁止抢占/关中断——CPU 无法在该读者还在临界区时发生上下文切换。因此：某 CPU 发生过上下文切换 → 该 CPU 上没有读者在临界区。遍历所有 CPU 确认每颗都至少切换过一次 → 全系统没有旧读者了 → 宽限期结束，安全回收。底层机制：`rcu_read_lock` = 关中断，写者侧对每个 CPU 检测一次上下文切换。

**Q10: RCU 发布-订阅机制中，rcu_assign_pointer 和 rcu_dereference 分别保证什么？如果不用会出什么问题？**

`rcu_assign_pointer`（写屏障）：保证对新节点数据的所有写入，在指针更新对外可见之前完成。防止读者看到新指针但数据还没初始化完（读到半成品）。`rcu_dereference`（读屏障）：保证读取新指针后，再去读其成员时，读到的是该指针关联的最新值。不用这些屏障 → CPU/编译器可能重排序指令 → 读者读到脏数据（use-after-init 顺序颠倒）。

**Q11: 哲学家就餐问题，方案 4（总先拿编号小的叉子）为什么能防止死锁？破坏了哪个 Coffman 条件？**

将叉子编号 0-4。规则：每个哲学家必须先 P 编号小的叉子，再 P 编号大的。关键：哲学家 4 的左手是叉 4、右手是叉 0——它必须先 P(0) 再 P(4)。叉 0 同时是哲学家 0 的左叉，哲学家 0 也会先 P(0)。两者不可能同时持有叉 0 → 不可能出现"所有人持一只等另一只"的环路。破坏了 Coffman 条件 4（循环等待）。

延伸：方案 2（拿不到就放+随机等）破坏了条件 2（持有并等待）；方案 3（限制 N-1 人）没有直接破坏某个条件，但用鸽巢原理保证了至少一人能拿到两只。

**Q12: 死锁的四个 Coffman 条件是什么？各自含义？**

| 条件 | 含义 | 破坏方法示例 |
|------|------|-------------|
| 互斥 | 资源不能共享，一次只能一人用 | 用无锁数据结构（如 RCU） |
| 持有并等待 | 持已有资源同时等新资源 | 一次性申请所有资源，或拿不到就放 |
| 不可抢占 | 资源不能被强制夺走 | 允许强行回收（一般难实现） |
| 循环等待 | 存在 A→B→C→A 的等待环 | 统一编号，按序申请（哲学家方案 4） |

破坏任一条件即可预防死锁。

**Q13: RCU 相比读者-写者锁，为什么读者侧性能好得多？代价是什么？**

读写锁中，读者也要修改共享状态（如 `readers` 计数器原子递增），多核下产生 cache line 竞争（cache coherence 协议的 invalidate/update 延迟）。RCU 读者完全不写任何共享内存（`rcu_read_lock` = 关中断/禁抢占），读者数量增加不影响性能——可线性扩展。代价：写者更复杂（两阶段 + 宽限期等待），内存有额外开销（旧数据多版本并存直到回收），且读临界区不能长时间沉静（关中断影响系统响应）。
