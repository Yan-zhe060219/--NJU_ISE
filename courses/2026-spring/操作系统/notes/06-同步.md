## 一句话总结

互斥只解决"不能同时进"，同步解决"按什么顺序进"——条件变量（condition variable）和信号量（semaphore）是两大同步原语，前者灵活但需手动判条件，后者自带整数状态但表达能力有限。

## 知识地图

```
同步 (Synchronization) = 控制线程执行的相对顺序

生产者-消费者问题 → 引出同步需求
  │
  ├── 错误尝试 1: 无锁 → 竞态条件
  ├── 错误尝试 2: 锁保护 depth + 解锁后判断 → TOCTOU
  ├── 错误尝试 3: 持锁判断+执行 → 正确但忙等
  ├── 错误尝试 4: wait/wakeup → 丢失唤醒
  └── 正确方案: futex wait/wake → 条件变量的雏形
        │
        ▼
条件变量 (Condition Variable)
  ├── cond_wait(cv, lk): 原子释放锁+阻塞，唤醒后重新获取锁
  ├── cond_signal(cv): 唤醒一个等待者
  ├── cond_broadcast(cv): 唤醒所有等待者
  ├── Hansen/Mesa 语义: signal 和唤醒非原子 → 必须 while 循环
  └── Hoare 语义: 原子转移锁 → 条件保证成立（实现复杂）

信号量 (Semaphore)
  ├── P(s): 值>0 则减1；否则阻塞
  ├── V(s): 值+1，有等待者则唤醒
  ├── 初值=1 → 互斥锁 | 初值=0 → happens-before | 初值=N → N个资源
  └── 局限: 只能表达整数状态，"二选一"类型的同步不方便
```

## 核心概念

### 1. 为什么互斥不够？

互斥只保证**同时只有一个线程在临界区**，但不保证执行顺序。线程同步需要控制"不能太快"（等条件满足）和"不能太慢"（条件满足了就得继续）。

同步问题的一般形式：**生产者-消费者问题**（Dijkstra 提出，能代表绝大多数并发问题）。

### 2. 生产者-消费者问题

一个或多个线程共享有界缓冲区：
- 生产者：缓冲区有空位 → 放入数据；否则等待
- 消费者：缓冲区有数据 → 取走数据；否则等待

简化版（打印括号）：`depth` = 当前缓冲区使用量，produce 打印 `(`（要求 depth < n），consume 打印 `)`（要求 depth > 0）。

### 3. 解决方案的演进

**尝试 1**：直接判断 depth，无锁 → 竞态条件（depth 是共享变量）。

**尝试 2**：用互斥锁保护 depth 的读取，但解锁后才判断 ready → read 和 use 之间有窗口，另一线程可能篡改 depth（TOCTOU）。

**尝试 3**：持锁判断+执行 → 正确。但条件不满足时要先解锁再重试（忙等），且反复加解锁性能差。

**尝试 4**：用 wait/wakeup 阻塞代替忙等 → **丢失唤醒**（unlock 和 wait 之间，wakeup 已经发出）。

**尝试 5**：用 futex 解决丢失唤醒 → 每次 wait 前用原子变量记录当前"版本号"，futex_wait 二次检查值是否变化。这本质上就是条件变量的实现。

### 4. 条件变量（Condition Variable）

两个核心操作：

```c
cond_wait(cond_t *cv, mutex_t *lk):
    1. 原子地：释放 lk + 阻塞自己
    2. 被唤醒后：重新获取 lk

cond_signal(cond_t *cv):
    唤醒一个等在 cv 上的线程（无等待者时什么也不做）
```

**实现原理**（基于 futex）：
```c
void cond_wait(cond_t *cv, mutex_t *lk) {
    int val = atomic_load(&cv->value);  // 记录当前版本
    mutex_unlock(lk);
    futex_wait(&cv->value, val);        // 值未变才阻塞
    mutex_lock(lk);
}

void cond_signal(cond_t *cv) {
    atomic_fetch_add(&cv->value, 1);    // 改变版本号
    futex_wake(&cv->value);
}
```

**关键设计：为什么必须是"先改值、后唤醒"？**

如果顺序反过来（先 futex_wake 再 atomic_add），存在丢失唤醒窗口：

```
消费者                                  生产者
───────                                ──────
val = cv->value;  // = 5
mutex_unlock();
                                       futex_wake(&cv->value); // 没人睡，空唤醒！
futex_wait(&cv->value, 5);
  → 内核检查：value == 5，等于 val
  → 没变 → 真正入睡
                                       atomic_add(&cv->value, 1); // 5→6
                                       // 没有第二次 wake 了！消费者永久丢失
```

正确顺序下，即使 wake 发生在线程 futex_wait 之前，futex_wait 也会发现值变了，直接返回不睡眠。

**用 futex 直接实现生产者-消费者**（条件变量底层原理完整展示）：

```c
int cnd1 = 0;   // 生产者条件 futex（等"有空位"）
int cnd2 = 0;   // 消费者条件 futex（等"有数据"）
int depth = 0;
mutex_t lk;

void produce() {
    while (1) {
retry:
        mutex_lock(&lk);
        if (!(depth < n)) {           // 条件不满足
            int val = cnd1;           // ① 快照版本号
            mutex_unlock(&lk);
            futex_wait(&cnd1, val);   // ② 值没变则睡，变了立即返回
            goto retry;               // ③ 醒来重新抢锁+重判条件
        }
        printf("("); depth++;
        atomic_add(&cnd2, 1);         // ④ 先改版本号
        futex_wake(&cnd2);            // ⑤ 再唤醒消费者
        mutex_unlock(&lk);
    }
}

void consume() {
    while (1) {
retry:
        mutex_lock(&lk);
        if (!(depth > 0)) {
            int val = cnd2;
            mutex_unlock(&lk);
            futex_wait(&cnd2, val);
            goto retry;
        }
        printf(")"); depth--;
        atomic_add(&cnd1, 1);
        futex_wake(&cnd1);
        mutex_unlock(&lk);
    }
}
```

这段代码就是条件变量的手工展开版——`cnd1`/`cnd2` 分别扮演 `cv_p`/`cv_c`。不丢唤醒的根源：futex_wait 在值变化时直接返回，不在窗口期遗漏 signal。

**条件变量数据结构**（极简）：
```c
typedef struct {
    int futex;          // 版本号，futex_wait 用它检查"值是否变化"
    // 隐式：内核维护的等待队列
} cond_t;
```
条件变量不存储"条件"——条件在共享状态（depth）里。条件变量只管线程的阻塞和唤醒。

### 5. Hansen/Mesa vs Hoare 语义

这是条件变量最核心的概念区分：

| | Hansen/Mesa | Hoare |
|---|---|---|
| signal→唤醒 | **非原子** | **原子** |
| signal 后 | 被唤醒线程可能抢不过第三者 | 锁直接转移给被唤醒线程 |
| 条件保证 | 不保证（条件可能被第三者破坏） | 保证 |
| 代码写法 | `while(!cond) cond_wait(...)` | `if(!cond) cond_wait(...)` |
| 实现难度 | 简单（默认行为） | 复杂（需调度器配合） |
| 实际采用 | POSIX、Java、绝大多数 OS | PL 研究界 |

**Hansen/Mesa 语义的金科玉律**：`cond_wait` 必须放在 `while` 循环里，唤醒后重新检查条件！

**为什么 if 是致命的——两个消费者竞争场景：**

```c
// 错误写法（if）
if (!(depth > 0))
    cond_wait(&cv_c, &lk);
// 此时 depth 可能已经 == 0 了！

// 正确写法（while）
while (!(depth > 0))
    cond_wait(&cv_c, &lk);
// 醒来再检查一次，不满足继续睡
```

具体时间线：
```
消费者 C1（先到）         消费者 C2（后到，抢先）        生产者 P
───────────────           ────────────────────          ──────
while(!(depth>0))
  cond_wait → 睡眠
                          mutex_lock → depth==0
                          while → cond_wait → 睡眠       mutex_lock
                                                         depth++ → signal
C1 被唤醒，抢锁...
  但 C2 抢先拿到锁！       mutex_lock 成功
                          depth--, depth 归零
                          mutex_unlock
C1 终于拿到锁
  → depth == 0！
  → if 已过，继续消费 → UB ❌     → while 重检，发现不满足，再睡 ✅
```

Hansen/Mesa 语义下，从被唤醒到重新获取锁之间，条件可能被第三者（C2）破坏。while 本质上把条件判断从"唤醒即满足"变成了"醒来再验证"。

**常见错误汇总：**

| 错误写法 | 后果 | 正确写法 |
|---------|------|---------|
| `if(!cond) cond_wait()` | 第三者破坏条件后继续执行 → UB | `while(!cond) cond_wait()` |
| signal 在 unlock 之后 | 被唤醒者抢锁撞墙，多一次上下文切换 | unlock 后再 signal（性能优化，语义正确即可） |
| 单条件变量 + signal | 生产者唤醒生产者 → 死锁 | 双条件变量 + signal，或单条件变量 + broadcast |

### 6. 条件变量的正确使用法则

1. 必须有**共享状态**用于判定条件（不能只用条件变量）
2. 用**互斥锁**保护共享状态和条件变量操作
3. wait/signal/broadcast 时**持有互斥锁**
4. wait 必须在 **while 循环**中（Hansen/Mesa 语义）
5. 不同条件用**不同的条件变量**（除非用 broadcast）

### 7. 为什么需要两个条件变量？

生产者-消费者中有两个不同的等待条件：
- 生产者等"有空位"（`cv_p`）
- 消费者等"有数据"（`cv_c`）

如果只用一个条件变量 + signal：生产者生产后 signal，可能唤醒的是另一个生产者（它检查条件不满足，又睡），而该被唤醒的消费者没被唤醒 → **所有人都永远睡着**。

解决方案：
- **两个条件变量**：精确唤醒正确的线程类别
- **broadcast**：一次全唤醒，不该醒的 while 检查后自动回去睡（简单但性能差）

### 8. 条件变量的应用：计算图并行化

给定 DAG 计算图 G = (V, E)，(u, v) ∈ E 意味着 v 需要 u 的结果。

并行化策略：
- 每个节点 v：wait 所有前驱 u 都完成 → 执行计算 → signal/broadcast 所有后继
- 可进一步抽象为**线程池**：调度线程维护计算图，找出 ready 节点放入队列；worker 线程从队列取任务执行

这就是动态规划的并行版本（如 Edit Distance 的对角线并行）。

### 9. 信号量（Semaphore）

Dijkstra 1965 年提出。一个整数值 + 两个原子操作：

```c
P(sem_t *s):  // wait / down / acquire
    while (s->value <= 0)  // 值不是正数就阻塞
        wait();
    s->value--;

V(sem_t *s):  // post / up / release
    s->value++;
    wake_one_waiter();
```

**初始值的含义**（"资源数"视角）：
- **1**：互斥锁（binary semaphore）——只有 1 个资源，谁拿到谁进
- **0**：顺序控制（happens-before）——没资源就得等，直到有人 V 释放
- **N**：N 个资源可用，直到被 P 完

**初值 = 0 的 happens-before 程序**（经典考题）：

```c
sem_t sem;
sem_init(&sem, 0, 0);   // X = 0

int main() {
    create_thread(&c, child);
    P(&sem);               // 父线程：等子线程完成
    do_something();        // ← 这行严格在子线程 V 之后执行
    return 0;
}

void *child(void *arg) {
    do_something();        // 子线程：先干活
    V(&sem);               // 告诉父线程"我完成了"
    return NULL;
}
```

初值必须为 0 的原因：P 在 value ≤ 0 时阻塞。X=0 意味着"一开始没有资源"——父线程想 P 但计数器 = 0，只能等子线程 V 后计数器变 1 才能通过。X=1 则父线程直接通过 P，happens-before 失效。

时间线分析：
```
初值 X=0，父先到 P:                   初值 X=0，子先完成:
  父 P → 0≤0 阻塞 😴                   子 V → 0→1
  子 V → 0→1，唤醒父                    父 P → 1>0，1→0，直接通过
  父 醒来 → do_something()             父 do_something()
  ✅ 父严格在子之后                      ✅ 子已完成，父直接过
```

两种时间线下，父都不可能在子之前执行。P/V 之间建立了 happens-before 顺序。

**与其他原语对比**：信号量的 happens-before（初值 0）语义上等价于：
- 条件变量版：`while(!done) cond_wait(&cv, &lk)` + `done=1; cond_signal(&cv)`
- futex 版：`futex_wait(&done, 0)` + `done=1; futex_wake(&done)`

区别在于信号量把"计数器"和"等待/唤醒"融合成一个东西——不需要额外的状态变量和条件判断。

**初值 X=1 为什么错**：`P` 在 value>0 时直接减 1 通过，不阻塞 → 父可能在子之前执行 do_something() → 没有 happens-before。

**用信号量解 P-C 问题**（极其简洁）：
```c
sem_t empty = MAX;  // 缓冲区空位数
sem_t full = 0;     // 缓冲区数据数

void produce() {
    P(&empty);      // 等空位（空位数 -1）
    printf("(");
    V(&full);       // 数据数 +1，唤醒消费者
}

void consume() {
    P(&full);       // 等数据（数据数 -1）
    printf(")");
    V(&empty);      // 空位数 +1，唤醒生产者
}
```

**信号量的局限**：V 操作无法指定唤醒哪类线程（"二选一"型同步不便），整数状态无法表达非整数条件。

### 10. 互斥锁、条件变量、信号量的关系

```
信号量 = 互斥锁 + 条件变量 + 整数计数器

条件变量 = 更灵活的信号量（条件可以是任意布尔表达式）

互斥锁 = 初值为 1 的信号量（只有互斥功能）
```

实现关系：信号量可以用互斥锁 + 条件变量实现，条件变量可以用 futex 实现。

## 难点突破

### 难点 1：为什么 cond_wait 要传入互斥锁？

`cond_wait(cv, lk)` 不是简单的"阻塞自己"——它需要**原子地**完成两个操作：释放锁 + 阻塞。

如果不原子：释放锁之后、阻塞之前，另一个线程可能 signal（此时该线程还没阻塞，signal 丢失）。传入的锁让 cond_wait 能够在内核层面原子完成"解锁+睡眠"，避免丢失唤醒。

### 难点 2：Hansen/Mesa 语义下为什么必须 while 而不是 if？

```
// 错误写法（if）:
if (!condition)
    cond_wait(&cv, &lk);
// 此时 condition 可能被第三者破坏了！

// 正确写法（while）:
while (!condition)
    cond_wait(&cv, &lk);
// 醒来后再检查一次，不满足继续睡
```

场景：消费者 C₁ 被 signal 唤醒，但在它获得锁之前，另一个消费者 C₂ 抢先进入临界区消费了数据。C₁ 获取锁后，condition 已不成立——如果用 `if`，C₁ 会错误地继续执行。

`while` 本质上把条件判断从"唤醒即满足"变成了"醒来再验证"。

## 记忆卡片

**Q1: 互斥和同步的区别是什么？**
A: 互斥 = "不能同时进"（安全）；同步 = "按什么顺序进"（控制 happens-before）。互斥是同步的一种特例。

**Q2: 条件变量的两个操作及其语义？**
A: cond_wait(cv, lk) = 原子释放 lk + 阻塞，醒来后重获 lk；cond_signal(cv) = 唤醒一个等待者。

**Q3: Hansen/Mesa 和 Hoare 语义的核心区别？**
A: Hansen/Mesa 中 signal 和唤醒非原子（默认，须 while 循环）；Hoare 中原子转移锁（条件保证成立，但实现复杂）。

**Q4: cond_wait 为什么必须在 while 循环中？**
A: Hansen/Mesa 语义下，从被唤醒到获得锁之间，条件可能被其他线程破坏。while 保证醒来后重新验证。

**Q5: 信号量初值 0、1、N 分别代表什么？**
A: 0 = happens-before（等别人 V）；1 = 互斥锁；N = N 个可用资源。

**Q6: 生产者-消费者用信号量为什么比用条件变量简洁？**
A: 信号量自带整数状态——empty/full 两个信号量天然追踪缓冲区空位和数据数，不需要手动维护 depth 和 while 条件。

## 期末简答题整理

**Q7: 简述生产者-消费者问题的五种错误尝试及其对应的问题。**

| 尝试 | 方法 | 问题 |
|------|------|------|
| 1 | 无锁直接判断 depth | 竞态条件（depth 是共享变量） |
| 2 | 锁保护读取，解锁后判断 | TOCTOU——读和用之间有窗口 |
| 3 | 持锁判断+执行 | 正确但忙等，反复加解锁性能差 |
| 4 | wait/wakeup 阻塞替代忙等 | 丢失唤醒——unlock 和 wait 之间 wakeup 已发出 |
| 5 | futex wait/wake（二次检查值） | **正确**——futex_wait 检查值是否变化，消除丢失唤醒 |

**Q8: 为什么条件变量必须与 while 配合而非 if？画出关键时间线说明。**

两个消费者 C1、C2 都等数据。生产者 P 生产一个 → signal 唤醒 C1。C2 抢先获得锁，消费数据使 depth 归零。C1 获得锁后：用 `if` 则不再检查条件，在 depth==0 时错误消费（UB）；用 `while` 则重新检查，发现条件不成立，继续睡眠。根本原因是 Hansen/Mesa 语义下 signal 和唤醒非原子，条件在唤醒到获得锁之间可能被第三者破坏。

**Q9: 条件变量 signal 操作中，为什么必须"先 atomic_add 改值，后 futex_wake 唤醒"？反过来会怎样？**

反过来（先 wake 后 add）：等待者在 futex_wait 之前收到了空唤醒（无人睡眠），接着 futex_wait 检查值时发现值未变（因为 add 还没执行），判定无人 signal，真正入睡。随后的 atomic_add 虽然改了值，但没有第二次 wake——等待者永久丢失。正确顺序下，即使 wake 先于 futex_wait 发出，futex_wait 也会发现值已变化，直接返回不睡眠。

**Q10: 信号量实现 happens-before 顺序控制时，初值为什么必须是 0？**

P 操作在 value ≤ 0 时阻塞。初值 = 0 意味着"一开始没有资源"——父线程执行 P 时计数器 = 0，必须阻塞等待子线程执行 V（value: 0→1）后才能通过，建立了父严格在子之后的 happens-before 关系。初值 = 1 则父线程 P 时 value > 0，直接通过不阻塞，可能在子之前执行，happens-before 失效。

**Q11: 对比信号量和条件变量在生产者-消费者问题中的实现差异。**

| 维度 | 条件变量 | 信号量 |
|------|---------|--------|
| 共享状态 | 手动维护 depth | 不需要——empty/full 就是状态 |
| 条件判断 | `while(!cond)` 手动写 | P 内置"等计数器 > 0" |
| 通知 | cond_signal 手动调用 | V 内置通知 |
| 代码行数 | ~10 行 | ~6 行 |
| 灵活性 | 条件可以是任意布尔表达式 | 条件只能是"计数器 > 0" |

信号量把"计数器 + 等待 + 唤醒"融合成一个原语，对于能用整数表达的同步问题（如 P-C、资源池、限流），信号量更简洁。对于复杂条件（如"等 A 且 B 都完成"），条件变量 + while 更灵活。

**Q12: cond_wait 为什么必须传入互斥锁？如果不传会怎样？**

如果自己写 `unlock(lk); futex_wait(cv, val)`，两个操作之间有窗口：unlock 后、futex_wait 前，signal 可能已经发出。此时该线程还没开始等 → 丢失唤醒。传入锁让内核把"unlock + 标记自己为等待者"作为一个原子操作完成，消除此窗口。
