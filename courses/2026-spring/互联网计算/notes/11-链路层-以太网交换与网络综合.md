## 一句话总结

以太网（Ethernet）是统治性的有线 LAN 技术，交换机通过自学习（self-learning）构建转发表实现即插即用帧转发；VLAN 在物理交换机之上定义虚拟隔离广播域；MPLS 用固定长度标签实现广义转发——入口决策、核心执行，是 SDN 的精神先驱；数据中心以富互连拓扑 + SDN 构成现代网络基础设施；最后用"一次 Web 请求的完整旅程"将 DHCP → ARP → DNS → TCP → HTTP 五层封装串联，完成整门课程的综合回顾。

## 场景设定：帧到达交换机之后

上一章（10 号笔记）我们跟着一个以太网帧，从 NIC 封装出发，经过 CSMA/CD 信道竞争，最终被目的主机的 NIC 接收。但我们刻意跳过了中间最关键的一环——**局域网交换机（Ethernet Switch）**。

帧通过网线到达的，不是直接连到目的主机，而是先到达交换机的一个端口。交换机内部发生了什么？它怎么知道这个帧该从哪个端口转发出去？如果它不知道目的 MAC 在哪怎么办？如果 LAN 里有成千上万台主机，广播风暴会不会淹没整个网络？

这就是本章要解决的问题。我们从交换机内部开始，逐步外推到企业级 VLAN 隔离、运营商级 MPLS 加速、超大规模数据中心，最后用"一次 Web 请求"的全栈旅程，把五层协议栈的每一层串起来。

> "Our journey down the protocol stack is now complete!" —— 课件以这句话收尾。本章是整门课的收官之作。

## 一、以太网帧结构——6 个字段的精确分工

在深入交换机之前，先看清它处理的对象——以太网帧长什么样。

### 1.1 逐字段拆解

```
┌──────────┬──────────┬──────────┬──────┬──────────────┬──────┐
│ Preamble │ Dest MAC │ Src MAC  │ Type │    Data      │ CRC  │
│  8 bytes │  6 bytes │  6 bytes │ 2 B  │ 46-1500 bytes│ 4 B  │
└──────────┴──────────┴──────────┴──────┴──────────────┴──────┘
```

| 字段 | 大小 | 做什么 | 为什么需要 |
|------|------|--------|-----------|
| **Preamble（前导码）** | 8 字节 | 7 字节 `10101010…` + 1 字节 `10101011`（SFD，帧首定界符） | 收发双方时钟同步——NIC 需要知道"比特从哪开始"。类比：音乐会开始前指挥棒敲三下——所有人对齐节奏 |
| **Destination MAC** | 6 字节 | 目的 MAC 地址 | 交换机/接收 NIC 用它判断"是不是给我的" |
| **Source MAC** | 6 字节 | 源 MAC 地址 | 交换机用它**学习**——"从端口 3 来的帧，源 MAC 是 A，说明 A 在端口 3 方向" |
| **Type（类型）** | 2 字节 | 指示上层协议（`0x0800` = IPv4, `0x86DD` = IPv6, `0x0806` = ARP） | 接收端解封装时知道把数据交给网络层的哪个协议——IP 还是 ARP？这就是**多路分解（demultiplexing）** |
| **Data（Payload）** | 46-1500 字节 | 封装的网络层数据报（通常 IP 数据报） | 最小 46 字节是为了 CSMA/CD 碰撞检测能正常工作——帧太短来不及检测到碰撞就发完了。不够 46 字节时填充（pad） |
| **CRC** | 4 字节 | 32 位循环冗余校验（CRC-32） | 检测帧在传输中是否损坏。校验失败 → 直接丢弃，不上交网络层 |

### 1.2 以太网的服务模型：无连接，不可靠

> "Ethernet: 'dominant' wired LAN technology — first widely used LAN technology, simpler, cheap, kept up with speed race: 10 Mbps – 400 Gbps"

以太网从 10 Mbps 一路演进到 400 Gbps，但两个核心特性始终不变：

- **Connectionless（无连接）**：发送和接收 NIC 之间**无握手**（no handshaking）。有帧就发，不管对方是否准备好
- **Unreliable（不可靠）**：接收 NIC **不发 ACK 或 NAK**。CRC 校验不过 → 帧丢弃 → 数据恢复**完全交给上层（TCP）**。如果上层没有可靠传输（如 UDP），丢的数据就永久丢失

**类比**：以太网像邮政明信片——写上地址就扔进邮筒，不确认对方收没收到。TCP 像挂号信——必须签收，丢了补发。

**为什么这样设计？** 和上一章 CRC 只在链路层做检测不做纠正的逻辑一致：有线链路（光纤/双绞线）误码率极低，逐跳确认会增加不必要的延迟。把可靠性推到端到端——TCP 只关心"最终到了没"，链路层只管"这一跳传过去有没有错"。

802.3 以太网标准家族：所有标准共享**相同的 MAC 协议和帧格式**，区别只在速率（2M ~ 400G）和物理介质（铜双绞线、光纤）。这意味着不论你插的是百兆网线还是万兆光纤，帧结构完全一样——这正是分层的好处。

## 二、交换机——帧的智能分拣员

### 2.1 交换机是什么？

> "Switch is a link-layer device: takes an active role — store, forward Ethernet frames; examine incoming frame's MAC address, selectively forward frame to one-or-more outgoing links"

交换机是**链路层设备**——它只看 MAC 地址，不碰 IP 头部。和集线器（hub）有本质区别：集线器是**物理层设备**，收到信号后向所有端口复制转发，所有连在同一集线器上的主机共享一个碰撞域。交换机工作在链路层，有"智能"——它能**选择性地**把帧只转发到目的主机所在的端口，其他端口不被打扰。

四个关键特征：
- **存储转发（Store and Forward）**：收到完整帧、CRC 校验通过后，才查表转发。这引入了少量延迟，但避免了转发损坏的帧
- **检查 MAC 地址**：只看帧头部的 MAC 地址字段，不碰 IP 层
- **透明（Transparent）**：主机不知道交换机的存在——主机发出的帧和直连对方主机时一模一样
- **即插即用、自学习（Plug-and-Play, Self-Learning）**：无需任何配置，插上就能工作

### 2.2 自学习机制——交换机怎么知道谁在哪？

交换机的核心是一个**交换机表（switch table）**：`<MAC address, interface, TTL>`。这张表不是手工配置的，也不是路由协议算的——它是**从经过的帧中自动学习**的。

收到一个帧时，交换机做两件事：

**学习（Learning）**：记下这个帧的**源 MAC 地址**和**入接口**。既然帧从端口 3 进来、源 MAC 是 A，说明主机 A 在端口 3 方向——以后发给 A 的帧就从这个端口走。

**转发（Forwarding）**：查目的 MAC 在不在表里。

```
收到帧：dest = B's MAC, src = A's MAC, 入端口 = 3

Step 1 — 学习：记录 <A's MAC → port 3> 到交换机表

Step 2 — 查表转发：
  ┌─ B 在表中，port = 5 → 从 port 5 转发
  ├─ B 在表中，port = 3 → 丢弃！（源和目的在同一端口，B 应该已经直接收到了）
  └─ B 不在表中 → 泛洪（flood）！向除 port 3 外的所有端口转发
```

**为什么泛洪？** 交换机不知道 B 在哪，但 B 如果存在，一定连在某个端口上。泛洪就是"喊一嗓子"——B 收到了会回复，回复的帧经过交换机时，交换机就学到了 B 的位置。这是**逐跳的、概率保证的**学习方法，不需要全局拓扑知识。

**类比**：你到一个新公司，不知道张三坐哪。你在大办公室里喊"张三！"——全办公室都听到了，张三回答"这儿！"——从此你知道张三坐第 3 排。交换机就是这样记住每个 MAC 地址的位置的。

### 2.3 多交换机级联——全网自动发现

多台交换机级联时，自学习机制同样有效：

```
  [A] ─── [Switch1] ─── [Switch2] ─── [B]
```

A 第一次发帧给 B → Switch1 泛洪（不知道 B 在哪）→ Switch2 收到泛洪帧 → Switch2 学到 A 在 Switch1 方向 → Switch2 继续泛洪 → B 收到 → B 回复 → Switch2 学到 B → Switch1 学到 B 在 Switch2 方向。

几轮之后，所有交换机都知道所有主机的 MAC 对应哪个端口。无需配置、无需路由协议、无需中央控制器——这就是**即插即用**的威力。

两个注意点：
- 自学习交换网络**不能有环路**——否则泛洪帧会永远在环里转。解决方案是 STP（生成树协议，Spanning Tree Protocol），逻辑阻塞部分端口使拓扑变成无环树
- 交换机表中的条目有 **TTL**（老化时间）——一段时间没有来自某 MAC 的帧，条目自动删除。为什么？主机可能换了端口、关了机、拔了网线。不加 TTL 的话表会越来越大且越来越错

### 2.4 交换机 vs 路由器

| | 交换机（Switch） | 路由器（Router） |
|---|---|---|
| **工作层** | 链路层（第 2 层） | 网络层（第 3 层） |
| **检查的头部** | 以太网帧头（MAC 地址） | IP 数据报头（IP 地址） |
| **转发表建立** | 自学习（flood + learn），即插即用 | 路由算法（OSPF/BGP），需配置或协议交换 |
| **转发依据** | MAC 地址（扁平，48 位） | IP 地址前缀（分层，32 位） |
| **广播域** | 所有端口同一广播域（默认） | 每个接口独立广播域 |

交换机网络还有一个巨大优势：每个链路是**独立的碰撞域**、支持**全双工**。A→A' 和 B→B' 可以**同时进行**，互不干扰。这和上一章 CSMA/CD 的共享信道竞争形成了鲜明对比——在现代交换网络中，**碰撞几乎不存在了**，因为每台主机独占一条到交换机的链路。

## 三、VLAN——一台交换机变多台

### 3.1 为什么需要 VLAN？

交换机解决了碰撞域的问题，但没有解决**广播域**的问题。默认情况下，交换机的所有端口属于同一个广播域——ARP 广播、DHCP 发现、未知目的 MAC 的泛洪……全部到达**每一个**端口。当 LAN 从几十台主机扩展到几千台时，三个问题浮现：

1. **扩展性**：广播流量（ARP、DHCP、泛洪）淹没整个 LAN，每台主机都要处理大量与自己无关的广播帧
2. **安全/隐私**：计算机系的 ARP 请求不应到达电子系。同一个物理交换机上不同部门的流量应该隔离
3. **管理**：员工换办公室——物理端口变了，但逻辑上还想留在原部门

**VLAN（Virtual LAN，虚拟局域网）**正是解决这三个问题的方案。核心思想：**一个物理交换机 = 多个虚拟交换机**。

### 3.2 基于端口的 VLAN（Port-based VLAN）

通过交换机管理软件将端口分组——端口 1-8 属于 VLAN 10（CS 系），端口 9-16 属于 VLAN 20（EE 系）。

```
物理交换机
┌─────────────────────────────┐
│  VLAN 10          VLAN 20  │
│  [1][2]…[8]      [9]…[16] │
│     虚拟交换机1      虚拟交换机2 │
└─────────────────────────────┘

- VLAN 10 内的帧只能在端口 1-8 之间转发，到达不了 VLAN 20
- VLAN 20 的广播不会打扰 VLAN 10 的主机
- 这相当于"买了两个小交换机"——但只需一台物理设备
```

关键特性：
- **流量隔离**（traffic isolation）：VLAN 端口组的帧只能到达同组端口
- **动态成员**（dynamic membership）：端口可在 VLAN 间动态重新分配——软件配置即可，不用拔网线
- **VLAN 间转发**：通过路由完成。不同 VLAN 就像不同子网——需要路由器（或三层交换机）来转发 IP 数据报

### 3.3 跨交换机 VLAN——802.1Q

单台交换机上的 VLAN 容易。但企业里一栋楼有多台交换机——VLAN 10 的主机可能分散在三台交换机上。怎么让跨交换机的 VLAN 帧保持"我属于 VLAN 10"的身份？

**Trunk 端口（干线端口）**：连接两台交换机的端口被配置为 trunk 模式。Trunk 端口承载**所有 VLAN** 的帧，但每个帧必须携带 VLAN ID 标签——否则对端交换机不知道这个帧该归哪个 VLAN。

**802.1Q 协议**在标准以太网帧中插入 4 字节标签：

```
原始以太网帧:
┌──────┬───────┬──────┬──────────┬──────┐
│DMAC  │ SMAC  │ Type │  Data    │ CRC  │
└──────┴───────┴──────┴──────────┴──────┘

802.1Q 帧:
┌──────┬───────┬──────────┬──────┬──────────┬──────┐
│DMAC  │ SMAC  │ 0x8100   │VLAN  │  Type    │ Data │ CRC  │
│      │       │(TPID)    │info  │          │      │(重算)│
└──────┴───────┴──────────┴──────┴──────────┴──────┘
                       ← 4 字节 802.1Q 标签 →
                       Tag Protocol ID (0x8100) + Tag Control Info
                       TCI = 3位优先级 + 1位DEI + 12位VLAN ID
```

12 位 VLAN ID → 最多 4094 个 VLAN（0 和 4095 保留）。

**简单场景**：SW1 的端口 3（VLAN 10）收到帧 → 加上 VLAN ID=10 的 802.1Q 标签 → 从 trunk 端口发出 → SW2 的 trunk 端口收到 → 识别 VLAN ID=10 → 剥掉标签 → 只向 VLAN 10 的端口转发。两台交换机上的 VLAN 10 端口，逻辑上属于"同一台虚拟交换机"。

### 3.4 VXLAN / EVPN——跨越数据中心的 L2

802.1Q 只能在同一 L2 域内工作（VLAN ID 只有 12 位，跨不了 IP 路由器）。如果需要把两个数据中心的同一 VLAN 连接起来——中间隔着互联网——怎么做？

**VXLAN（Virtual eXtensible LAN）**：把以太网帧封装在 UDP/IP 数据报中进行隧道传输。外层 IP 负责跨数据中心传输，内层以太网帧保持原始的 VLAN 信息。

> "a tunneling scheme to overlay Layer 2 networks on top of Layer 3 networks" [RFC 7348]

**类比**：你要把一个玻璃杯从上海送到北京——不能直接扔车里（会碎）。你把它包上泡沫纸（VXLAN 封装），装进快递箱（UDP/IP），箱子到了北京再拆开，杯子完好如初。原始以太网帧就是那个杯子——在 L3 网络中传输时被"裹"了起来。

## 四、MPLS——标签比 IP 更快

### 4.1 MPLS 要解决什么问题？

IP 路由的最大瓶颈是**最长前缀匹配（LPM）**——每台路由器在转发表中查找目的 IP 的最长匹配前缀，时间复杂度 O(log N)。核心路由器有几万条路由表项，每个分组都要做一次 LPM 查找。

**MPLS（Multiprotocol Label Switching，多协议标签交换）**换了一条路：在入口给分组打上**固定长度标签**，后续路由器只按标签查表转发——O(1) 查表，远比 LPM 快。借用课件原话：

> "MPLS: high-speed IP forwarding among network of MPLS-capable routers, using fixed length label (instead of shortest prefix matching) — borrowing ideas from Virtual Circuit approach, but IP datagram still keeps IP address!"

**MPLS 头部**插入在以太网头部和 IP 头部之间：

```
| Label (20 bits) | Exp (3 bits) | S (1 bit) | TTL (8 bits) |
                   实验/CoS       栈底标志
```

### 4.2 MPLS 的核心机制

**入口路由器（Ingress LSR）**：收到 IP 数据报 → 查 MPLS 转发表（可基于源+目的，不只是目的）→ 打标签 → 转发。

**中间路由器（Transit LSR）**：只按标签查表 → 交换（swap）标签 → 转发。**不检查 IP 头部，不做 LPM。**

**出口路由器（Egress LSR）**：剥掉标签 → 恢复为纯 IP 数据报 → 正常 IP 路由。

**类比**：快递中转站。普通 IP 路由 = 每个中转站都要看完整地址"江苏省苏州市工业园区××路××号"来判断下一站。MPLS = 入口站看了完整地址后，贴个标签"去 3 号分拣口"，后面所有站只认"3 号"这个标签——不用再看完整地址。

### 4.3 为什么说 MPLS 是 SDN 的精神先驱？

> "MPLS routing: path to destination can be based on source and destination address — flavor of generalized forwarding (MPLS 10 years earlier)"

三种超越传统 IP 路由的能力：

| 能力 | 说明 |
|------|------|
| **流量工程（Traffic Engineering）** | 同一目的地的不同源地址可以打不同标签、走不同路径。IP 路由做不到——IP 只看目的地址 |
| **快速重路由（Fast Reroute）** | 预计算备份路径，链路故障时毫秒级切换到备路。比 OSPF/BGP 的收敛快得多 |
| **广义转发** | 入口路由器做决策（打标签），下游只执行（按标签转发）。**决策与执行分离**——这恰好是 SDN 的核心哲学 |

MPLS 和 SDN 的共同基因是**将转发决策与转发执行分离**：
- MPLS：入口 LSR 做决策（选择标签路径），下游 LSR 执行（按标签转发）
- SDN：控制器做决策（计算流表），交换机执行（按流表匹配+转发）
- 通信机制不同（RSVP-TE vs OpenFlow），但**架构逻辑一致**

MPLS 比 SDN 早了约十年——不是同一个东西，但蕴含了同样的设计哲学。

### 4.4 MPLS 信令——标签路径怎么建立？

不能手工为每个入口-出口对配置标签路径。MPLS 需要信令协议自动建立：

- 链路状态路由协议（OSPF/IS-IS）被**扩展**——洪泛时携带 MPLS 路由所需信息（带宽、预留带宽）
- 入口路由器使用 **RSVP-TE**（Resource Reservation Protocol - Traffic Engineering）信令协议，沿路径向下游路由器发送 PATH 消息，沿途建立 MPLS 转发条目
- 下游路由器沿反向路径回复 RESV 消息，分配标签

最终效果：入口路由器可以为一个**流（flow）**——比如视频会议流量（源 X → 目的 Y，要求低延迟高带宽）——建立一条独占的高带宽标签路径，和网页浏览流量（同样目的 Y 但走默认路径）物理分离。

## 五、数据中心网络——互联网的"工厂车间"

### 5.1 规模与挑战

数据中心是现代互联网的"工厂"——数十万台服务器紧密耦合，承载着电商、视频、搜索、AI 训练。Google、Amazon、Microsoft 各自运营着上百个数据中心。

三大挑战：
- **海量客户端**：数百万用户同时访问，每个请求可能触及数十台后端服务器
- **可靠性**：单台服务器随时可能挂（磁盘坏、电源烧、内存错），网络不能跟着瘫痪
- **负载均衡**：请求必须均匀分散到可用服务器，避免"一台忙死，九台闲着"
- **避免瓶颈**：处理能力、网络带宽、存储 I/O ——任何一个环节成为瓶颈都会拖垮整体

### 5.2 网络层次结构

```
                     Internet
                         │
                 ┌───────┴───────┐
                 │ Border Router  │ ← 连接外部，运行 BGP
                 └───────┬───────┘
                         │
                 ┌───────┴───────┐
                 │ Tier-1 Switch  │ ← 聚合，连接 ~16 个 T2
                 └───────┬───────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
    ┌─────┴─────┐  ┌─────┴─────┐  ┌─────┴─────┐
    │Tier-2 SW  │  │Tier-2 SW  │  │Tier-2 SW  │ ← 连接 ~16 个 TOR
    └─────┬─────┘  └─────┬─────┘  └─────┬─────┘
          │              │              │
    ┌─────┴─────┐       ...            ...
    │ TOR SW    │ ← 架顶交换机，100G-400G 连 blades
    └─────┬─────┘
          │
    ┌─────┴─────────────┐
    │ Rack (20-40 服务器) │
    └───────────────────┘
```

**TOR（Top of Rack，架顶交换机）**：每机架一台，是这个机架所有服务器的"第一跳"。TOR 往上连到汇聚层，往下连到每台服务器。

### 5.3 多路径——不只是快，更是活

数据中心网络中交换机/机架之间**富互连**——任意两个 TOR 之间有多条路径可达。目的有两个：

- **增加吞吐**：多路径 = 更多总带宽。流量可以分散到多条路径上，不被一条 100G 链路卡住
- **冗余**：一条链路断了（光纤被踢松、交换机风扇停了），流量自动走另一条路径——上层应用完全无感知

**负载均衡器（Load Balancer）**是数据中心前端的"交通指挥"：
- 对外暴露一个公网 IP（用户访问 `www.google.com` 都打到这个 IP）
- 接收请求后，根据后端服务器负载、请求类型、用户位置，把请求路由到具体的服务器
- 对外部客户端**隐藏内部拓扑**——外部只看到一个 IP，内部可能有上万台服务器在同时处理请求

### 5.4 ORION——Google 的无路由协议网络

> ORION 是 Google 自研的 SDN 控制平面，用于内部数据中心（Jupiter 架构）和广域网（B4）。

最惊人的设计：**ORION 管理的网络中没有运行传统路由协议——没有 OSPF，没有 BGP。** 路由和流量工程以应用的形式实现在 ORION 核心之上，使用**发布-订阅分布式微服务架构**，OpenFlow 用于交换机信令和监控。

这意味着什么？传统意义上"路由器 = 硬件盒子 + 跑路由协议"的模型在 Google 的数据中心里根本不存在。网络行为完全由中央软件定义——控制器说"流 X 走路径 Y"，交换机就执行。课件用了一个耐人寻味的标题："**Are Protocols Dead?**（协议正在消亡？）"——在 SDN 的世界里，传统分布式路由协议确实在被集中式编程替代。

## 六、综合：一次 Web 请求的全栈旅程

> "Goal: identify, review, understand protocols (at all layers) involved in seemingly simple scenario: requesting www page"

这是整门课的收尾。一个看似简单的操作——打开浏览器输入 `www.google.com` 回车——背后涉及五层协议的全部知识。让我们一步一步走完。

**场景**：学生笔记本电脑刚插上网线，接入校园以太网。要做的第一件事：获得网络配置。

### Step 1 — DHCP：获取"身份证"

刚插上网线的电脑什么都没有——没有 IP 地址，不知道网关是谁，不知道 DNS 服务器在哪。DHCP（Dynamic Host Configuration Protocol）就是用来解决这个"第一天"问题的。

```
DHCP 发现报文:
  → UDP (src port 68, dest port 67)
    → IP (src=0.0.0.0, dest=255.255.255.255 — 广播！)
      → Ethernet (dest MAC=FF-FF-FF-FF-FF-FF — 广播帧！)
```

DHCP 服务器（通常跑在网关路由器上）收到后回复 **DHCP ACK**，包含：
- 分配给本机的 IP 地址（如 `192.168.1.10`）
- 首跳路由器（网关）IP 地址
- DNS 服务器 IP 地址
- 子网掩码、租约时间

**至此**：客户端有了 IP、知道了网关和 DNS。但要发 DNS 查询，需要先把帧发给路由器——路由器 MAC 地址是多少？

### Step 2 — ARP：翻译网关的 MAC

客户端在 ARP 表中没有路由器的 MAC 地址 → **ARP 查询广播**（dest MAC = `FF-FF-FF-FF-FF-FF`）："网关 IP 是 192.168.1.1，请告诉我你的 MAC"。

网关路由器收到 → 单播 ARP 响应 → 客户端将 `<网关IP, 网关MAC>` 存入 ARP 表。

**至此**：客户端可以封装发给网关的帧（dest MAC = 路由器 MAC），里面装着 DNS 查询。

### Step 3 — DNS：域名 → IP

```
DNS 查询报文:
  → UDP (dest port 53)
    → IP (dest = DNS 服务器 IP)
      → Ethernet (dest MAC = 路由器 MAC，经交换机转发到网关)
```

路由器收到帧 → 剥掉帧头 → 取出 IP 数据报 → 查转发表（由 OSPF/BGP 构建）→ "DNS 服务器在 ISP 方向" → 封装新帧 → 发送。

数据报经校园网 → Comcast 网络 → 多跳路由 → 到达 DNS 服务器。

DNS 服务器回复：`www.google.com → 64.233.169.105`。

**至此**：客户端知道了 Google 的 IP。但想和 Google 的 Web 服务器通信，需要先建立 TCP 连接。

### Step 4 — TCP：三次握手

客户端向 `64.233.169.105:80` 发起 TCP 连接：

```
① 客户端 → 服务器：TCP SYN (seq=x)
   封装在 IP 数据报中，dest IP=64.233.169.105
   帧的 dest MAC = 路由器 MAC（如 Step 2）

   数据报跨域路由（经 OSPF 域内 + BGP 域间）→ 到达 Google 服务器

② 服务器 → 客户端：TCP SYNACK (seq=y, ack=x+1)
   IP dest = 客户端 IP，反向路径由路由表决定

③ 客户端 → 服务器：TCP ACK (ack=y+1)
   TCP 连接建立 🎉
```

**至此**：客户端和 Google Web 服务器之间有一条可靠的双向字节流。现在可以发送 HTTP 请求了。

### Step 5 — HTTP：请求网页

```
HTTP GET / HTTP/1.1
Host: www.google.com

→ 写入 TCP socket
  → TCP segment (dest port 80)
    → IP datagram (dest=64.233.169.105)
      → Ethernet frame (dest MAC changes per hop!)
        → Physical layer (bits on the wire)
```

Google Web 服务器收到 HTTP 请求 → 处理 → 回复 HTTP Response（含 HTML 页面）。

客户端浏览器收到 HTTP 响应 → 解析 HTML → 渲染页面。**页面出来了。**

### 封装链路全貌

回顾整个过程，每一层都在忠实地执行自己的职责：

```
应用层：   HTTP GET / 
运输层：   TCP SYN → SYNACK → ACK → HTTP data over TCP
网络层：   IP datagram (src=客户端IP, dest=64.233.169.105) — 端到端不变
链路层：   Ethernet frame (dest MAC 每跳改变 — 逐跳转发)
物理层：   比特流经双绞线/光纤传输
```

五层协议栈的每一层，门课程的每一章——从第 1 章的分层架构、第 2 章的 DNS/HTTP、第 3 章的 TCP 可靠传输、第 4-5 章的 IP 路由与 BGP/SDN、第 6 章的以太网交换——全部在这场"一次 Web 请求"中同时登场。

## 难点突破

### 难点 1：交换机自学习为什么"即插即用"但需要 STP？

自学习的优雅在于：交换机不需要知道全网拓扑——它只维护一张从**源 MAC → 入接口**的本地映射。未知目的时**泛洪**，对端回复时沿路交换机自动学到新映射。这不需要任何配置或路由协议——插上就能工作。

**但泛洪有一个致命前提：拓扑必须无环。** 如果三台交换机连成环形，泛洪帧会永远在环里转——每台交换机收到帧、不知目的在哪、继续泛洪、下一台继续泛洪……**广播风暴（broadcast storm）**瞬间吞没所有带宽。

这就是 **STP（生成树协议，Spanning Tree Protocol）** 存在的意义：通过逻辑阻塞部分端口，使物理环状拓扑变成逻辑树状拓扑。STP 不在本课范围内，但理解"即插即用"的边界——自学习解决转发表的建立，STP 解决拓扑的安全——有助于理解交换机网络的完整图景。

### 难点 2：MPLS 标签转发与 IP 路由的本质区别是什么？

IP 路由是**同构**的——每跳路由器用同样的算法（OSPF/BGP），基于同样的信息（目的 IP），做出独立的转发决策。这是分布式的，容错性强，但每跳都做重复的 LPM 查找。

MPLS 是**异构**的——入口路由器做决策（基于源+目的+QoS 选路径、打标签），后续路由器只执行（按标签 O(1) 查表转发）。核心路由器被"简化"了——它不需要理解 IP 路由的完整语义，只需要"看到标签 X → 转发到端口 Y"。

**架构类比**：
- IP 路由 = 民主制：每个路由器平等参与决策，各自算各自的
- MPLS = 入口独裁 + 下游服从：入口决定整条路径，沿途只执行
- SDN = 中央集权：控制器替所有交换机做决定

三层递进：IP（分布式平等）→ MPLS（入口决策+下游执行）→ SDN（全集中决策）。这就是课件说"MPLS 是 SDN 精神先驱"的含义。

### 难点 3：VLAN 和子网的关系是什么？

初学者经常混淆：VLAN 是第 2 层的隔离，IP 子网是第 3 层的划分。两者是不同层的概念，但实践中**通常一一对应**——一个 VLAN = 一个 IP 子网。

- VLAN 隔离的是**广播域**：VLAN 10 的 ARP 广播到达不了 VLAN 20
- IP 子网隔离的是**路由域**：`192.168.1.0/24` 和 `192.168.2.0/24` 之间的流量需要路由器转发

实践中的最佳做法：**VLAN 10 → 子网 192.168.10.0/24，VLAN 20 → 子网 192.168.20.0/24**。不同 VLAN 之间的通信必须经过路由器（或三层交换机）——路由器不仅转发 IP 数据报，也天然地将广播隔离在两个 VLAN 之间。路由器的每个接口是一个独立的广播域。

### 难点 4：数据中心为什么不用传统路由协议？

传统路由协议（OSPF、BGP）是为**广域网**设计的——路由器数量可控（几百到上万）、拓扑相对稳定、收敛时间秒级可接受。

数据中心的条件完全不同：
- **规模**：数十万台服务器，每台等价于一个"节点"。如果用 OSPF，洪泛会淹没一切
- **变化频率**：虚拟机在机架间迁移（live migration），IP 地址随 VM 移动——传统路由的收敛速度跟不上
- **路径多样性**：任意两个 TOR 之间有多条等价路径——传统路由的"单下一跳"模型不够用
- **流量模式**：数据中心内部的东西向流量（server-to-server）远多于南北向（外部↔内部）

所以 Google 的 ORION 选择了一条完全不同的路：**放弃分布式路由协议，用集中式 SDN 控制**。控制器拥有全网拓扑和流量矩阵的全局视图，可以计算最优路径、执行流量工程、毫秒级响应故障——这些是传统分布式路由协议做不到的。

## 关键原句

> "Ethernet: 'dominant' wired LAN technology — first widely used LAN technology, simpler, cheap, kept up with speed race: 10 Mbps – 400 Gbps"
> **翻译：** 以太网是"统治性"的有线 LAN 技术——首个广泛使用的 LAN 技术，更简单、便宜，跟上了速度竞赛：从 10 Mbps 到 400 Gbps。

> "Switch is a link-layer device: takes an active role — store, forward Ethernet frames; examine incoming frame's MAC address, selectively forward frame to one-or-more outgoing links"
> **翻译：** 交换机是链路层设备：扮演主动角色——存储、转发以太网帧；检查入帧的 MAC 地址，选择性地将帧转发到一个或多个出口链路。

> "Port-based VLAN: switch ports grouped so that single physical switch operates as multiple virtual switches over single physical LAN infrastructure"
> **翻译：** 基于端口的 VLAN：交换机端口被分组，使单个物理交换机在单一物理 LAN 基础设施上表现为多个虚拟交换机。

> "MPLS: high-speed IP forwarding among network of MPLS-capable routers, using fixed length label (instead of shortest prefix matching) — borrowing ideas from Virtual Circuit approach, but IP datagram still keeps IP address!"
> **翻译：** MPLS：在 MPLS 路由器网络中，用固定长度标签（而非最长前缀匹配）实现高速 IP 转发——借用了虚电路方法的思想，但 IP 数据报仍然保留 IP 地址！

> "MPLS routing: path to destination can be based on source and destination address — flavor of generalized forwarding (MPLS 10 years earlier)"
> **翻译：** MPLS 路由：到达目的地的路径可基于源地址和目的地址——这是广义转发的一种形式（MPLS 比 SDN 早约十年）。

> "Our journey down the protocol stack is now complete! Goal: identify, review, understand protocols (at all layers) involved in seemingly simple scenario: requesting www page"
> **翻译：** 我们沿协议栈向下的旅程至此完整！目标：识别、回顾、理解一次看似简单的请求网页场景中涉及的所有层协议。

> "Ethernet frames carried within IP datagrams between sites — a tunneling scheme to overlay Layer 2 networks on top of Layer 3 networks" [RFC 7348]
> **翻译：** 以太网帧在站点之间的 IP 数据报中承载——一种在第 3 层网络之上覆盖第 2 层网络的隧道方案。

## 记忆卡片

**Q: 以太网帧由哪些字段组成？以太网的服务模型是什么？**
**A:** 帧结构：Preamble（8B，时钟同步）+ Dest MAC（6B）+ Src MAC（6B）+ Type（2B，指示上层协议）+ Data（46-1500B）+ CRC（4B）。最小 46 字节是因为 CSMA/CD 碰撞检测需要帧足够长。服务模型：**connectionless（无连接）**——不握手；**unreliable（不可靠）**——不 ACK，CRC 校验失败则丢弃，丢帧恢复仅由上层（TCP）负责。MAC 协议：unslotted CSMA/CD with binary backoff。所有 802.3 标准共享同一 MAC 协议和帧格式，只速率和物理介质不同。

**Q: 交换机如何自学习？收到未知目的 MAC 时怎么处理？**
**A:** 交换机收到帧时：(1) **学习**——记录源 MAC + 入接口 + TTL 到交换机表；(2) **查表转发**——目的 MAC 在表中 → 若出口≠入口则转发，出口=入口则丢弃；目的 MAC 不在表中 → **泛洪（flood）**——向除入接口外所有端口转发。对端回复时沿途交换机自动学到新映射。多交换机级联时自学习正常工作——经过几轮泛洪+学习，全网 MAC 位置自动收敛。但拓扑不能有环路（需要 STP）。

**Q: 为什么需要 VLAN？802.1Q 做了什么？**
**A:** 单一广播域 LAN 面临三个问题：(1) **扩展性**——广播流量（ARP、DHCP、泛洪）淹没全网；(2) **安全/隐私**——CS 系的 ARP 不应到达 EE 系；(3) **管理**——换办公室但逻辑归属不变。Port-based VLAN 将端口分组，一个物理交换机 = 多个虚拟交换机，实现流量隔离。802.1Q 在帧中插入 4 字节标签（Tag Protocol ID + 12 位 VLAN ID + 优先级），使 trunk 端口能区分不同 VLAN 的帧。VXLAN/EVPN 进一步通过 UDP/IP 隧道实现跨数据中心 L2 扩展（L2 over L3）。

**Q: MPLS 和 IP 路由的本质区别是什么？为什么说 MPLS 是 SDN 的精神先驱？**
**A:** IP 路由是**同构**的——每跳独立基于目的地址做 LPM，路径仅由目的决定。MPLS 是**异构**的——入口路由器基于源+目的+QoS 选路并打标签，下游仅按标签 O(1) 查表转发。MPLS 将"决策"集中到边缘、核心只执行——**决策与执行分离**正是 SDN 的核心哲学。三种超越 IP 的能力：流量工程（同目的不同源走不同路径）、快速重路由（毫秒级故障切换）、广义转发（入口决定整条路径）。MPLS 比 SDN 早了约十年。

**Q: 一次 Web 请求（www.google.com）经历了哪些协议步骤？**
**A:** (1) **DHCP**：获取本机 IP、网关 IP、DNS 服务器 IP（DHCP→UDP→IP→Eth，广播帧）；(2) **ARP**：解析首跳路由器 MAC 地址（ARP 广播→单播响应）；(3) **DNS**：解析 `www.google.com` → `64.233.169.105`（DNS→UDP→IP→Eth，经 OSPF/BGP 路由到 DNS 服务器）；(4) **TCP**：三次握手 SYN→SYNACK→ACK 建立到 Web 服务器的连接；(5) **HTTP**：GET 请求→HTTP 响应→浏览器渲染。全程展示五层封装：HTTP → TCP segment → IP datagram → Ethernet frame → Physical bits。每层各司其职，层层封装。

**Q: 交换机（Switch）和路由器（Router）有什么区别？**
**A:** 交换机工作在链路层（L2），检查 MAC 地址，转发表通过**自学习**（flood + learn）建立，即插即用；路由器工作在网结层（L3），检查 IP 地址，转发表通过**路由协议**（OSPF/BGP）建立。交换机默认所有端口同一广播域（需 VLAN 隔离），路由器每个接口独立广播域。交换机让每链路独占碰撞域+全双工，现代交换网络中碰撞几乎不存在。

### 简答题预测 + 标准答案

**Q1: 画出以太网帧结构，标注每个字段的名称、大小和作用。以太网的服务模型是什么？**（8-10 分）

**标准答案**：

```
┌──────────┬──────────┬──────────┬──────┬──────────────┬──────┐
│ Preamble │ Dest MAC │ Src MAC  │ Type │    Data      │ CRC  │
│  8 bytes │  6 bytes │  6 bytes │ 2 B  │ 46-1500 bytes│ 4 B  │
└──────────┴──────────┴──────────┴──────┴──────────────┴──────┘
```

| 字段 | 大小 | 作用 |
|------|------|------|
| Preamble | 8 B | 时钟同步（7B `10101010` + 1B SFD） |
| Dest MAC | 6 B | 目的 MAC 地址 |
| Src MAC | 6 B | 源 MAC 地址（交换机自学习的关键） |
| Type | 2 B | 上层协议类型（`0x0800`=IPv4），用于多路分解 |
| Data | 46-1500 B | 封装的网络层数据报（最小 46B 为 CSMA/CD 碰撞检测所需） |
| CRC | 4 B | CRC-32 差错检测，校验失败丢弃 |

服务模型：**connectionless（无连接，不握手）+ unreliable（不可靠，不 ACK）**。丢帧恢复仅由上层（TCP）负责。MAC 协议为 unslotted CSMA/CD with binary backoff。

---

**Q2: 解释交换机的自学习机制。收到未知目的 MAC 的帧时怎么处理？**（8-10 分）

**标准答案**：

交换机收到帧时执行两步：

**Step 1 — 学习（Learning）**：记录帧的**源 MAC 地址**、**入接口**和**时间戳**到交换机表（`<MAC, interface, TTL>`）。如帧从端口 3 来、源 MAC=A，则记录 A→port 3。

**Step 2 — 转发（Forwarding）**：以目的 MAC 查交换机表：
- 找到条目且出口≠入口 → 从表项指示的端口转发
- 找到条目且出口=入口 → **丢弃**（源和目的在同一段，目的主机已直接收到）
- 未找到条目 → **泛洪（flood）**——向除入接口外的所有端口转发

对端回复时，沿途交换机学到新映射。整个过程无需配置，即插即用。交换机表有 TTL 老化机制。拓扑不能有环路（需 STP）。

---

**Q3: 对比交换机（Switch）和路由器（Router）。**（6-8 分）

**标准答案**：

| | 交换机 | 路由器 |
|---|---|---|
| **工作层** | 链路层（L2） | 网络层（L3） |
| **检查头部** | 以太网帧头（MAC 地址） | IP 数据报头（IP 地址） |
| **转发表建立** | 自学习（flood + learn），即插即用 | 路由算法（OSPF/BGP） |
| **转发依据** | MAC 地址（48 位扁平） | IP 前缀（32 位分层） |
| **广播域** | 所有端口同一广播域（默认） | 每个接口独立广播域 |

---

**Q4: 简述 VLAN 的动机和 802.1Q 的工作原理。**（6-8 分）

**标准答案**：

**动机**：单一广播域 LAN 面临 (1) 扩展性问题——广播流量（ARP、DHCP、泛洪）淹没全网；(2) 安全/隐私——跨部门广播泄漏；(3) 管理问题——换物理位置但需保留逻辑归属。

**Port-based VLAN**：将交换机端口分组，一个物理交换机表现为多个虚拟交换机。VLAN 间流量隔离，跨 VLAN 通信需路由。

**802.1Q**：在以太网帧中插入 4 字节标签（2B Tag Protocol ID `0x8100` + 2B Tag Control Info），含 12 位 VLAN ID（最多 4094 个 VLAN）和 3 位优先级。Trunk 端口用 802.1Q 标签区分不同 VLAN 的帧，实现跨交换机 VLAN。CRC 因帧内容改变需重算。

---

**Q5: 描述一次 Web 请求（输入 www.google.com 到页面显示）涉及的所有协议步骤。**（10-12 分）

**标准答案**：

**Step 1 — DHCP**：客户端无 IP → DHCP 发现报文（UDP→IP 广播→Eth 广播帧 `FF-FF-FF-FF-FF-FF`）→ DHCP 服务器回复 DHCP ACK，包含本机 IP、网关 IP、DNS 服务器 IP。

**Step 2 — ARP**：客户端需要网关的 MAC 地址 → ARP 查询广播 → 网关单播 ARP 响应，告知 MAC。

**Step 3 — DNS**：DNS 查询报文（UDP port 53→IP→Eth→经交换机到网关→经 OSPF/BGP 路由到 DNS 服务器）→ DNS 服务器回复 `www.google.com → 64.233.169.105`。

**Step 4 — TCP**：三次握手。SYN→经域间路由到 Google 服务器→SYNACK→客户端 ACK。TCP 连接建立。

**Step 5 — HTTP**：HTTP GET 请求→TCP socket→IP datagram（端到端不变）→Ethernet frame（dest MAC 逐跳变）→物理层。服务器回复 HTTP Response（含 HTML）。浏览器渲染页面。

**封装链**：HTTP → TCP segment → IP datagram → Ethernet frame → Physical bits。

---

**Q6: 对比 MPLS 标签转发与 IP 路由，为什么说 MPLS 是 SDN 的精神先驱？**（8-10 分）

**标准答案**：

IP 路由是**同构**的——每跳路由器用同样的协议（OSPF/BGP），基于同样的信息（目的 IP），独立做 LPM 查找。路径仅由目的地址决定。

MPLS 是**异构**的——入口路由器基于源+目的+QoS 做决策并打标签，后续路由器仅按固定长度标签 O(1) 查表转发。**决策与执行分离**——入口决策、下游执行，这正是 SDN 的核心哲学。

三种超越传统 IP 路由的能力：
1. **流量工程（Traffic Engineering）**：同一目的地的不同源地址可打不同标签走不同路径。IP 路由做不到——IP 只看目的地址
2. **快速重路由（Fast Reroute）**：预计算备份路径，链路故障时毫秒级切换到备路，远快于 OSPF/BGP 收敛
3. **广义转发（Generalized Forwarding）**：入口决定整条路径，不限于目的地址——比 SDN 早了约十年

**架构类比**：IP 路由 = 民主制（每路由器平等决策）→ MPLS = 入口独裁+下游服从（决策与执行分离）→ SDN = 中央集权（控制器替所有交换机决策）。三层递进，逻辑一致。

---

**Q7: 数据中心网络和传统企业网络有什么不同？ORION 为什么放弃传统路由协议？**（6-8 分）

**标准答案**：

**数据中心网络的特殊条件**：
- **规模**：数十万台服务器，传统 OSPF 洪泛会淹没一切
- **变化频率**：虚拟机在机架间实时迁移，IP 地址随 VM 移动——传统路由协议收敛秒级，跟不上毫秒级变化
- **路径多样性**：任意两个 TOR 之间有大量等价路径——传统路由的"单下一跳"模型不够用
- **流量模式**：东西向流量（server-to-server）远多于南北向（外部↔内部），与互联网流量特征相反

**ORION（Google 的 SDN 控制平面）**：
- 用于内部数据中心（Jupiter 架构）+ 广域网（B4）
- **无传统路由协议**——无 OSPF、无 BGP。路由和流量工程以应用形式实现在 ORION 核心之上
- 使用发布-订阅分布式微服务架构 + OpenFlow 信令
- 控制器拥有全网拓扑和流量矩阵的全局视图——集中计算最优路径、执行流量工程、毫秒级故障响应

**本质**：数据中心的条件（规模、速度、路径多样性、集中管理）与传统广域网完全不同——分布式路由协议的优势（自主容错、去中心化）反而成了劣势（收敛慢、无全局视图）。SDN 集中式编程是数据中心的自然选择。

### 易错点

- **交换机表 ≠ 路由表**：交换机表是自学习来的（`<MAC, port, TTL>`），路由表是路由协议算来的（`<prefix, next-hop, interface>`）。两表在同一台三层交换机中共存但独立维护
- **泛洪 ≠ 广播**：泛洪是交换机行为（未知目的 MAC → 向所有其他端口发），广播是帧类型（dest MAC = `FF-FF-FF-FF-FF-FF`）。两者不等价但经常同时出现
- **VLAN 隔离的是广播域，不是碰撞域**：交换机的每个端口已经是独立碰撞域（全双工）。VLAN 是更进一步——隔离广播域。两层隔离，不同层次
- **MPLS 标签不是 MAC 地址替代**：MPLS 标签在以太网头和 IP 头之间（"2.5 层"），不替代 MAC。帧的 MAC dest 仍然是下一跳的 MAC
- **802.1Q 标签插入后 CRC 必须重算**：很多学生忘记——帧内容变了，FCS 必须重新计算，否则对端 CRC 校验失败
- **"一次 Web 请求"中 IP 地址端到端不变 vs MAC 地址逐跳改变**：这是贯穿全课的核心考点。DNS 解析返回的是**目的 IP**，ARP 解析的是**下一跳 MAC**——两者从不混淆
- **交换机是 L2 设备 ≠ 不涉及 IP**：交换机转发帧时不看 IP 头部，但三层交换机可以同时做路由（VLAN 间转发时看 IP）
