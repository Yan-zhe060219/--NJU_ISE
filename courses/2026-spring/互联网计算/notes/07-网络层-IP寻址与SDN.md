## 一句话总结

IP 地址的演化史是一条主线——分类编址浪费严重 → 子网划分缓解内部管理 → CIDR 彻底抛弃固定边界并实现路由聚合 → DHCP 让地址分配即插即用 → NAT 用端口复用临时续命 → IPv6 用 128 位地址根本解决枯竭。与此同时，数据平面从"只能按目的 IP 转发"演进到 SDN 的 match+action 广义转发——OpenFlow 用一套流表抽象统一了路由器、交换机、防火墙和 NAT 的所有转发行为。

## 场景设定：网络层的三个追问

第 06 章我们站在路由器内部，看到一个数据报如何被最长前缀匹配（LPM）转发。但那章留下了一个关键问题没有回答：**路由表里的那些前缀从哪来的？谁分配的 IP 地址？为什么地址长成 `223.1.2.9` 这个样子？**

这一章就是回答这三个追问。而且你会发现一个贯穿始终的张力：**IP 地址永远不够用**。从分类编址到 CIDR 到 NAT 到 IPv6，整个 IP 寻址的演化史就是人类与"地址枯竭"搏斗的历史。最终 SDN 和 Middlebox 又告诉我们：今天的互联网早已不是教科书上那个干净的沙漏模型了。

先记住一个事实，后面所有内容都基于它：

> **每个网络接口都需要一个独立的 IP 地址**（A separate address is required for each physical interface of a host/router to a network — facilitates routing）。

路由器的每个网口有一个 IP，主机的每个网卡有一个 IP。IP 地址标识的是**接口**，不是设备。

## 1. Classful Addressing — 第一代方案及其失败

### 1.1 为什么要分类？

IP 地址是 32 位的全局标识符。问题来了：这 32 位里，多少位表示"网络号"（netid），多少位表示"主机号"（hostid）？

第一代方案很简单：**按高位的固定模式来分**。这就是分类编址（Classful Addressing）。

```
Class A: 0xxxxxxx . host . host . host     → 首 bit 为 0
Class B: 10xxxxxx . net  . host . host     → 首两 bit 为 10
Class C: 110xxxxx . net  . net  . host     → 首三 bit 为 110
Class D: 1110xxxx . 组播地址               → 首四 bit 为 1110
Class E: 1111xxxx . 保留（实验用）         → 首四 bit 为 1111
```

看到关键设计了吗？**读第一个字节的前几 bit 就能判断是哪类地址**——不需要额外元数据，路由器看一眼就知道网络号和主机号的边界在哪。

### 1.2 五类地址的具体数据

| Class | 首 bit(s) | 范围 | 网络数 | 每网主机数 | 用途 |
|-------|-----------|------|--------|-----------|------|
| A | `0` | 1.x.x.x ~ 126.x.x.x | 2⁷−2 = 126 | 2²⁴−2 ≈ 1600万 | 单播：巨型组织 |
| B | `10` | 128.0.x.x ~ 191.255.x.x | 2¹⁴ = 16384 | 2¹⁶−2 ≈ 6.5万 | 单播：大中型组织 |
| C | `110` | 192.0.0.x ~ 223.255.255.x | 2²¹ ≈ 200万 | 2⁸−2 = 254 | 单播：小型组织 |
| D | `1110` | 224.x.x.x ~ 239.x.x.x | — | — | 组播（Multicast） |
| E | `1111` | 240.x.x.x ~ 255.x.x.x | — | — | 保留（实验，未部署） |

A/B/C 是**单播（Unicast）**——地址 = 网络号 + 主机号，先定位网络，再定位接口。所以有"网络数"和"每网主机数"。

D 类和 E 类则完全不同：

**Class D（组播）—— 标识一组主机，而非一个接口。** 组播地址不指向某个具体网络或接口，而是指向一个**组播组**（multicast group）。比如 10 台分布在全球不同网络的主机同时"加入"了组 `224.0.1.1`，往这个地址发一个数据报，网络层会复制递送给所有组成员。剩下的 28 位全部是"组标识符"，没有网络号/主机号的层次划分，所以自然没有"多少个网络、每网多少主机"的概念——最多有 2²⁸ 个不同的组播组。

**Class E（保留）—— 从未实际部署。** IANA 锁在柜子里的实验地址块，从未进入公网运营。既然没分配过，就谈不上统计网络数和主机数。

> 通俗记法：**A/B/C 找人（单播），D 喊一群人（组播），E 锁在柜子里没用过。**

几个细节：
- `127.0.0.0/8`（Class A 中 127 开头）保留给**回环测试（loopback）**——`127.0.0.1` 就是"我自己"，数据不会真的发到网络上，用于测试本机 TCP/IP 协议栈是否正常。
- 全 0 的主机号表示"这个网络本身"（网络地址），全 1 的主机号表示广播地址。所以每网实际可用主机数要减 2。
- Class A 和 B 早已全部分配完毕，C 类也几近枯竭。

### 1.4 公网地址 vs 私有地址：不是所有设备都要公网 IP

分类编址管的是**公网可达**的接口——理论上互联网上每一台设备都需要一个 A/B/C 类公网地址。但一台设备真的需要"全球可达"吗？你家里手机和笔记本电脑，需要被地球另一边的人直接 ping 通吗？

不需要。所以 RFC 1918 从 A/B/C 三类中各划了一段作为**私有地址（Private Address）**，任何人可以免费使用，但**不出公网**——路由器不会转发源或目标为私有地址的数据报到公网：

| 私有地址段 | CIDR 记法 | 相当于 | 典型场景 |
|-----------|-----------|--------|---------|
| `10.0.0.0 ~ 10.255.255.255` | `10.0.0.0/8` | 1 个 A 类 | 大型企业内网 |
| `172.16.0.0 ~ 172.31.255.255` | `172.16.0.0/12` | 16 个 B 类 | 中型组织内网 |
| `192.168.0.0 ~ 192.168.255.255` | `192.168.0.0/16` | 256 个 C 类 | 家庭/小型办公室 |

你家里 WiFi 路由器给手机分的 `192.168.1.x` 就是私有地址——它在公网上不可路由，必须经过后面第 5 节讲的 NAT 转换成公网 IP 才能访问外网。私有地址的存在大大缓解了公网地址的压力：一个公司几千台设备用私有地址，只需几个公网 IP 通过 NAT 共享出口。

> 关键区分：**分类编址（A/B/C/D/E）管的是公网侧的结构，私有地址是"内部自用、出门翻译"的补充机制。** 今天 CIDR 早已取代了分类编址的概念——IANA 分配的是 `/8`、`/12` 等 CIDR 前缀块，不再说"给你一个 Class B"。但历史遗留的 Class A 块（如 MIT 的 `18.0.0.0/8`）仍在路由表中，路由器只会把它当成一条 CIDR 前缀处理，不会因为首 bit 是 0 就特殊对待。

### 1.3 致命缺陷：固定边界的巨大浪费

假设你是一个有 1000 台主机的中型企业。Class C 只有 254 个地址，不够。你只能申请 Class B——然后你就占了一个 6.5 万地址的块，其中 6.4 万个永远用不到。这就是 **IP 地址空间的快速枯竭**的根本原因：不是地址总数不够（2³² ≈ 43 亿），而是**分配粒度太粗**导致大片地址被浪费。

**这是整个 IP 寻址演化的第一推动力**——后面的子网划分、CIDR、NAT、IPv6，全部可以追溯到这个问题。

## 2. Subnetting — 组织内部的灵活切分

### 2.1 子网划分解决什么问题？

分类编址解决的是"全球如何分配地址"，但组织拿到一个网络号之后呢？比如你拿到了一个 Class B 网络 `128.10.0.0`，内部有多个局域网（LAN），你怎么把地址空间分给各个 LAN？

**子网划分（Subnetting）** 的思路：从主机号中"借"几个高位 bit 作为子网号（subnet number）。

```
原来（Class B）：  |← 16-bit 网络号 →|←  16-bit 主机号  →|
子网划分后：       |← 16-bit 网络号 →|← subnet →|← host →|
                                   ↑ 子网掩码决定这里的分界线
```

**子网掩码（Subnet Mask）** 指示哪些 bit 是子网号、哪些是主机号。例如 `255.255.255.0` 表示前 24 位是网络+子网，后 8 位是主机。

### 2.2 子网划分的妙处

- **对外透明**：不管内部划了多少子网，对外部互联网来说，整个组织看起来**仍然是一个网络**——路由表不需要为每个子网单独记录条目。这隔离了互联网路由表的增长。
- **内部灵活**：每个 LAN 分配一个子网号，本地路由器在子网之间路由。你可以按部门（财务部 `/24`、研发部 `/24`）或按楼层划分子网。

子网划分是 CIDR 的前奏——它证明了一个道理：**地址分配的粒度应该是任意的，不应该被 A/B/C 类的固定边界束缚**。

## 3. CIDR — 彻底解放地址分配

### 3.1 核心思想：抛弃"类"的概念

CIDR（Classless Inter-Domain Routing，无类域间路由）做了一件激进但正确的事：**完全消灭 A/B/C 类的概念**。IP 地址不再有"类"属性，统一写成 `a.b.c.d/n`，其中 `n` 是网络前缀长度（network prefix）。

```
例：10.217.123.7，子网掩码 255.255.240.0

IP:   00001010 . 11011001 . 01111011 . 00000111
掩码: 11111111 . 11111111 . 11110000 . 00000000
      ←—————— 前 20 位是网络前缀 ——————→←— 主机 →

→ CIDR 记法：10.217.112.0/20
```

`/20` 的意思是前 20 位是网络前缀，后 12 位是主机号。ISP 可以给大客户分 `/16`、给小客户分 `/28`——**按需分配，精确到 bit**。

### 3.2 路由聚合：CIDR 的杀手级优势

这正是第六章"最长前缀匹配"存在的原因。CIDR 让**层次化编址（Hierarchical Addressing）** 成为可能：

```
ISP 获得大块：200.23.16.0/20
  ├── 组织 A：200.23.16.0/23
  ├── 组织 B：200.23.18.0/23
  ├── 组织 C：200.23.20.0/24
  └── 组织 D：200.23.21.0/24
```

对外部世界，ISP 只需要通告一条 `200.23.16.0/20`。所有发往这四个组织的数据报先到 ISP，ISP 内部再用更长的前缀（`/23`、`/24`）精确匹配到具体组织。

**这就是路由聚合（Route Aggregation）**：多个连续前缀可以聚合成一个更短的前缀向外通告。全球路由表从几十万条缩小到几十万条（仍然很大，但比没有 CIDR 时好太多）。

### 3.3 回顾第六章：为什么需要最长前缀匹配？

现在你明白了：**如果一台路由器同时知道 `200.23.16.0/20`（聚合路由）和 `200.23.18.0/23`（更具体的路由），它必须选择 `/23`——因为更长的前缀意味着更精确的目标**。这就是第六章路由器转发时执行 LPM（Longest Prefix Matching）的根本原因。CIDR 是"因"，LPM 是"果"。

> 关键直觉：**CIDR 把地址分配变成了层次化的树**。ISP 是树干，下级组织是树枝，具体子网是树叶。路由聚合让外部世界只需看到树干。最长前缀匹配让内部精确到树叶。二者配合，地址分配和路由转发完美衔接。

## 4. DHCP — 主机如何获得 IP 地址？

### 4.1 两个不同的问题

"如何获得 IP 地址"实际上是两个问题：

| 问题 | 答案 |
|------|------|
| 主机如何获得其所在网络内的 IP（host part）？ | 手工配置 或 **DHCP** |
| 网络如何获得自己的 IP 前缀（network part）？ | ISP 从其分配的大块中划出一个子块 |

主机地址的获取有三种方式：系统管理员手动写入配置文件（如 UNIX `/etc/rc.config`）、或者使用 DHCP 自动获取。显然，在移动设备和临时接入场景下，手动配置完全不现实——你不可能让每个连咖啡店 WiFi 的人手动配 IP。

### 4.2 DHCP 四步交互

DHCP（Dynamic Host Configuration Protocol）让主机在加入网络时**动态获取 IP 地址**，实现即插即用（plug-and-play）。

```
客户端                                     DHCP 服务器
  │                                           │
  │  (1) DHCP Discover ──────────────────────→│  广播："谁有 IP？"
  │      src: 0.0.0.0, dst: 255.255.255.255   │  （客户端还没有 IP）
  │                                           │
  │  (2) DHCP Offer ←──────────────────────│  服务器响应："这个 IP 可用"
  │                                            │
  │  (3) DHCP Request ──────────────────────→│  客户端确认："我要这个"
  │                                           │
  │  (4) DHCP ACK ←────────────────────────│  服务器分配："给你"
  │                                           │
  │  现在客户端有了：                          │
  │  · 自己的 IP 地址                          │
  │  · 默认网关（first-hop router）地址        │
  │  · DNS 服务器名称 & IP                     │
  │  · 子网掩码                                │
```

四个关键设计：

- **全部走 UDP 广播**（因为客户端一开始连 IP 都没有，无法建 TCP 连接）
- **租约机制（lease）**：IP 地址不是永久给的，有期限。到期可以续约；断开连接/关机后地址释放，供其他主机复用——这对移动用户极其重要
- **DHCP 服务器通常内置于路由器中**，为路由器连接的所有子网提供服务
- **封装链**是分层模型的经典实例：`DHCP → UDP → IP → Ethernet`，Ethernet 帧以广播地址 `FF:FF:FF:FF:FF:FF` 发出，经路由器逐层解封装到 DHCP

## 5. NAT — 打补丁续命，但代价是什么？

### 5.1 NAT 到底是什么？

CIDR 大幅度缓解了地址浪费，但 IPv4 总共也就 43 亿地址——地球人口 80 亿，每人不止一个设备。**地址空间即将物理上不够用**。在 IPv6 全面部署之前，需要一个过渡方案。

NAT（Network Address Translation，网络地址转换）的核心思想：**内网（Intranet）用私有地址，外网（Internet）用公有地址，在交界处做地址转换**。

这样做有三个好处：
- **防火墙效果**：外网看不到内网主机的真实地址，隐藏了内部拓扑
- **地址扩展**：整个组织的内网主机共享少量公网 IP
- **隔离内部变更**：组织内部重新编址不影响外部路由

### 5.2 三种 NAT 类型

| 类型 | 映射方式 | 适用场景 |
|------|----------|----------|
| **Static NAT** | 一个私有 IP ↔ 一个公有 IP（固定映射） | 内网服务器对外提供服务 |
| **Dynamic NAT** | 从公有 IP 池中按需分配，用完归还 | 内网客户端上网 |
| **NAPT**（端口地址转换） | 多个私有 IP:Port ↔ 一个公有 IP:不同 Port | 家庭/企业共享上网（**最常用**） |

NAPT 又叫 Overloading / Masquerading / Single-Address NAT——最常用的形式。它的转换表长这样：

```
协议  | 内网地址:端口      | 外网地址:端口        | 外部目标:端口
TCP  | 10.1.1.3:1723     | 192.168.2.2:1492    | 176.21.17.9:23
TCP  | 10.1.1.2:1723     | 192.168.2.2:1723    | 176.21.17.9:23
TCP  | 10.1.1.1:1024     | 192.168.2.2:1024    | 172.20.7.3:23
```

注意这两行：**两台不同的内网主机（10.1.1.3 和 10.1.1.2）用同一个源端口 1723 访问同一台外网服务器**。NAT 路由器把 10.1.1.3 映射到公网端口 1492，把 10.1.1.2 映射到公网端口 1723——外网服务器根本不知道这两个连接来自不同主机，它只看到同一个公网 IP + 不同的源端口。

### 5.3 NAPT 工作过程详解

```
内网主机 10.0.0.1                           外部服务器 128.119.40.186
      │                                              │
      │  (1) 发包：src=10.0.0.1:3345                  │
      │          dst=128.119.40.186:80                 │
      │                                              │
      ├──────────→ NAT 路由器 ──────────→              │
      │           查表，改写：                           │
      │           src=138.76.29.7:5001                  │
      │           dst=128.119.40.186:80                 │
      │           (2) ──────────────────→               │
      │                                              │
      │                           (3) 响应：            │
      │           ←────────────────── src=128.119.40.186:80
      │           收到，查表：        dst=138.76.29.7:5001
      │           目标端口 5001 → 查表 → 10.0.0.1:3345  │
      │           (4) dst=10.0.0.1:3345                 │
      │           ←──────────                           │
```

**端口号就是区分内网主机的钥匙**。这里 NAT 直接依赖第三章运输层的端口复用/分解（Mux/Demux）机制——没有端口号，NAPT 就无法工作。

### 5.4 NAT 的争议：端到端原则被打破了

Internet 最初的设计哲学是**端到端原则**（end-to-end principle）：网络层只管尽力而为转发，智能放在终端。NAT 在数据路径上插入了**有状态的处理**：

- **P2P 应用的噩梦**：两个都在 NAT 后面的主机无法直接通信（因为没有公网可达地址）。Skype 的解决方案是**中继（Relay）**——NATed 超节点主动连到中继服务器，外部客户端也连到中继，中继在两条连接之间桥接数据。
- **地址随时间变化**：租约到期、重连可能导致公网映射变化，应用层必须处理这种情况。

**一句话**：NAT 是用"破坏架构纯净性"换取"地址空间续命"的务实选择。

## 6. IPv6 — 根本解决方案

### 6.1 为什么需要 IPv6？

IPv4 32 位地址空间即将物理上枯竭——不是浪费问题，是 bit 数本身不够。同时，IPv4 路由器每跳重算校验和（checksum）拖慢了转发速度，QoS 支持也不够好。

IPv6 的设计目标：
1. **解决地址枯竭**——128 位地址空间
2. **加速转发处理**——简化固定头部，去掉校验和和分片
3. **更好地支持 QoS**——流标签 + 流量类别
4. **新能力**——任播（Anycast）、地址自动配置、内置 IPsec

### 6.2 IPv6 头部结构

```
 0               8               16              24              32
┌───────────────┴───────────────┴───────────────┴───────────────┐
│ Version (4) │ Traffic Class (8) │     Flow Label (20)          │
├───────────────────────────────┴───────────────────────────────┤
│        Payload Length (16)     │   Next Header (8)  │ Hop(8) │
├───────────────────────────────────────────────────────────────┤
│                                                                 │
│                    Source Address (128 bits)                     │
│                                                                 │
├───────────────────────────────────────────────────────────────┤
│                                                                 │
│                  Destination Address (128 bits)                  │
│                                                                 │
└───────────────────────────────────────────────────────────────┘
                      固定 40 字节
```

逐个字段：

| 字段 | 大小 | 作用 |
|------|------|------|
| **Version** | 4 bit | 固定为 6 |
| **Traffic Class** | 8 bit | 区分不同优先级/类别（类似 IPv4 ToS 但更灵活）。可用于 DiffServ 编码点。上層协议可设值，但不应假设值在传输中不变（源、转发者、接收者都可修改） |
| **Flow Label** | 20 bit | 标识属于同一"流"的数据报（见下文） |
| **Payload Length** | 16 bit | 载荷长度（含扩展头部 + 上层数据） |
| **Next Header** | 8 bit | 标识紧接 IPv6 头部之后的下一个头部类型（扩展头或上层协议，如 TCP/UDP） |
| **Hop Limit** | 8 bit | 同 IPv4 TTL，每跳减 1，到 0 丢弃 |
| **Src/Dst Addr** | 128 bit × 2 | 源和目标地址 |

### 6.3 相比 IPv4，去掉了什么？为什么？

| IPv4 有 | IPv6 去掉了 | 原因 |
|----------|-------------|------|
| Header Checksum | ✅ 去掉 | 每跳重算校验和是路由器的 CPU 瓶颈之一。IPv6 依赖上层协议（TCP/UDP）和链路层做差错检测 |
| Fragmentation 相关字段 | ✅ 去掉 | IPv6 不允许中间路由器分片——分片只在源端做。路由器不再需要处理分片逻辑，大幅简化 |
| Options（可变长） | 改为扩展头部 | IPv4 的可变长选项让头部长度不固定，硬件处理困难。IPv6 把选项独立为扩展头部，夹在固定头部和上层协议头部之间，大多数中间路由器不检查 |

### 6.4 Flow Label — IPv6 最精巧的设计

**流（Flow）** 是从特定源到特定目的地的一系列分组，它们共享相同的转发处理需求（如路由路径、资源分配、丢弃策略、计费和安全策略）。

- 一个流可以包含单个 TCP 连接，也可以包含多个 TCP 连接
- 一个应用可以产生一个流或多个流
- 流的需求在流开始前定义好，然后分配一个唯一的非零 Flow Label

**关键优势**：路由器收到分组后，**只需查 Flow Label 表就能决定如何处理，而不需要深入解析 IP 头部、TCP/UDP 端口等更深层字段**。这极大加速了转发——本质上是对"流"做了一次性分类，后续直接走快车道。

对应地，**Traffic Class** 用于标记分组的优先级——比如实时视频可以用高优先级（类似 DiffServ 中的 EF），普通文件下载用低优先级。

### 6.5 IPv6 相比 IPv4 的完整优势

1. **扩展的寻址能力**：128 位地址 → 可扩展的组播 → **任播（Anycast）**——发往一组节点中的"最近"一个 → 地址自动配置（无需 DHCP 也能自己生成地址）
2. **改进的选项机制**：扩展头部独立于固定头部，大多数不被中间路由器检查，易于扩展新选项
3. **资源分配支持**：Traffic Class + Flow Label 允许 QoS 处理超越尽力而为（如实时视频）
4. **更高效健壮的移动性机制**
5. **内置安全**：IP 层强加密和认证（IPsec 集成）

### 6.6 过渡策略：渐进而非革命

不可能一夜之间把全球所有路由器从 IPv4 升级到 IPv6。需要过渡期，期间 IPv4 和 IPv6 共存。

**方案一：Dual Stack（双栈）**

```
A ──IPv6──→ B ═══IPv4═══→ C ═══IPv4═══→ D ═══IPv4═══→ E ──IPv6──→ F
   IPv6      IPv6/v4      IPv4        IPv4        IPv4/v6      IPv6

A→B: IPv6 分组（完整）
B→C: 转换为 IPv4（需要地址转换，部分 IPv6 特性丢失）
C→D: IPv4 分组
D→E: IPv4 分组
E→F: 转换为 IPv6
```

优势是兼容性好，缺点是**地址转换会丢失 IPv6 特有信息**（如 Flow Label、扩展头部），而且转换本身就增加处理开销。

**方案二：Tunneling（隧道）**

```
逻辑视图：  A ────── IPv6 ────────────────────────────────→ F

物理视图：  A ──IPv6──→ B ═══IPv4隧道═══→ E ──IPv6──→ F
           IPv6       IPv6/v4              IPv6/v4     IPv6

A→B: 纯 IPv6 分组
B→E: 整个 IPv6 分组作为载荷封装在 IPv4 数据报中
     源=B的IPv4地址，目标=E的IPv4地址
     有效载荷减少了（IPv4 头部占空间），但 IPv6 特性完整保留
E→F: 解封装，恢复原始 IPv6 分组
```

隧道的问题是**额外头部减少了有效数据载荷**，但保真度更好——IPv6 分组完整穿越了 IPv4 区域，不丢失任何信息。

## 7. Generalized Forwarding & SDN — 从固定到可编程

### 7.1 回顾：传统转发的局限

第 06 章我们花了很多篇幅讲传统路由器的转发：**只根据目的 IP 地址做最长前缀匹配，然后转发**。这是"基于目的的转发"（destination-based forwarding）。功能焊死在硬件里——路由器就是路由器，防火墙就是防火墙，交换机就是交换机。

但如果我想做"来自 10.3.*.* 且目标是 10.2.*.* 的流量走端口 3"怎么办？传统 IP 转发做不到——它只看目的地址，不看源地址。

### 7.2 广义转发：match+action 抽象

**广义转发（Generalized Forwarding）** 的核心理念：把"怎么处理一个分组"分解为两个通用步骤——**匹配（match）** 和 **动作（action）**。

一个流表条目（flow table entry）包含四个要素：

| 要素 | 含义 |
|------|------|
| **Match** | 匹配分组头部中的哪些字段值（可以是 L2/L3/L4 任意字段的组合） |
| **Action** | 匹配后执行什么操作：转发到端口、丢弃、修改头部、封装后发给控制器…… |
| **Priority** | 多条规则匹配时，用优先级消除歧义（类似 LPM 中选最长前缀） |
| **Counters** | 统计有多少字节/分组匹配了这条规则（用于监控、调试、计费） |

`*` 表示通配符（wildcard），即不关心该字段的值：

```
src = *.*.*.*,  dst = 3.4.*.*      → forward(2)       "所有去往 3.4.*.* 的都走端口2"
src = 1.2.*.*, dst = *.*.*.*      → drop             "来自 1.2.*.* 的统统丢弃"
src = 10.1.2.3, dst = *.*.*.*     → send to controller "来自这个特殊地址的去问控制器"
```

> 关键跃迁：**传统转发只匹配目的 IP 一个字段，广义转发可以匹配 L2-L4 任意字段的任意组合**。数据平面的行为从硬件固定的逻辑变成了软件可编程的逻辑。

### 7.3 OpenFlow：SDN 的标准协议

OpenFlow 是 SDN 中控制器（Controller）与数据平面设备（交换机/路由器）通信的标准协议。每条流表条目的结构：

```
┌──────────────────────────────────────┐  ┌──────────┐  ┌─────────┐  ┌──────────┐
│              Match                    │  │  Action   │  │  Stats  │  │ Priority │
│  (L2 + L3 + L4 头部字段)              │  │ (动作)    │  │ (统计)  │  │ (优先级) │
├──────────────────────────────────────┤  ├──────────┤  ├─────────┤  ├──────────┤
│ Ingress Port | Src MAC | Dst MAC |   │  │ forward  │  │ #bytes  │  │ 数字越大 │
│ Eth Type | VLAN ID | VLAN Pri |      │  │ drop     │  │ #pkts   │  │ 越优先   │
│ IP Src | IP Dst | IP Proto | IP ToS │  │ modify   │  │         │  │          │
│ TCP/UDP Src Port | TCP/UDP Dst Port │  │ send to  │  │         │  │          │
│                                      │  │controller│  │         │  │          │
└──────────────────────────────────────┘  └──────────┘  └─────────┘  └──────────┘
   ← 链路层 →  ←———— 网络层 ————→  ← 运输层 →
```

可匹配的字段覆盖了三层头部：入端口、源/目的 MAC、以太网类型、VLAN ID/Priority、源/目的 IP、IP 协议类型、ToS、TCP/UDP 源/目的端口。

四种基本动作：
1. **Forward**：转发到指定端口（可以多播到多个端口）
2. **Drop**：丢弃（防火墙的"deny"）
3. **Modify**：修改头部字段（NAT 的"改写地址和端口"）
4. **Encapsulate and forward to controller**：封装后发给控制器（SDN 控制器集中决策）

### 7.4 统一抽象：一套机制替代四种设备

OpenFlow 最优雅的地方：**match+action 用同一套机制描述了所有网络设备的转发行为**。

| 设备 | 传统做法 | OpenFlow match+action |
|------|---------|----------------------|
| **Router** | 查路由表，LPM 匹配目的 IP | match(目的 IP 前缀) → action(forward out port) |
| **Switch** | 查 MAC 表，自学习 | match(目的 MAC) → action(forward 或 flood) |
| **Firewall** | ACL 规则列表，逐条匹配 | match(IP + TCP/UDP 端口) → action(permit 或 deny) |
| **NAT** | 专用 NAT 表 | match(IP + port) → action(rewrite address and port) |

**它们只是匹配的字段和执行的 action 不同。底层机制完全一样。** 这意味着——用一套可编程硬件（OpenFlow 交换机），配上不同的流表规则，就可以让同一台设备一会儿当路由器用，一会儿当防火墙用，一会儿当 NAT 用。这就是 SDN 的核心威力。

### 7.5 一个具体例子

```
          Host h6 (10.3.0.6)
              │
          ┌───s3───┐  控制器：让来自 h5/h6 的流量
          │        │  经过 s1 → s2 到达 h3/h4
     Host h5 (10.3.0.5)
          │
          └───s1──────s2──── Host h4 (10.2.0.4)
              │        │
         Host h1    Host h3
       (10.1.0.1)  (10.2.0.3)

s1 的流表：
  match(入端口=1, IP Dst=10.2.0.3) → forward(4)    去 h3 的走端口4
  match(入端口=1, IP Dst=10.2.0.4) → forward(4)    去 h4 的走端口4
  match(入端口=2, IP Src=10.3.*.*, IP Dst=10.2.*.*) → forward(4)

s2 的流表：
  match(入端口=4) → forward(2 或 3)  分发给 h3 或 h4

s3 的流表：
  match(IP Src=10.3.*.*) → forward(3)  h5/h6 的流量发往 s1
  match(IP Dst=10.2.*.*)  → forward(3)  去 h3/h4 的也发往 s1
```

控制器（Controller）通过编排多台交换机的流表，创建出**网络范围的行为**——比如"从 h5 和 h6 来的数据报，经过 s1 再到 s2，最终到达 h3 或 h4"。在传统网络中，这需要每台设备各自跑路由协议、各自计算——而且无法表达"来自特定源的流量走特定路径"这种策略。

## 8. Middleboxes — 理想与现实的差距

### 8.1 教科书上的网络 vs 真实的网络

教科书告诉你互联网是一个干净的沙漏：IP 是细腰（thin waist），上面跑着各种运输层和应用层协议，下面承载在各种链路层技术上。**每台设备只实现 IP 这一层协议**，这就是互操作性的全部秘密。

**但真实的网络不是这样的。**

RFC 3234 定义 Middlebox（中间盒）为：

> "any intermediary box performing functions apart from normal, standard functions of an IP router on the data path between a source host and destination host"
>
> 在源和目标之间数据路径上，执行标准 IP 路由器功能之外的任何功能的中间设备。

### 8.2 中间盒无处不在

```
企业网：        防火墙、IDS、NAT、负载均衡器、缓存
运营商/ISP：    防火墙、IDS、NAT（CGNAT）、缓存/CDN
数据中心：      负载均衡器、应用层网关、SSL 终结器
移动网络：      NAT、防火墙、TCP 代理
```

这些设备不在教科书的五层模型里，但它们处理着互联网的大部分流量。**IP 沙漏模型长出了中年"游泳圈"（love handles）**——原本纯净的 IP 层被插入了防火墙、NAT、缓存、IDS、负载均衡器等各种中间处理逻辑。

### 8.3 中间盒的未来：从专有硬件到软件定义

```
过去：封闭的专有硬件（proprietary hardware）
      ↓
现在：白盒硬件（whitebox hardware）+ 开放 API
      ↓         ↓
    SDN         NFV
 (集中控制)   (网络功能虚拟化：在白盒网络/计算/存储之上实现可编程服务)
```

SDN 提供**逻辑上集中的控制**和配置管理（通常在私有/公有云中），NFV 则把网络功能本身变成跑在白盒硬件上的软件。防火墙不再是一个铁盒子，而是一个可以部署在任何地方的软件实例。这就是"软件吃掉世界"在网络领域的表现。

## 难点突破

### 难点1：CIDR 路由聚合为什么能工作？

**困惑**：如果 ISP 通告了一个聚合路由 `200.23.16.0/20`，怎么保证发往其中某个子网（如 `200.23.18.0/23`）的数据报不会错误地跑到另一个子网？

**关键**：**聚合只在"对外通告"层面产生效果**。对外部网络，ISP 确实只通告 `/20`，所有发往这个块的流量先汇集到 ISP。但当数据报到 ISP 内部后，ISP 的路由器有**更具体的路由条目**（`/23`、`/24`），LPM 会选择最长匹配——也就是更具体的那个前缀。这就是为什么层次化编址 + 最长前缀匹配 = 路由聚合 + 精确交付。

**类比**：一个国家对外通告"所有寄往中国的邮件先到北京分拣中心"（聚合路由 `/20`）。到了北京之后，分拣中心根据更具体的地址（省→市→区→街道）逐级分发（LPM）。北京不需要向全世界通告每个街道的邮编——只需要通告"中国"就够了。

### 难点2：NAPT 如何区分不同内网主机的同端口连接？

**困惑**：两台内网主机同时用源端口 1723 访问同一台外部服务器——返回的响应都是 `dst=138.76.29.7:???`，怎么知道该交给谁？

**关键**：**NAT 路由器在转换时会为不同内网主机分配不同的外部端口号**。如转换表所示：

```
10.1.1.3:1723 → 192.168.2.2:1492    （分配了 1492）
10.1.1.2:1723 → 192.168.2.2:1723    （保留了 1723）
```

这两台主机从内网发出的都是 `src=10.1.1.x:1723`，但在 NAT 路由器处，10.1.1.3 的连接被改写成公网端口 1492，10.1.1.2 的连接保留了 1723。当响应回来时，目标端口就是"钥匙"——1492 对应 10.1.1.3，1723 对应 10.1.1.2。**即使两台内网主机用了相同的源端口，它们在 NAT 转换表中有不同的外部端口映射，路由器能精确区分。**

### 难点3：为什么 IPv6 去掉分片和校验和反而更好？

**分片**：IPv4 允许中间路由器对超过 MTU 的数据报进行分片。这意味着路由器需要做分片逻辑（判断 MTU、切分、重组头部），拖慢转发。IPv6 的策略是：**路由器不分片——如果数据报太大，直接丢弃并回 ICMP 错误**。分片由源端在发送前完成（Path MTU Discovery）。路由器变简单了、变快了。

**校验和**：IPv4 路由器每跳都要重算头部校验和——因为 TTL 每跳减 1，校验和必须跟着变。这是每跳最耗 CPU 的操作之一。IPv6 直接去掉校验和，依赖上层协议（TCP/UDP 有自己的端到端校验和）和链路层 CRC 做差错检测。代价是极小概率的漏检，收益是每跳转发速度显著提升。

| OpenFlow | 开放流协议 | SDN 控制器与交换机之间的标准通信协议 |
| Flow Table | 流表 | 存储 match+action 规则的表 |
| Middlebox | 中间盒 | 数据路径上执行非标准 IP 路由功能的中间设备 |
| NFV | 网络功能虚拟化 | 用虚拟化技术在白盒硬件上实现网络功能 |
| SDN | 软件定义网络 | 控制平面集中化、数据平面可编程的网络架构 |
| Anycast | 任播 | 发往一组节点中"最近"一个的通信模式 |
| Thin Waist | 细腰 | IP 层作为互联网唯一强制实现的协议层 |

## 关键原句

> "A separate address is required for each physical interface of a host/router to a network – Facilitates routing"
>
> 主机/路由器的每个物理网络接口都需要一个独立的 IP 地址——这便于路由。

> "Classless Inter Domain Routing (CIDR) – An IP address is represented as 'A.B.C.D/n', where n is called the IP (network) prefix"
>
> 无类域间路由（CIDR）——IP 地址表示为 'A.B.C.D/n'，其中 n 称为 IP（网络）前缀。

> "Goal: host dynamically obtains IP address from network server when it 'joins' network – can renew its lease on address in use – allows reuse of addresses (only hold address while connected/on)"
>
> 目标：主机在"加入"网络时从网络服务器动态获取 IP 地址——可以续约正在使用的地址——允许地址复用（仅在连接/开机时持有地址）。

> "NAT – Enables different sets of IP addresses for internal and external traffic – The IP address translations occur where the Intranet interfaces with the broader Internet"
>
> NAT——允许内部和外部流量使用不同的 IP 地址集——IP 地址转换发生在内网与更广互联网的交界处。

> "IPv6 – Initial motivation: address space exhaustion – Rapid growth of networks and the Internet – 32-bit address space (esp. net address) soon to be completely allocated"
>
> IPv6——最初动机：地址空间耗尽——网络和互联网的快速增长——32 位地址空间（尤其是网络地址）即将被完全分配。

> "A flow is uniquely identified by the combination of Source and destination address and a non-zero 20-bit Flow Label"
>
> 一个流由源地址、目的地址和一个非零的 20 位流标签的组合唯一标识。

> "Middlebox (RFC 3234): any intermediary box performing functions apart from normal, standard functions of an IP router on the data path between a source host and destination host"
>
> 中间盒（RFC 3234）：在源主机和目标主机之间的数据路径上，执行正常、标准 IP 路由器功能之外的功能的任何中间设备。

> "match+action abstraction: match bits in arriving packet, take action"
>
> match+action 抽象：匹配到达分组中的 bit 位，执行动作。

## 记忆卡片

> **Q: 串讲 IP 地址的演化史——为什么从分类编址走到 CIDR？**
> **A:** 分类编址（A/B/C/D/E）按固定边界划分网络号和主机号，导致严重浪费——A 类太大（1600 万台主机），C 类太小（254 台）。子网划分允许组织内部"借"主机位划分子网，但没有解决全局分配粒度的问题。CIDR（`a.b.c.d/n`）彻底抛弃了类的概念，前缀长度任意指定。配合层次化编址，CIDR 实现了**路由聚合**——ISP 对外只通告一个短前缀，内部用更长、更具体的前缀逐级精确匹配。这就是第 06 章路由器需要最长前缀匹配（LPM）的根本原因。

> **Q: DHCP 的工作过程是什么？除了 IP 地址还能拿到什么？**
> **A:** 四步 UDP 广播：Discover → Offer → Request → ACK。DHCP 服务器返回四样东西：(1) 客户端的 IP 地址，(2) 默认网关（first-hop router）地址，(3) DNS 服务器的名称和 IP，(4) 子网掩码。全程广播是因为客户端一开始连 IP 都没有，无法建单播连接。封装链为 `DHCP → UDP → IP → Ethernet`，Ethernet 帧的目标地址是广播 `FF:FF:FF:FF:FF:FF`。

> **Q: NAPT 如何用一个公网 IP 区分多台内网主机的流量？**
> **A:** NAT 路由器维护一张 `{内网 IP:Port} ↔ {外网 IP:Port}` 的转换表。外部响应回来时，**目标端口号就是查表的钥匙**。即使两台内网主机碰巧用了相同的源端口，NAT 路由器会给它们分配不同的外部端口映射。每条 TCP/UDP 连接都有唯一的外部端口，响应因此能精确送回对应的内网主机。

> **Q: IPv6 为什么去掉校验和和分片？**
> **A:** **校验和**：IPv4 路由器每跳都要重算头部校验和（因为 TTL 每跳减 1，校验和必须跟着变），这是每跳最耗 CPU 的操作之一。IPv6 直接去掉，依赖上层协议（TCP/UDP 有自己的端到端校验和）和链路层 CRC 做差错检测。**分片**：IPv6 路由器永远不分片——超过 MTU 的数据报直接丢弃并回 ICMP 错误，由源端在发送前通过 Path MTU Discovery 完成分片。两项改动都让每跳转发速度显著提升。

> **Q: OpenFlow 的 match+action 抽象是什么？它如何统一不同网络设备？**
> **A:** **match+action** 抽象：匹配 L2-L4 任意头部字段（MAC、IP、TCP/UDP 端口等），执行动作（转发、丢弃、修改、发给控制器）。路由器 match 目的 IP 前缀然后转发，交换机 match 目的 MAC 然后转发/泛洪，防火墙 match IP+端口然后允许/拒绝，NAT match IP+端口然后改写地址——**底层机制完全相同，差别的只是匹配哪些字段、执行什么动作**。同一台 OpenFlow 交换机配上不同流表规则，可以当路由器、交换机、防火墙或 NAT 用。

> **Q: IPv4→IPv6 的两种过渡策略各有什么优劣？**
> **A:** **双栈（Dual Stack）**：路由器同时跑 IPv4 和 IPv6 协议栈，在两种格式间转换。优点：兼容性好。缺点：地址转换会丢失 IPv6 特有信息（Flow Label、扩展头部）。**隧道（Tunneling）**：IPv6 分组作为载荷封装在 IPv4 数据报中穿越 IPv4 区域。优点：IPv6 分组完整保留，不失任何信息。缺点：额外的 IPv4 头部减少了有效载荷容量。

> **Q: IP 沙漏的"细腰"是什么？"游泳圈"又是什么？**
> **A:** "细腰"是 IP 层——互联网上每台设备必须实现的唯一协议，上面承载各种运输层和应用层协议，下面适配各种链路层和物理层技术。这是互联网互操作性的根基。"游泳圈"是**中间盒**（Middleboxes）——防火墙、NAT、负载均衡器、缓存、IDS 等——它们在数据路径上插入了有状态的处理逻辑，打破了端到端原则的纯净性。互联网到了中年，细腰上长出了赘肉。

### 必考简答题

**1. 为什么分类编址失败了？CIDR 如何解决这些问题？**（★★★）

**答**：分类编址按 A/B/C 类固定网络-主机边界分地址，导致严重浪费——A 类 1600 万主机太多，C 类 254 台太少，分配粒度太粗。CIDR 用 `a.b.c.d/n` 抛弃固定边界，前缀长度任意指定，按需分配。同时层次化编址使 ISP 对外通告聚合前缀，内部用更长前缀精确匹配，缩小了全球路由表。

**2. DHCP 的四步交互过程是什么？它提供哪些信息？**（★★）

**答**：Discover（客户端广播找服务器）→ Offer（服务器回应可用 IP）→ Request（客户端确认选择）→ ACK（服务器正式分配）。全程 UDP 广播。ACK 返回：客户端 IP 地址、默认网关地址、DNS 服务器名和 IP、子网掩码。

**3. NAPT 如何处理多台内网主机共享一个公网 IP 的流量？**（★★★）

**答**：NAT 路由器维护 `{内网 IP:Port} ↔ {外网 IP:Port}` 转换表。每台内网主机即使源端口相同，路由器分配不同的外部端口映射。响应回来时，目标端口号是查表的钥匙，路由器根据映射将分组改回对应内网主机地址送达。

**4. IPv6 相比 IPv4 做了哪些关键改进？为什么去掉校验和和分片？**（★★★）

**答**：128 位地址解决枯竭；简化 40 字节固定头部；去掉校验和（每跳重算太慢，依赖上层 TCP/UDP 和链路层 CRC 做检测）；去掉路由器分片（源端做 Path MTU Discovery，路由器不分片，超 MTU 直接丢弃回 ICMP）；新增 Flow Label 标识流加速转发、Traffic Class 支持 QoS、内置 IPsec。

**5. OpenFlow 的 match+action 抽象如何统一不同网络设备？**（★★★）

**答**：match 任意 L2-L4 头部字段（MAC、IP、TCP/UDP 端口），action 执行转发/丢弃/修改/发给控制器。路由器 match 目的 IP → forward；交换机 match 目的 MAC → forward/flood；防火墙 match IP+port → permit/deny；NAT match IP+port → rewrite。底层机制完全相同，只差匹配字段和动作。

### 必考计算题

**类型一：CIDR 前缀计算**（★★★）

> 已知 IP `10.217.123.7`，子网掩码 `255.255.240.0`，求：网络前缀、网络地址、广播地址、可用 IP 范围。

**解法**：
```
IP:   00001010 . 11011001 . 01111011 . 00000111  (10.217.123.7)
掩码: 11111111 . 11111111 . 11110000 . 00000000  (255.255.240.0)

AND  → 00001010 . 11011001 . 01110000 . 00000000

网络前缀 = /20（掩码中 1 的个数）
网络地址 = 10.217.112.0（AND 结果）
广播地址 = 10.217.127.255（主机位全 1：后 12 位 = 111111111111 → 10.217.112.0 + 0.0.15.255）
可用 IP = 10.217.112.1 ~ 10.217.127.254（去掉全 0 和全 1）
可用数量 = 2¹²−2 = 4094
```

**类型二：路由聚合**（★★★）

> 将以下前缀聚合成最短的一个前缀通告出去：
> `200.23.16.0/23`、`200.23.18.0/23`、`200.23.20.0/24`、`200.23.21.0/24`

**解法**：
```
200.23.16.0/23 → 200.23.00010000.0/23
200.23.18.0/23 → 200.23.00010010.0/23
200.23.20.0/24 → 200.23.00010100.0/24
200.23.21.0/24 → 200.23.00010101.0/24

范围：200.23.16.0 ~ 200.23.21.255
找共同前缀：200.23.16.0 和 200.23.21.255 的二进制

200.23.00010000.0  → 200.23.00010000.00000000
200.23.00010101.255 → 200.23.00010101.11111111

共同部分：200.23.00010...（前 5+3 = 前 21 bit 相同？不对）

仔细看：
16 = 00010000
21 = 00010101
这两个从第 3 位（从右数，即 bit 2）开始不同

从前面的 bit 对齐：
200.23.  → 前 16 位相同
第三个字节：00010xxx — 前 5 位相同（00010），后 3 位不同

所以共同前缀 = 16 + 5 = 21 位

聚合结果 = 200.23.16.0/21
```

**类型三：子网划分**（★★）

> 某组织获得 `128.10.0.0/16`，需要划分 8 个子网，每个子网至少容纳 500 台主机。请设计子网掩码。

**解法**：
- 8 个子网需要借 log₂8 = 3 位（2³ = 8）
- 500 台主机需要至少 9 位（2⁹−2 = 510 > 500, 2⁸−2 = 254 < 500）
- 原始主机位 = 16，借 3 位 → 剩 13 位做主机位（2¹³−2 = 8190 > 500 ✓）
- 子网掩码 = /19 = 255.255.224.0

**验证**：
```
子网 0：128.10.0.0/19    （128.10.0.0  ~ 128.10.31.255）
子网 1：128.10.32.0/19   （128.10.32.0 ~ 128.10.63.255）
子网 2：128.10.64.0/19   ...
...
子网 7：128.10.224.0/19   （128.10.224.0 ~ 128.10.255.255）
```

### 易错点

- **分类编址的"网络数"要减 2**（全 0 保留，127 回环），但**子网划分的子网数现不强制减 2**（看老师要求）
- **CIDR 聚合要找最长共同前缀**，不是简单取最小范围的 /n
- **NAPT 是端口号区分主机**，不是 IP 地址
- **IPv6 去的是头部校验和，TCP/UDP 自身的端到端校验和还在**
- **OpenFlow 不只管转发——match+action 涵盖了防火墙（drop）、NAT（rewrite）等所有行为**
