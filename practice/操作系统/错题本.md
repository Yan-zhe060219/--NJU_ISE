## 6.22 · 并发模块首次接触

### Q1 · fork/execve 保留 vs 替换
- **来源**：09-进程 §三大系统调用
- **弱项**：🟡 fork 正确，execve 只说"重置文件状态"不完整
- **答案**：execve **替换**：地址空间（代码/数据/堆/栈全部清空，载入新程序）。execve **保留**：① 文件描述符（除非标记 FD_CLOEXEC）② 环境变量 ③ 进程 ID/父进程 ID ④ 当前工作目录 ⑤ 信号处理设置（SIG_IGN 保留，SIG_DFL 的恢复默认）
- **回看**：fork=复制（COW优化），execve=变身（保留fd是shell管道 `ls | wc` 能工作的原因），exit=终结

### Q2 · MFQ 机制与愚弄方法
- **来源**：10-调度 §5 MFQ + 难点突破§1
- **弱项**：🟡 机制描述模糊，"降级后获更长时间片"说法不精确
- **答案**：新进程入最高优先级（短时间片）→ 用完时间片降一级（获更长时间片）→ I/O 阻塞的没用完→留当前级。自然结果：I/O 密集留高层(短片·频繁跑)，CPU 密集沉底层(长片·偶尔跑)。愚弄：时间片快完时故意 sleep → 不降级 → 永驻高优先级。防御：追踪长期 CPU 使用，超配额强制降级。
- **回看**：降级不是因为"CPU密集"标签，是因为**用完了时间片**。自动分类是副作用，不是机制。

### Q3 · Belady 异常
- **来源**：12-地址空间_续 §6 Belady 异常
- **弱项**：🟡 定义背对，但不理解"为什么"，需要具体例子
- **答案**：FIFO 3帧=9次缺页，4帧=10次缺页（具体推演见笔记/对话）。只有 LRU 和 Optimal 永不发生——它们满足栈算法属性。
- **回看**：考前扫一遍推演数字就记住了。

### Q4 · 调度计算：平均数算错
- **来源**：10-调度 计算题T1
- **弱项**：🔴 完成时间全对，但 FCFS 周转总和写成 26（应 61）、SJF 写成 26（应 57）、SRTF 写成 26（应 52）——把三个算法的周转和都写成了 26（实际是 SRTF 的等待和）。混淆了周转时间与等待时间。
- **答案**：周转时间=完成-到达，等待时间=周转-执行。FCFS平均周转15.25/平均等待8.75；SJF 14.25/7.75；SRTF 13/6.5；RR(q=4) 18.25/11.75。
- **回看**：周转≠等待！做完题检查：周转时间一定≥等待时间。

## 6.24 · 信号量专题

### Q5 · 有界缓冲区生产者-消费者 🔴

- **来源**：`/review go` 信号量推导 Q1
- **弱项**：🔴 基础知识欠缺——信号量初值含义不清晰，P/V 操作顺序规则不理解

**题目**：
```
缓冲区大小 N=8。多个生产者，多个消费者。
生产者循环生产 item 放入缓冲区。消费者循环取出消费。
用信号量实现，写完整伪代码。
```

**完整答案**：

```c
semaphore empty = 8;   // 空位数（有几个空位可用）
semaphore full  = 0;   // 已填充数（有几个 item 可取）
semaphore mutex = 1;   // 互斥锁，保护 buf[]/in/out 共享变量

item_t buf[8];
int in = 0, out = 0;

void producer() {
    while (1) {
        item_t item = produce();   // ① 生产（缓冲区外）
        
        P(empty);                  // ② 预订空位
        P(mutex);                  // ③ 拿锁
        
        buf[in] = item;            // ④ 放入
        in = (in + 1) % 8;
        
        V(mutex);                  // ⑤ 放锁
        V(full);                   // ⑥ 通知"有货了"
    }
}

void consumer() {
    while (1) {
        P(full);                   // ① 预订货物
        P(mutex);                  // ② 拿锁
        
        item_t item = buf[out];    // ③ 取出
        out = (out + 1) % 8;
        
        V(mutex);                  // ④ 放锁
        V(empty);                  // ⑤ 通知"有空位了"
        
        consume(item);             // ⑥ 消费（缓冲区外）
    }
}
```

**逐步骤解析**：

**1. 为什么是 3 个信号量？**
- 两个约束需要等待：缓冲区满（生产者等）、缓冲区空（消费者等）→ 各需要一个信号量
- 一个共享资源需要互斥：buf[]/in/out 是多个线程共享的 → 需要一个 mutex
- 约束 ≠ 互斥。约束是"条件不满足先等"，互斥是"临界区只能一个人进"。

**2. 每个信号量的初值为什么是这样？**

| 信号量 | 初值 | 推理 |
|--------|------|------|
| empty | 8 | 一开始缓冲区全空 → 有 8 个空位可以放 → 生产者可以直接 P 8 次不阻塞 |
| full | 0 | 一开始没东西可取 → 消费者一 P 就阻塞 → 必须等生产者 V 后才能取 |
| mutex | 1 | 临界区只能一人进 → 标准互斥初值 |

判断方法：想"一开始谁可以直接过，谁要等"。一开始生产者可以直接放 8 个 → empty=8。一开始消费者要等 → full=0。

**3. 为什么 P(empty) 必须在 P(mutex) 前面？**

错误顺序 `P(mutex) → P(empty)` 的死锁场景（缓冲区满时）：

```
生产者 A: P(mutex) ✅ → P(empty) ❌ 阻塞（满，empty=0）
消费者 B: P(full) ✅ → P(mutex) ❌ 阻塞（mutex 被 A 拿着）

→ A 等 B 释放空位，B 等 A 释放锁 → 死锁
```

**原则**：任何 P 操作，先申请"条件信号量"（empty/full），后申请"互斥信号量"（mutex）。V 操作相反：先 V(mutex) 后 V(条件信号量)。这不是固定语法，是死锁分析的结果。

**4. 为什么 produce() 和 consume() 放临界区外面？**

临界区只保护**共享变量**（buf/in/out）。produce() 和 consume() 只操作局部变量 item，不需要保护。放临界区外面可以缩短持锁时间，提高并发度。

### Q6 · 苹果-橘子问题 🔴

- **来源**：`/review go` 信号量推导 Q2
- **弱项**：🔴 不会从零设计——不知道如何将问题翻译成信号量

**题目**：
```
爸爸往盘子放苹果，妈妈往盘子放橘子。
儿子只吃苹果，女儿只吃橘子。
盘子一次只能放一个水果（N=1）。
用信号量实现。
```

**完整答案**：

```c
semaphore plate = 1;    // 盘子空（初值 1：一开始是空的）
semaphore apple = 0;    // 盘子里有苹果？（初值 0：没苹果）
semaphore orange = 0;   // 盘子里有橘子？（初值 0：没橘子）

void father() {        // 爸爸放苹果
    while (1) {
        P(plate);      // 等盘子空
        put_apple();   // 放苹果
        V(apple);      // 告诉儿子"有苹果了"
    }
}

void mother() {        // 妈妈放橘子
    while (1) {
        P(plate);      // 等盘子空
        put_orange();  // 放橘子
        V(orange);     // 告诉女儿"有橘子了"
    }
}

void son() {           // 儿子吃苹果
    while (1) {
        P(apple);      // 等盘子里有苹果
        take_apple();  // 取走苹果
        V(plate);      // 告诉爸爸/妈妈"盘子空了"
        eat();         // 吃（盘子外）
    }
}

void daughter() {      // 女儿吃橘子
    while (1) {
        P(orange);     // 等盘子里有橘子
        take_orange(); // 取走橘子
        V(plate);      // 告诉爸爸/妈妈"盘子空了"
        eat();         // 吃（盘子外）
    }
}
```

**逐步骤解析**：

**1. 为什么是 3 个信号量？**

这个问题和 Q1 不同之处在于：**放什么决定了谁取**。

- `plate`：盘子这个资源，一次只能一个人操作 → 初值 1（互斥 + 条件合一，因为 N=1）
- `apple`：苹果的信号——儿子等这个信号。初值 0（一开始没苹果）
- `orange`：橘子的信号——女儿等这个信号。初值 0（一开始没橘子）

**2. Q1 用 empty+full，这里为什么用 apple+orange？**

Q1 里所有 item 等价（不分类型），用 `full` 统一计数就行。

这里 item **分类型**——儿子只取苹果，女儿只取橘子。如果还用 `full`，儿子 P(full) 拿到一个橘子就错了。所以每种类型各一个信号量，精确通知"来的是谁的食物"。

**3. P/V 配对关系**

```
father: P(plate) ... V(apple)
mother: P(plate) ... V(orange)
son:    P(apple) ... V(plate)
daughter: P(orange) ... V(plate)
```

每对 P/V 构成一个"资源传递"：
- `plate`：放的人消耗盘子（P）→ 取的人归还盘子（V）
- `apple`：爸爸发出苹果（V）→ 儿子接收苹果（P）
- `orange`：妈妈发出橘子（V）→ 女儿接收橘子（P）

**4. 为什么这里没有单独的 mutex？**

盘子 N=1。`plate` 信号量既当互斥（同时只能一人操作盘子）又当条件（没空盘子时等）。当 N>1 时才需要把互斥和条件拆开。

**5. 和 Q1 有界缓冲区的本质区别**

| | Q1 有界缓冲区 | Q2 苹果-橘子 |
|---|---|---|
| item 类型 | 同质 | 异质（苹果/橘子） |
| 谁取 | 任意消费者 | 特定消费者（儿子/女儿） |
| 通知方式 | 一个 full 统记 | 按类型各一个信号量 |
| 互斥 + 条件 | 分离（empty/full + mutex） | 合并（plate 同时做互斥和条件） |

### Q7 · 理发店问题 🔴

- **来源**：`/review go` 信号量推导 Q3
- **弱项**：🔴 不会从零设计——资源计数 + 多角色交互未掌握

**题目**：
```
理发店有 3 个理发师、5 把等待椅。
没顾客时理发师睡觉，顾客来叫醒理发师。
等待椅满时顾客离开。
用信号量实现。
```

**完整答案**：

```c
semaphore barbers = 0;     // 有多少理发师醒着/可用
semaphore customers = 0;   // 有多少顾客在等待
semaphore mutex = 1;       // 保护共享变量 waiting

int waiting = 0;           // 当前在等待的顾客数（坐在椅子上 + 未被服务的）
const int CHAIRS = 5;      // 等待椅数量
const int TOTAL_BARBERS = 3;

void barber(int id) {
    while (1) {
        P(customers);        // ① 等顾客来（没顾客就睡）
        
        P(mutex);            // ② 拿锁，修改 waiting
        waiting--;           // ③ 从等待椅起来一个
        V(mutex);            // ④ 放锁
        
        V(barbers);          // ⑤ 告诉顾客"我准备好了"（同步：椅子→理发椅）
        
        cut_hair();          // ⑥ 理发（无锁）
    }
}

void customer(int id) {
    P(mutex);                // ① 拿锁，检查 waiting
    
    if (waiting < CHAIRS) {  // ② 有位置
        waiting++;           // ③ 坐下
        V(mutex);            // ④ 放锁
        
        V(customers);        // ⑤ 通知理发师"有顾客来了"
        P(barbers);          // ⑥ 等理发师叫自己（同步：确认分配到了理发师）
        
        get_haircut();       // ⑦ 理发
    } else {                 // ② 没位置
        V(mutex);            // ③ 放锁
        leave();             // ④ 离开店
    }
}
```

**逐步骤解析**：

**1. 需要哪些信号量？初值为什么？**

| 信号量 | 初值 | 含义 | 为什么 |
|--------|------|------|--------|
| customers | 0 | 有顾客在等待理发师 | 一开始没顾客 → 理发师 P 就睡 |
| barbers | 0 | 有理发师可分配 | 一开始顾客要等理发师准备好 → 0 |
| mutex | 1 | 保护 waiting 共享变量 | 标准互斥 |

**2. 为什么 waiting 不能用信号量替代？**

信号量只能表达"有/没有"，不能直接读"有几个"。`waiting < 5` 需要知道确切数量 → 必须是普通整数变量 + mutex 保护。

**3. barbers 信号量的作用——为什么要 V(barbers) 然后 P(barbers)？**

这是**分配协议**：理发师和顾客的握手。

```
顾客:  V(customers)  →  "我来了！"
       P(barbers)    →  "哪个理发师服务我？"

理发师: P(customers)  →  "有顾客了"
        waiting--
        V(barbers)    →  "我在等你，过来吧"
```

没有 barbers 信号量会怎样？顾客 V(customers) 后，不知道哪个理发师空出来了，可能多个顾客冲向同一个理发师。barbers 信号量起**排队分配**作用——3 个理发师对应 barbers 信号量的 3 次 V。

**4. 为什么理发师先 P(customers) 再 P(mutex)，不是反过来？**

假设反过来 `P(mutex) → P(customers)`：

```
理发师 A: P(mutex) ✅ → P(customers) 💤 阻塞（没顾客）
理发师 B: P(mutex) 💤 阻塞（mutex 被 A 拿着）
顾客: P(mutex) 💤 阻塞

→ 死锁。A 持锁等顾客，顾客等锁进来。
```

**原则和 Q1 相同**：先 P 条件信号量（customers），再 P 互斥信号量（mutex）。

**5. 顾客 side 的 if/else 为什么都在 mutex 里？**

waiting 是共享变量，读、判断、++ 必须是原子的——否则两个顾客同时读 waiting=4，都以为能进来，实际第 6 个也进来了。

**6. 3 个理发师怎么体现？**

不在信号量初值里。理发师数量体现在：创建了 3 个理发师线程，每个都在 `P(customers)` 上等待。barbers 信号量的 V/P 配对确保每个顾客被一个理发师接走。

## 6.25 · 五大方向自测 — 调度 + 内存 + 文件系统

### Q8 · 调度计算粗心 🟡

- **来源**：五大方向自测 方向三 · FCFS + SJF 计算
- **弱项**：🟡 SJF 平均周转时间算错——FCFS 正确（51/4=12.75），SJF 周转和 8+3+22+14=47，但抄了 FCFS 的结果写成 51/4=12.75。正确答案是 SJF 平均周转 47/4=11.75。
- **根因**：不是概念问题——SJF 每个进程的完成/周转/等待都算对了。是做完题没有独立验算每个结果。
- **回看**：周转时间 = 完成 - 到达，等待时间 = 周转 - 执行。**周转一定 ≥ 等待**（除非执行时间为 0）。做完检查：两个算法的平均值应该不同（SJF 一定 ≤ FCFS，这是 SJF 之所以最优的原因）。

### Q9 · fork/exec 初始空白 🟡

- **来源**：五大方向自测 方向二 · 无法独立写 fork+exec 代码
- **弱项**：🟡 理解了 PV 操作之后，面对 fork/exec 题目时完全空白——不知道 fork 返回什么、exec 家族函数的关系、Shell 为什么要 while 循环。

**从零到理解的完整过程**：

**为什么需要 fork？** 你打开一个 Shell，敲 `ls`，Shell 需要启动 `ls` 程序。但 Shell 不能直接把自己变成 `ls`——那样 Shell 自己就没了，`ls` 跑完就退出，没人等你敲下一条命令。所以必须先"克隆一个自己"，让克隆体去变身。

**fork() 做了什么？** 内核把当前进程完整复制一份——地址空间（代码/数据/堆/栈）、寄存器（所以父子从同一行继续跑）、文件描述符表（指向同一内核文件对象，偏移量共享）。然后**一个调用返回两次**：

- 父进程：fork 返回 子进程的 PID（>0）——父需要这个 ID 去 wait/kill
- 子进程：fork 返回 0 —— 子只需要知道自己是被 fork 出来的

**execve() 做了什么？** 用新程序的代码/数据/堆/栈**彻底覆盖**当前进程。但保留：文件描述符、环境变量、PID、当前目录——这些跨 execve 保留的属性是 Shell 管道能工作的基础（`ls | wc`：管道的 fd 被 `ls` 和 `wc` 通过 fork 继承，穿越 execve 后仍然有效）。

**exec 家族**：`execve` 是唯一的系统调用。`execl("/bin/ls", "ls", "-l", NULL)` 只是包装——参数一个个写，不用拼数组。做的事完全一样。

**exit() 做了什么？** 冲洗 stdio 缓冲区 → 调用 atexit 清理函数 → 关闭所有 fd → 通知父进程（SIGCHLD）→ 进入僵尸状态。父进程通过 `wait()` 收尸（回收 PCB）。

**Shell 模板**：
```c
while (1) {
    type_prompt();                    // 显示 $
    read_command(&cmd, &args);       // 读用户输入
    pid_t pid = fork();
    if (pid == 0) {
        execve(cmd, args, environ);  // 子进程变身
        // execve 成功 → 这行不执行
        perror("exec failed");
        exit(1);
    } else {
        waitpid(pid, &status, 0);    // 父进程等孩子
    }
}
```
while 的作用：执行完一条命令后回到循环开头，继续等用户输入下一条。没有 while，Shell 执行完 `ls` 就自己退出了。

- **回看**：fork = 复制（Copy），execve = 变身（Transform），exit = 终结。fork 返回两次，execve 成功不返回。三个系统调用构成进程的"生、变、死"。

### Q10 · 内存管理：从零到理解 🟡

- **来源**：五大方向自测 方向四 · 多级页表计算初始完全不会
- **弱项**：🟡 面对"32位、4KB页、两级页表、每级10位"这类题目时完全不知道从哪里下手。根本原因：不理解虚拟地址和物理地址的关系，不知道页表到底是什么。

**从零理解——为什么需要虚拟内存？** 程序里写的 `mov [0x1000], eax`，这个 `0x1000` 是虚拟地址。每个进程都有自己的一套虚拟地址空间（32位 = 4GB），进程 A 的 0x1000 和进程 B 的 0x1000 指向**不同的物理内存位置**。如果不用虚拟内存，程序里的地址直接就是物理地址——那 A 写了 0x1000，B 读 0x1000 就读到了 A 的数据，互相踩踏。

**页表做什么？** 页表是"虚拟页号 → 物理页框号"的翻译字典。每个进程有自己的页表，切换进程时 OS 更新 CR3 寄存器指向新进程的页目录。

**虚拟地址如何拆解？** 32 位地址不是"一个数"，而是一个三元组：
```
|← PD 10位 →|← PT 10位 →|← 偏移 12位 →|
  页目录下标    页表下标     页内偏移

这三段**全部是数组下标**，不是任何物理地址。
```
- 偏移 12 位：因为页大小 4KB = 2¹²，在页内定位需要 12 位
- PD 10 位 + PT 10 位：剩下 20 位分配给两级索引

**页目录和页表长什么样？** 都是 4KB 的数组，每个条目 4 字节：
- 页目录 = 1024 个 PDE，每个 PDE 存"某个二级页表在物理内存第几框"
- 二级页表 = 1024 个 PTE，每个 PTE 存"某个数据页在物理内存第几框"
- PDE 和 PTE 的**格式完全一样**：20 位物理框号 + 12 位标志位（P/R/W/U/S/A/D）

**为什么多级能省内存？** 单级页表：2²⁰ = 100 万个 PTE × 4B = 4MB，每个进程都要 4MB——不管你实际用多少内存。两级页表：如果某段 4MB 地址空间没分配，对应的 PDE 就是 NULL，整个 4KB 的二级页表就不需要建。程序实际用 28MB（7 个 4MB 段），只需 4KB（页目录）+ 7×4KB = 32KB。

**查找全过程**：
```
① CR3 → 页目录物理基地址
② 页目录[PD下标] → 得到 PDE（存二级页表物理框号）
③ 二级页表[PT下标] → 得到 PTE（存数据页物理框号）
④ 物理框号 × 4KB + 偏移 → 最终物理地址
```
全程查的都是物理地址。虚拟地址只提供下标，不参与任何地址计算。

- **回看**：虚拟地址的三段全是下标。PDE 和 PTE 都是 4B 索引卡，存的是指向下一级的物理地址。多级省内存的本质：不用的区域不建二级表。

### Q11 · 文件系统 inode 多级索引 🟡

- **来源**：五大方向自测 方向五 · 最大文件大小计算初始不会
- **弱项**：🟡 知道有"直接指针"和"间接指针"但不知道怎么计算——一个间接块能装多少指针？为什么这么算？

**为什么需要多级索引？** 文件在磁盘上不一定是连续存放的——删来改去，空闲块碎片化。需要用"指针数组"记录文件的每个数据块在哪。但大部分文件很小（中位数 ~2KB），少数文件很大（几 GB）。如果把所有指针都预分配，小文件浪费；如果指针太少，大文件装不下。**多级索引就是折中**：小文件用直接指针（快，不浪费），大文件用间接指针（容量够）。

**一个间接块能装多少指针？** 块大小 4KB，每个指针 4B → 4KB ÷ 4B = 1024 个指针。这是所有计算的基础数字。

**inode 的 15 个指针逐级算**：
| 指针 | 类型 | 计算 | 容量 |
|------|------|------|------|
| 0-11 | 直接指针 | 12 × 4KB | 48KB |
| 12 | 单级间接 | 1024 × 4KB | 4MB |
| 13 | 双级间接 | 1024 × 1024 × 4KB | 4GB |
| 14 | 三级间接 | 1024³ × 4KB | 4TB |

逐级推导：直接 → 间接（指针块里的指针各指向一个数据块）→ 双间接（指针块里的指针各指向一个指针块，再指数据块），每次多一层就乘 1024。

**硬链接 vs 软链接**：
- 硬链接：两个文件名 → 同一个 inode 号。本质是 **inode 号的别名**。删任意一个名字，另一个还在（inode 的 links_count 减 1 但不归零）。不能跨文件系统，不能链接目录。
- 软链接：一个独立文件（有自己的 inode），数据内容是目标路径的字符串。本质是 **路径名的别名**。删原文件 → 悬空引用。可以跨文件系统，可以链接目录。

**文件描述符 FD**：`open()` 返回的整数，只是一个数字。内核用三张表赋予它意义：每进程的 FD 表（FD号→打开文件表指针）→ 全局打开文件表（文件偏移+访问模式→inode指针）→ 全局 inode 表（权限+大小+数据块指针）。fork 后父子共享打开文件表的同一条目，这就是父子共享文件偏移的原因。

- **回看**：多级索引的本质是"够用+灵活"——大部分小文件 48KB 直接搞定，大文件用间接指针层层扩展。1024 这个数来自一个块能装的指针数（4KB÷4B），以此为基数逐级乘。

## 第一部分：绪论 — 什么是操作系统？

> 来源：PPT 1（操作系统概述）+ PPT 2（各种视角下的操作系统）
> 对应考纲：绪论 · 基本概念（单选/简答来源）

### 1.1 计算机系统为什么需要操作系统？

**问题**：计算机硬件（CPU、内存、磁盘、键盘、显示器）各不相同，接口也不统一。如果每个应用程序都要自己驱动硬盘、自己管理内存、自己处理键盘中断——那写一个"Hello World"可能需要几千行代码。更糟糕的是，多个程序同时运行时，如果没有一个"管理者"，它们会互相踩踏对方的内存。

**解决方案**：在硬件和应用之间插入一层软件，这个软件就是**操作系统**。它做三件事：

**① 幻术师（提供抽象）**——把丑陋的硬件变成好用的对象。程序不需要知道硬盘是 SATA 还是 NVMe，它只需要知道"文件"这个概念。程序不需要知道物理内存哪块是自己的，它只需要知道"地址空间"。操作系统提供的核心抽象：**进程、线程、地址空间、文件、I/O、套接字**。

**② 裁决人（管理资源）**——多个程序同时运行，谁用 CPU？谁用内存？操作系统负责分配、保护和隔离。一个程序崩溃不应该影响其他程序（"Segmentation fault (core dumped)" — 只崩自己，不崩系统）。

**③ 性能优化员**——操作系统在存储设备之间腾挪数据（磁盘→内存→缓存），让程序尽可能跑得快。理想情况下操作系统自身的开销应该尽可能小。

> 课件原话："操作系统把难看的硬件接口翻译成了友好易用的接口，为每个程序提供他们的进程。"

| OSTEP | 负责让程序更容易运行、让程序共享内存、让程序与设备交互的软件集合 | 使程序运行更容易 |
| OSPP | 为用户和应用管理计算机资源的软件层 | 管理资源 |
| OSC | 充当计算机用户和硬件之间中介的程序 | 中介 |
| Tanenbaum | 运行在内核态的软件 | 内核态 |

### 1.3 用户态 vs 内核态 — 操作系统权力的来源

这是整个操作系统设计的基石。CPU 在硬件层面支持两种运行模式：

| | 用户态（User Mode） | 内核态（Kernel Mode） |
|---|---|---|
| 能执行的指令 | 受限（只能计算类指令） | 不受限（可以访问所有硬件） |
| 能访问的内存 | 只能访问自己的地址空间 | 可以访问所有内存 |
| 谁在上面跑 | 普通应用程序 | 操作系统内核 |
| 出问题影响 | 只影响自己（Segfault） | 整个系统崩溃（Kernel Panic） |

**为什么 CPU 要支持两种模式？** 如果应用程序能直接执行任何指令、访问任何内存，那么一个恶意（或有 bug）的程序就能读其他程序的数据、破坏文件系统、甚至搞垮整个机器。**用户态/内核态的区分是操作系统一切保护机制的基础。**

**如何从用户态进入内核态？** 三条路径：

1. **系统调用（syscall）**：程序主动请求 OS 服务。例如 `write()` — "我想写文件，但我没权限操作磁盘，请你帮我。"
2. **中断（Interrupt）**：外部硬件通知 CPU。例如键盘按下 → 键盘控制器发中断 → CPU 暂停当前指令流 → 跳去执行中断处理程序。
3. **异常/陷阱（Exception/Trap）**：程序执行了非法操作。例如除以零、访问非法地址 → CPU 触发异常 → 转入内核态处理（通常会杀掉进程）。

> 课件核心比喻："对于程序而言，操作系统就是 syscall 的解释器——就像 CPU 解释普通指令一样，操作系统解释 syscall。"

---

### 1.4 程序就是状态机 — 理解操作系统的最基本模型

这是课件贯穿始终的核心思维模型。

**程序的本质**：一个状态机。状态 = 内存(M) + 寄存器(R)。每执行一条指令，状态就迁移一次。

```
(M₀, R₀) → 执行指令 → (M₁, R₁) → 执行指令 → (M₂, R₂) → ...

普通指令（mov, add, call...）：CPU 自己就能解释
特殊指令（syscall）：CPU 看不懂，交给操作系统解释
                     操作系统可以任意修改 (M, R)
                     然后返回，程序对此毫无感知
```

从这个角度看：**程序 = 计算指令 + syscall**。操作系统的存在就是帮程序解释那些它自己做不到的事情。

**C 语言程序也可以看成状态机**：
- 状态 = 栈帧(stack frames) + 全局变量 + 堆(heap)
- 初始状态 = `main(argc, argv)`，全局变量为初始值
- 迁移 = 执行一条简单 C 语句（函数调用 = push 新栈帧，return = pop 栈帧）

> 课件原话："`.s`（汇编）和 `.c`（高级语言）是两种状态机，编译器是二者之间的桥梁（`.s = compile(.c)`）。"

---

### 1.5 操作系统中任何程序的一生

课件用 `strace` 展示了任何一个程序的完整生命周期：

```
① execve 加载到内存，设置初始状态
② 状态机执行：
   - 进程管理：fork, execve, exit, wait...
   - 文件/设备管理：open, close, read, write...
   - 存储管理：mmap, brk...
③ 调用 exit / exit_group 退出
```

**所有程序本质上就是不断调用 syscall 的状态机。** 操作系统就是这个状态机的"运行时环境"。

> 工具：`strace` 可以追踪任何程序的 syscall 调用，是理解"程序在做什么"的最好工具。

---

### 1.6 硬件视角：操作系统就是跑在裸机上的 C 程序

从硬件的角度看，操作系统没什么神秘的：

```
CPU Reset → Firmware (BIOS/UEFI) → Bootloader (MBR/GRUB) → OS Kernel (main函数)
```

**CPU Reset 之后发生了什么？**
1. CPU 从固定地址（x86: `0xFFFFFFF0`，ARM: `0x00000000`）开始执行
2. 这个地址映射到主板上的固件（Firmware = BIOS 或 UEFI）
3. 固件初始化硬件，找到引导设备（硬盘/USB），加载第一个扇区（MBR）到内存 `0x7C00`
4. MBR 里的 bootloader（如 GRUB）加载操作系统内核的 ELF 文件
5. 跳转到内核入口 → 操作系统的 `main()` 开始执行

**关键认知**：操作系统就是**一个拥有完整计算机控制权限的 C 程序**——它能直接访问所有硬件、处理所有中断。它和普通程序的唯一区别是权限。

---

### 1.7 上下文切换（Context Switch）—— 分时操作系统的核心

**问题**：一个 CPU 怎么同时运行多个程序？

**答案**：快速切换。CPU 在进程之间来回跳，每次切换前**保存当前进程的寄存器现场**（PC、SP、通用寄存器等），**恢复下一个进程的寄存器现场**。切换得足够快（每几毫秒一次），人感觉像同时在跑。

**上下文切换时保存什么？** x86 架构下包括：PC（EIP）、栈指针（ESP/EBP）、EFLAGS、通用寄存器（EAX/EBX/ECX/EDX...）、段寄存器（CS/DS/SS）。这些保存在**内核栈**中——安全、可靠。

**上下文切换什么时候发生？**
1. 进程主动让出（调用 sys_sched 或等 I/O 阻塞）
2. 时钟中断（操作系统抢占当前进程）

> 课件核心图：上下文切换就是 CPU 寄存器的"PUSH 保存 → POP 恢复"过程。硬件和操作系统配合，让进程 A 暂停、进程 B 恢复、进程 A 再次恢复时仿佛从未被打断过。

---

### 1.8 抽象视角：操作系统本身就是一个状态机

课件给出了最全局的视角。操作系统的状态由以下组成：

```
OS 状态 = 
  所有用户进程的元信息（PCB：PID、PC、栈指针、状态...）
  + 内核栈（每个进程一个，保存中断/系统调用的现场）
  + 内核堆（操作系统动态分配的数据结构）
  + 操作系统代码区
  + 所有文件/地址空间/设备的元信息
```

**操作系统的状态是被动迁移的——它自己不主动跑**。只有两个触发条件：
1. **用户程序执行 syscall**（主动请求：`read()`、`fork()`、`exit()`...）
2. **硬件中断发生**（被动事件：时钟中断、键盘输入、磁盘 I/O 完成...）

操作系统拿到控制权后，执行相应的处理代码，然后**返回用户态**，进程继续跑。整个过程对用户程序透明——它不知道自己在某个 syscall 时被暂停了 5ms 让给了另一个进程。

> 课件用 Python 实现了一个玩具操作系统（os-model.py / mosaic.py），用 `yield` 模拟进程切换，用 `send()` 模拟系统调用。核心原理完全一样——理解了玩具，就理解了真实 OS。

## 第二部分：并发 — 从"共享就出事"到"安全地共享"

> 来源：PPT 3（多处理器编程）+ PPT 4（互斥）+ PPT 5（互斥进阶）+ PPT 6（同步）+ PPT 7（同步进阶）+ PPT 8（并发Bugs）
> 对应考纲：内存一致性模型、互斥、条件变量、信号量、安全性与活性

### 2.1 为什么需要并发 — 单核时代结束了

**问题**：2000 年代之前，CPU 越来越快（摩尔定律），程序不用改也会越来越快。后来时钟频率撞墙了——再快散热跟不上。解决方案：在一个芯片上堆多个核，指望程序**并行**跑在多个核上。

**Amdahl 定律**：即使有无穷多 CPU，加速比也受限于程序中不可并行化的部分。
```
speedup = 1 / (1-p + p/n)
p = 可并行的比例, n = 并行线程数
若 p=0.9, n→∞ → speedup ≤ 10 倍
```

**更严重的问题**：代码的并行化和同步不简单，非常容易出错。操作系统本身就是世界上第一个并发程序——它的很多内部数据结构（进程列表、页表、文件系统）都得考虑数据竞争。

---

### 2.2 线程 — 并发的基本单位

**线程是什么？** 共享内存的执行流。多个线程**共享**堆和全局变量，但各有**独立的**栈和寄存器。

```
线程 = 自己的 PC + 自己的栈 + 自己的寄存器 (私有的)
      + 共享的堆 + 共享的全局变量 + 共享的代码 (共享的)
```

线程的关键认知：**一个线程执行一步，可能顺带改变另一个线程的状态**（因为共享内存）。线程 1 改了全局变量，线程 2 没做任何操作，但它的"世界"变了——这种被动改变是并发的核心难题。

**线程 vs 进程**：线程共享地址空间（同一个进程内的线程），操作系统不提供线程间保护——栈空间虽然约定是私有的，但别的线程实际上可以访问。地址空间的保护以**进程**为边界。

**线程生命周期**：Init → Ready → Running → Waiting → Finished。只有 Running 状态下线程的上下文在 CPU 上，其余状态 TCB 保存在内核的队列里。

---

### 2.3 并发编程的三大挑战 — 一切乱套了

**① 原子性丧失**：`sum++` 在 CPU 层面是三条指令（mov + add + mov），线程切换可能发生在任意两条之间。即使写成一条汇编指令 `incq`，在多核上依然不安全——两个核同时执行，结果还是错的。

课件用 `sum++` 的例子展示了问题：两个线程各加 1 亿次，结果永远小于 2 亿。
- 单核：线程被中断打断 → 违背 All-or-nothing
- 多核：两个核同时读写 → 隔离性(Isolation)也违背了

**② 顺序性丧失**：编译器会优化重排指令。比如：
```c
while (!done);  // 被编译器优化为 if (!done) while(1);
```
在单线程下没问题，多线程下另一个线程设置 `done=true` 的写入可能永远不被看到。

**③ 全局一致性丧失**：现代 CPU 也会乱序执行。x86 是 TSO 模型（允许"写→读"被重排），ARM/RISC-V 是宽松模型（允许任意重排）。不同的核可能看到不同的访存顺序。

> 考试重点：x86 的 TSO — 保证 读读、读写、写写 的全局顺序，但**不保证写读**的全局顺序。这就是为什么 `x=1; t=y` 和 `y=1; t=x` 可能打出 `0,0`。

### 2.4 互斥 — 用锁保护临界区

**临界区**：访问共享资源的代码段。**竞态条件**：多个线程大致同时进入临界区，结果不确定。

**Safety vs Liveness**（Leslie Lamport 提出）：
- Safety："坏事永不发生"（如两个线程不会同时进临界区）
- Liveness："好事终将发生"（如某个想进临界区的线程最终能进去）

**临界区解决方案需满足三个条件**：
1. 互斥（Safety）：最多一个线程在临界区
2. 行进（Liveness）：临界区空时，想进的能进
3. 有界等待（Fairness）：等待时间有上限

**软件锁的演化史**（从失败中学习）：
- 尝试 1：关中断 → 单核可行，多核无效；用户态没权限；临界区死循环则系统卡死
- 尝试 2：软件 flag → 只是把竞态转移到 flag 上（test 和 set 不是原子的）
- 尝试 3：严格轮转 → 违背 Liveness（别人不进，自己最多进一次）
- **Peterson 算法**：flag（想进去）+ turn（轮到谁），两个线程时正确，但现代 CPU 乱序执行下仍错误

**硬件拯救**：`lock cmpxchg`（x86）或 `LL/SC`（ARM/RISC-V）。CPU 能锁定内存地址，在一条指令内完成 test-and-set。基于此实现的**自旋锁**才是正确的。

**自旋锁的问题**：用户态临界区长 → 其他核空转浪费 CPU。解决方案演进：
1. `yield` → 让出 CPU，但反复调度开销大
2. `mutex`（阻塞锁）→ OS 维护等待队列，未拿到锁的线程直接睡眠
3. **Futex（两阶段锁）**→ Fast path：自旋一次（一条原子指令，不进内核）；Slow path：失败则调用 futex_wait 阻塞。Linux 的 `pthread_mutex` 就是这样实现的。

**内核中的自旋锁额外挑战**：中断处理程序可能也需要同一把锁 → 死锁。解决：xv6 的 `spin_lock` 先关中断再自旋，用 `push_off/pop_off` 追踪中断嵌套。

### 2.5 条件变量 — 控制线程的顺序

**锁只能保证互斥，不能控制顺序。** 比如"缓冲区空时，消费者等；缓冲区满时，生产者等"——这是顺序控制，不是互斥。

**条件变量**：一个同步原语，让线程在某个条件不满足时睡觉，等条件满足时被叫醒。
- `cond_wait(cv, lk)`：原子地释放锁 + 阻塞自己；被唤醒时重新获取锁
- `cond_signal(cv)`：唤醒一个等待的线程；没有等待者则什么也不做
- `cond_broadcast(cv)`：唤醒所有等待的线程

**Hansen/Mesa vs Hoare 语义**（两个图灵奖得主各站一边）：
- **Hoare 语义**：signal → 被唤醒线程立即执行，signal 和被唤醒方之间原子。实现复杂，业界不用。
- **Hansen/Mesa 语义**：signal 后，被唤醒线程只是变成就绪，不一定立即执行。中间可能有其他线程抢先进入临界区改变条件。因此 **`cond_wait` 必须在 while 循环里**——醒来后重新检查条件。

**经验法则**：
1. 条件变量必须配合互斥锁和共享状态
2. `cond_wait` 一定要在 while 循环里（不是 if）
3. 不同条件用不同条件变量（避免错误的唤醒）
4. 或者用 `cond_broadcast` 一次唤醒所有（简单但性能差）

---

### 2.6 信号量 — 有记忆的同步原语

**为什么要有信号量？** 条件变量无记忆——如果 signal 发生在 wait 之前，signal 就丢了。信号量自带一个整数计数器，V 操作即使先于 P 发生，也会把计数 +1，后续 P 能看到。

**信号量 = 整数资源计数器**：
- `P(sem)`：如果 sem>0 → sem--，继续；否则阻塞
- `V(sem)`：sem++，如果有阻塞线程则唤醒一个

**初值的含义**：
- 初值=1 → 互斥锁（只有一个资源，一次只能一个人拿）
- 初值=0 → 顺序控制（一开始没资源，必须等别人 V）
- 初值=N → N 个资源可用（如缓冲区有 N 个空位）

**信号量解决生产者-消费者的优雅之处**：
```c
P(empty) → 占一个空位 → 生产 → V(full)    // 生产者消费空位，生产货物
P(full)  → 占一个货物 → 消费 → V(empty)    // 消费者消费货物，生产空位
```
不需要 while 循环检查条件——信号量自己会阻塞/唤醒。

**信号量的局限**：条件判断必须是整数的（"缓冲区还有几个空位"），如果不是整数条件（如打印 fish 的"要么打 < 要么打 > 二选一"），信号量就不太好用了。此时条件变量更灵活。

**信号量 vs 条件变量 vs 互斥锁**：
- 条件变量 + 互斥锁 = 可以实现信号量
- 信号量 = 可以实现互斥锁（但不能直接实现条件变量）
- 大多数场景：复杂同步用条件变量，简单计数同调用信号量

---

### 2.7 经典同步问题

**① 生产者-消费者**（已讲，略。考试重点：信号量方案 + 为什么 P(empty) 要在 P(mutex) 前面 → 避免死锁）

**② 读者-写者**：读者可同时读（读-读不互斥），写者独占（写-写互斥，写-读互斥）。
- 读者优先：读者持续来时写者饿死
- 写者优先：写者持续来时读者饿死
- 公平方案：用 ticket lock 排队
- RCU：读者完全无锁，写者分 removal（原子替换指针）和 reclamation（等旧读者全部退出后释放旧数据）。适合读多写少场景（Linux 内核 10%+ 锁是 RCU）

**③ 哲学家就餐**：
- 错误 1（全拿左边）→ 死锁（循环等待）
- 错误 2（拿不到右边就放下）→ 活锁（反复同时放下又拿起）
- 方案：随机睡眠 → 大多数情况下 OK
- 方案：限制 N-1 人上桌 → 鸽巢原理保证至少一人能吃
- 方案：给筷子编号，先拿小号 → 破坏循环等待，简单有效
- 考试排除哲学家，但**死锁四个必要条件**和**破环方法**是考点

### 2.8 死锁 — 四个必要条件 + 应对策略

**死锁**：一组线程每个都在等组内其他线程释放资源，全体卡死。

**四个必要条件**（Coffman, 1971）：
1. 互斥 — 资源不能被共享
2. 持有并等待 — 持有些资源，等更多资源
3. 不可抢占 — 不能抢别人持有的资源
4. 循环等待 — 形成等待环

**死锁一定饿死，饿死不一定死锁。**

**应对策略**：
1. **鸵鸟算法** — 忽略，重启大法（低频+低代价时）
2. **预防** — 破坏四个条件之一：
   - 破坏"持有并等待"→ 一次申请所有锁（不现实）
   - 破坏"不可抢占"→ 允许抢（很多资源不支持）
   - 破坏"循环等待"→ **Lock ordering**（按固定顺序申请锁，最实用）
3. **避免** — 银行家算法（需要知道最大需求，不实用）
4. **检测** — 构建锁申请图，DFS 检测环（Linux lockdep）

---

### 2.9 并发 Bugs — 97% 是原子性和顺序性

**实证研究**（Shan Lu, ASPLOS'08）：四个大型软件的并发 bug 中，除死锁外 97% 可归为：
- **原子性违背（AV）**：忘记上锁。代码块本应原子执行，中间被插入了。
- **顺序性违背（OV）**：事件未按预期顺序发生。比如先 check 后 set 之间被打断。

**并发工具不能保证正确——你得正确使用它们。**

**检测工具**：
- AddressSanitizer：非法内存访问（`-fsanitize=address`）
- ThreadSanitizer：数据竞争检测（`-fsanitize=thread`），基于 happens-before 关系

> 对应考纲：进程和线程、上下文切换、fork/execve/exit、调度算法、虚拟内存、TLB、多级页表、缺页异常、页面置换算法

### 3.1 调度 — 多个进程争 CPU，谁先跑？

**问题**：一个 CPU，多个进程等着跑。选谁？怎么选？

**调度的时机**（操作系统什么时候重新做决定）：
- 发生系统调用（fork、exit 等）
- 当前进程阻塞（等 I/O、等子进程）
- 发生中断（I/O 完成中断、时钟中断）

**机制与策略分离**：机制 = 上下文切换（怎么换），策略 = 选哪个进程（选谁）。两者独立设计和演进。

**调度评价指标**：
| 指标 | 含义 | 目标 |
|------|------|------|
| CPU 利用率 | CPU 忙的时间占比 | 越大越好 |
| 吞吐量 | 单位时间完成的进程数 | 越大越好 |
| 周转时间 | 进程从到达到完成的总时间 | 越小越好 |
| 等待时间 | 进程在就绪队列的时间 | 越小越好 |
| 响应时间 | 从提交到第一次执行的时间 | 越小越好 |
| 公平性 | 同优先级进程获得的时间 | 尽量相等 |

**重点算法**：

**① FCFS（先来先服务）**：按到达顺序，简单。问题：护航效应——长进程挡在短进程前面，平均等待时间被拉高。

**② SJF（最短作业优先，非抢占）**：执行时间最短的优先。**平均等待时间最优**（数学上可证明）。问题：不公平（长进程可能饿死），需要预知执行时间。

**③ SRTF（最短剩余时间优先，抢占版 SJF）**：新进程到达时，如果其执行时间比当前进程剩余时间更短，就抢占。每次选择剩余时间最短的。

**④ RR（时间片轮转）**：每个进程固定时间片，用完回到队尾。响应时间好，但周转时间差（频繁上下文切换）。时间片太大 → 退化为 FCFS，太小 → 切换开销占比过高。

**⑤ 优先级调度**：每个进程有优先级，高优先级先跑。问题：低优先级可能饿死。解决：老化（定期提升优先级）。

**⑥ MFQ（多级反馈队列）**：现代 OS（Windows/Mac/Linux）实际使用的策略。核心机制：
- 多个优先级的队列，高优先级队列时间片短，低优先级队列时间片长
- 新进程入最高优先级
- 用完时间片 → 降一级（更长的时间片）
- I/O 阻塞的没用完 → 留在当前级
- 自然结果：I/O 密集留高层（短时间片，频繁跑），CPU 密集沉底层（长时间片，偶尔跑）
- 愚弄方法：时间片快完时故意 sleep → 不降级。防御：追踪长期 CPU 使用量

**⑦ CFS（完全公平调度器）**：Linux 默认调度策略。用红黑树按虚拟运行时间排序，每次选运行时间最少的进程。O(1) 选择，O(log n) 插入。

**优先级反转**（考试可能考）：高优先级进程因为等低优先级进程释放锁而被中优先级抢占，导致高优先级饿死。解决：优先级继承（持有锁的低优先级进程临时提升到等待者的优先级）。

### 3.2 虚拟内存 — 程序以为独占 4GB

> 详细内容已在 Q10 中讲述，此处仅补充 PPT 中的核心概念脉络。

**从物理地址到虚拟地址**：早期程序直接用物理地址 → 一个程序 bug 搞垮其他程序 + OS。后来引入 base/bound 寄存器做保护（每个进程有自己的 base+bound），但依然不够——程序知道物理地址，不安全。

**虚拟内存的四个关键能力**：
1. **保护**：不同进程的映射函数值域不相交
2. **动态重定位**：进程的物理地址可以在运行时变化（不是编译时）
3. **数据共享**：不同进程的不同虚拟地址映射到同一物理地址
4. **连续空间假象**：虚拟地址连续 ≠ 物理地址连续

**TLB（Translation Lookaside Buffer）**：页表在内存里，每次访存要先查页表（至少一次额外内存访问）→ 太慢。TLB 是 CPU 内部的硬件缓存，缓存最近使用的虚拟页→物理框映射。命中时几乎零延迟。

**缺页异常（Page Fault）**：访问的虚拟页不在物理内存 → MMU 触发异常 → OS 从磁盘读入 4KB → 更新页表 → 重试指令。缺页率 p 的有效访问时间 = (1-p)×访存时间 + p×缺页开销。即使 p 只有 0.001，性能已下降 40 倍。

**页面置换算法**：内存满了，需要换出哪个页？
- Optimal（理论最优，不可实现，用作基准）
- FIFO（可能 Belady 异常：分配更多帧反而更多缺页）
- LRU（最近最少使用，近似最优但实现复杂）
- Clock（LRU 的近似，用访问位实现，实际最常用）

**COW（写时复制）**：fork 时父子共享同一物理页，标为只读。任一方写入时才触发缺页，复制一份。避免全量拷贝的巨大开销。

## 第四部分：持久化 — 数据在断电后还能活下来

> 来源：PPT 13（设备管理）+ PPT 14（文件系统）
> 对应考纲：软链接/硬链接、inode 多级索引、磁盘原理
> 注：设备管理/驱动程序不考；日志文件系统不考

### 4.1 文件系统 — 磁盘上的"图书馆"

> inode、多级索引、硬链接/软链接、文件描述符已在 Q11 详述，此处仅补充 PPT 中的关键额外概念。

**文件系统解决的四个问题**：命名数据（文件和目录）、访问与保护、磁盘空间管理、可靠性。

**目录的本质**：一个特殊文件，存储 ⟨文件名, inode号⟩ 的映射表。路径解析就是逐级查目录的过程：从根目录 inode → 找到 `usr` → 再找 `ast` → 再找 `mbox`。

**文件组织形式（四种）**：
1. 连续分配：文件占据连续磁盘块，只需记住起始块和块数。简单但外部碎片严重。
2. 链表分配：每块指向下一块。无碎片但随机访问慢（需要遍历链表）。
3. FAT：指针集中放表里。随机访问只需查 FAT（在内存），减少 I/O。大磁盘 FAT 本身大。
4. 索引式分配（inode 多级索引）：在用的才建索引，大部分小文件直接用 12 个直接指针。

**FFS（快速文件系统）**：原始 Unix 文件系统只利用了约 2% 磁盘带宽——数据随意放置，寻道时间占比过高。FFS 用块组（柱面组）将相关数据放在一起：同一目录的文件放同一柱面，数据块靠近其 inode。现代 SSD 不需要（随机=顺序）。

**磁盘布局**：Boot Block | Superblock | 空闲管理(inode bitmap + data bitmap) | inode 表 | 数据区。Superblock 存文件系统元信息（inode 数量、数据块数量等），mount 时读入。

## 补充 · 管程实现读者-写者问题（经典考点）

**管程** = 互斥锁（自动） + 共享变量 + 条件变量。进入管程自动拿锁，离开自动放锁。条件变量：`cv.wait()` 释放锁+阻塞；`cv.signal()` 唤醒一个等待者。

**题目要求**：① 最多 K 个读者同时读 ② 只有一个写者 ③ 写者优先（写者来后不许新读者）④ 写者等当前读者全部离开。

**管程设计**（关键：找共享状态 → 写条件 → 建函数）：

```
Monitor ReaderWriter {
    int read_count = 0;
    bool write_active = false;
    bool write_waiting = false;
    condition can_read, can_write;

    void reader_enter() {
        while (write_active || write_waiting || read_count >= K)
            can_read.wait();
        read_count++;
    }
    void reader_exit() {
        read_count--;
        if (read_count == 0) can_write.signal();  // 最后离开的唤醒写者
        can_read.signal();                        // 空出位置给其他读者
    }
    void writer_enter() {
        write_waiting = true;                     // 我来，新读者停！
        while (write_active || read_count > 0)
            can_write.wait();
        write_active = true;
        write_waiting = false;
    }
    void writer_exit() {
        write_active = false;
        can_read.signal();                        // 先通知读者
        can_write.signal();                       // 也可能通知写者
    }
}
```

**写者优先的体现**：`writer_enter()` 先把 `write_waiting=true`，后续读者在 while 条件里看到 `write_waiting==true` 直接阻塞。已在读的不受影响（已经进管程了）。

## 6.25 · 2022-2023 往年卷刷题记录

### Q12 · 直接 syscall vs API 封装 🟢
- **来源**：2023 卷 Q1(五)
- **问题**：能否绕过 `fork()`/`printf()` 直接发系统调用？
- **答案**：可以（汇编 `syscall` 指令直接发），但三个弊端：① 代码复杂度暴增、可读性差 ② 不同 CPU 架构系统调用约定不同（x86 用 rax/rdi，ARM 用 x8/x0）③ 不同 OS 系统调用号不同（Linux 的 write=1，macOS 不同）。API = 可移植的抽象层。
- **回看**：API 封装了"这个平台上系统调用号是几、参数放哪个寄存器"。

### Q13 · 存储管理技术全览 🟡
- **来源**：2023 卷 Q2(三)
- **五种技术碎片对比**：

| 技术 | 内碎片 | 外碎片 | 核心原因 |
|------|--------|--------|---------|
| 固定分区 | ✅ | ✗ | 分区大小固定，进程用不满 → 浪费在块内 |
| 可变分区 | ✗ | ✅ | 要多少给多少，但分配/释放产生碎片空洞 |
| 分页 | ✅ | ✗ | 框大小统一，最后一页用不满（平均半页/进程） |
| 分段 | ✗ | ✅ | 段大小可变，同可变分区 |
| 伙伴系统 | ✅ | ✅ | 2的幂次分配 → 内碎片；分配释放仍有外碎片 |

- **回看**：可变分区仅外碎片；伙伴系统两者都有；固定分区和分页仅内碎片。答案给的是伙伴系统和固定分区。

### Q14 · XCHG 与自旋锁设计 🟢
- **来源**：2023 卷 Q3
- **核心**：软件 flag 失败因为"看"和"写"是两个操作。XCHG 原子交换——同时把 1 贴门上、取回旧值。旧值=0 → 抢到了；旧值=1 → 别人在用，继续转。
- **完整设计链**：软件flag → XCHG自旋锁 → ticket lock(排队) → futex两阶段锁 → 内核自旋锁(关中断)
- **代码**：
```c
void spin_lock() { int key=1; while(1){ XCHG(key, lock); if(key==0) break; } }
void spin_unlock() { lock = 0; }
```

### Q15 · 死锁避免决策 🟢
- **来源**：2023 卷 Q4(二)
- **决策时机**：每次资源申请时。若批准后系统进入不安全状态 → 拒绝。
- **需要信息**：① 各进程当前持有资源 ② 系统资源总数 ③ 各进程对资源的最大需求（最难获得，现实中不实用——所以银行家算法不实用）
- **判断逻辑**：假设批准 → 更新状态 → 检查是否存在安全序列（逐步回收资源）

### Q16 · 页表综合计算 🟡
- **来源**：2023 卷 Q5
- **关键点**：
  - 反置页表按物理框索引（不是虚拟页），表项需存(pid, 页号)。省内存但需遍历搜索。
  - 访问位=0 修改位=1：OS 定期清零访问位，而修改位在写回磁盘前一直保持
  - CALL 指令涉及 2 次内存访问（压栈+取值），可能引发多次缺页。锁定位机制让置换算法跳过正在用的页。
  - NRU 算法优先淘汰访问位=0 且修改位=0 的页（其次是访问位=0 修改位=1，等等）

### Q17 · inode + fd + dup 综合 🟡
- **来源**：2023 卷 Q6
- **256 的来源**：1KB块 ÷ 4B指针 = 256 个指针（不是32位的问题，是块大小决定的）
- **fd 由"最小可用整数"决定**：0/1/2 被 stdin/stdout/stderr 占用，第一个 open 返回 3
- **fork 后父子共享文件偏移**：父进程 lseek 改了偏移，子进程从新位置继续读。子进程本要 600 字节但父进程读到 12200，只剩 400 字节可读 → 返回 400
- **逻辑块→物理块**：直接指针块 1 次 I/O，间接指针块 2 次（先读间接块再读数据块）。已缓存的不重复读。

## 公式

| 公式 | 用在哪 |
|------|--------|
| 周转时间 = 完成 - 到达 | 调度计算 |
| 等待时间 = 周转 - 执行 | 调度计算 |
| 页内偏移位数 = log₂(页大小) | 内存计算 |
| 页号位数 = 地址位数 - 偏移位数 | 内存计算 |
| 单级页表大小 = 2^页号位数 × PTE大小 | 内存计算 |
| 一个间接块指针数 = 块大小 ÷ 指针大小 | 文件系统 |
| 直接指针容量 = N × 块大小 | 文件系统 |
| 单间接容量 = (块/指针) × 块大小 | 文件系统 |
| 双间接容量 = (块/指针)² × 块大小 | 文件系统 |
| 有效访问时间 = (1-p)×访存时间 + p×缺页开销 | 缺页性能 |

## 代码模板

**生产者-消费者信号量方案**：P(empty) → P(mutex) → 操作 → V(mutex) → V(full)。**先 P 条件信号量，再 P 互斥锁！**

**fork+exec 模板**：fork() → 子进程返回 0（调用 execve），父进程返回子 PID（调用 wait）。

**信号量初值**：问"一开始谁能直接过？"→ 初值 = 能过几个；"一开始谁要等？"→ 初值 = 0。

## 易错点

- 周转 ≠ 等待！周转=完成-到达，等待=周转-执行
- 死锁四个必要条件：互斥 + 持有并等待 + 不可抢占 + 循环等待
- cond_wait 必须在 while 循环（不是 if）
- 信号量 V 操作 = 释放资源，P 操作 = 申请资源
- 硬链接 = inode 号别名，软链接 = 路径名别名
- execve 保留：fd、环境变量、PID、cwd、信号设置（SIG_IGN）
- fork 返回两次：父进程返回子PID，子进程返回0
