## 6.20 · 模块二 需求文档化 (02-05)

### Q17 · 需求验证 vs 需求确认
- **来源**：02-05-需求文档化验证与冲突检测
- **弱项**：🟡 方向对但表述反了
- **答案**：验证（Validation）= 做对了产品吗？（面向用户需要）；确认（Verification）= 产品做对了吗？（面向规格标准）
- **回看**：Validation（用户） vs Verification（规格）— V&V

### 💡 本日关键洞察 · 用户需求 vs 功能需求的边界
- **问题**：用户需求「使用者可以预约图书」和功能需求「系统应提供图书预约功能」写起来很像

- **回看**：考试时用户需求用「用户可以…」，功能需求用「系统应支持/记录/验证…」

## 6.22 · 补充-设计模式

### Q17 · 可修改性的实现手段
- **来源**：补充-设计模式 §1
- **弱项**：🟡 答成"解决方案的抽象模板" — 混淆了定义与手段
- **答案**：核心手段是**接口与实现的分离**（interface+实现类、继承、组合三种方式）。设计模式是"解决方案的抽象模板"只是定义，不是手段。
- **回看**：四种模式本质都是接口与实现分离的不同运用

### Q18 · 策略模式为什么用组合而不是继承
- **来源**：补充-设计模式 §3 + 难点突破§1
- **弱项**：🟡 能说"多态"，漏两条核心理由
- **答案**：① **依赖倒置** — Context 依赖 Strategy 接口而非具体实现；② **运行时动态切换** — `setStrategy()` 随时换，继承只能在 `new` 时选定；③ 组合支持策略队列实现"n 选多"
- **回看**："避免暴露接口"混淆到迭代器模式了——迭代器屏蔽集合内部结构，策略模式不涉及这个

### Q19 · 抽象工厂"组合爆炸"
- **来源**：补充-设计模式 §4 + 难点突破§2
- **弱项**：🟡 直觉对，表述模糊
- **答案**：组合爆炸 = 普通工厂为每种产品组合建一个类 → 工厂数 = 引擎种类×轮胎种类×车身种类（乘积爆炸）。抽象工厂：工厂接口为每种产品类型定义一个 `createXxx()`，一个具体工厂=一个产品族。限制：新产品**类型**难增加（要改接口），但新**产品族**容易加。
- **回看**：说"产线难更改"对，但要精确到"新产品类型难增加"

### Q20 · 设计场景→设计原则映射
- **来源**：补充-设计模式 §🔥 新考法
- **弱项**：🔴 文档转换器场景 — ① 漏列设计原则（应列 DIP/OCP/SRP/面向接口编程）；② 误列 LSP（场景无继承，不适用）；③ 说"增加格式要修改接口"——恰好反了
- **答案**：策略模式新增格式只需加 ConcreteConverter 类，Converter 接口和 Context 都不动。这是 OCP 的体现，也是 DIP 的结果。
- **回看**：核心考试能力——看到场景→说出原则→推出设计。新增=加类不动接口不动Context。

### Q21 · DIP 在类图/包图中的体现
- **来源**：03-03 §5 + 补充-设计模式 + 04-02 速查表
- **弱项**：🟡→🟢 深讲后已纠正
- **答案**：类图=依赖箭头指向接口(虚线+鱼骨)，不指向具体类。包图=接口归高层包所有（不独立成层），展示层→逻辑层接口(VO)←逻辑层实现→数据层接口(PO)←数据层实现。箭头：实现=实线+空心三角，依赖=虚线+鱼骨。
- **回看**：顺序图不受 DIP 影响（展示运行时交互，不展示编译期依赖）

## 6.22 · 补充-代码设计 + 软件构造

### Q22 · TDD 为什么必须先写失败测试
- **来源**：补充-软件构造 §3 (TDD)
- **弱项**：🟡 答"试探边界值"——混淆到测试用例设计方法了
- **答案**：核心原因是先写测试定义"什么算成功"——测试本身就是规格。如果先写代码再补测试，测试只能验证"代码做了什么"而非"代码应该做什么"。Red 阶段测试失败证明：① 功能确实缺失；② 测试框架有效。
- **回看**：边界值/等价类 = 测试用例设计方法（黑盒），TDD Red = 规格驱动开发（流程）。两个维度，不混。

### Q23 · 契约式设计 vs 防御式编程的关系
- **来源**：补充-代码设计 §3
- **弱项**：🟡 方向对，关系表述模糊
- **答案**：契约式设计 = "我承诺"（前置/后置/不变式定义方法契约）；防御式编程 = "我不信你"（主动检查输入/外部依赖/返回值）。契约定义信任边界，防御在边界上设关卡。异常和断言是实现两者的技术手段。
- **回看**：不是"都依赖上下文"，是互补关系——一个定义边界，一个守卫边界

### Q24 · switch/case ≠ 表驱动编程
- **来源**：补充-代码设计 §2 复杂决策简化
- **弱项**：🔴 说"用 case"——switch/case 只是语法糖，本质还是 if-else 链（条件与行动绑定）
- **答案**：表驱动 = 数据与逻辑分离。用数组/Map 存阈值和对应行动，循环一次搞定。新增条件只加数据不改变控制结构。switch 新增 case 要改控制结构——没有分离。
- **回看**：表驱动核心 = 数组+循环替代 if-else 链。if-else 链→switch→表驱动，越往后越解耦。

## 6.22 · 05-01 软件测试

### Q25 · Fault/Error/Failure 中文术语对应
- **来源**：05-01-软件测试 §2
- **弱项**：🟡 举例方向对，中文术语对应反了（说"错误=缺陷=Fault"）
- **答案**：Fault=缺陷（代码中隐藏的bug），Error=错误（Fault激活后的中间不稳定状态），Failure=失效（用户可见的失败表现）。巧记：Fault=炸弹→Error=引信燃烧→Failure=爆炸。
- **回看**：因果链 = Fault → Error → Failure，可递归迭代

### Q26 · 语句/条件/路径覆盖的用例数量关系
- **来源**：05-01-软件测试 §6
- **弱项**：🔴 回答 4/9/9 — 语句覆盖是最弱标准，不可能比路径覆盖需要更多用例
- **答案**：覆盖强度 语句<条件<路径；用例数量 语句≤条件≤路径。2个决策点(不嵌套)：语句覆盖≥2，条件覆盖=2，路径覆盖=4(=2²)。路径可能爆炸(嵌套/循环时远超2ⁿ)。
- **回看**：记死顺序——语句<条件<路径，用例数量方向一致。漏了 s3/s5 就不叫语句覆盖。

## 6.23 · 2020卷做题

### Q27 · 用例数量判断 + 参与者范围
- **来源**：2020卷 Q2(1) + 02-03 §7
- **弱项**：🔴 两处错误 — ① 认为 3 个用例（多算了一个"设置再订货规则"）② 认为用例 2 的参与者应包括仓库经理
- **答案**：**2 个用例**。① 手工创建询价单（Actor=采购人员）；② 自动生成询价单（Actor=库管员）。"设置再订货规则"不是这里的用例——题干说"在先前的步骤中已设置"，它是前置条件，仓库经理在更早时间以不同目标完成。**参与者只包括当前交互中直接与系统对话的人**——仓库经理设完规则就退场了，不参与"运行排程→系统生成询价单"的交互。
- **关键理解**：用例划分标准 = **参与者的一次完整业务目标**，不是"功能模块"。把 CRUD 拆成增删改查 4 个用例是经典错误（教师 PPT 点名批评）。判断公式：问自己"这个人做完这件事之后，是否有任务达成的满足感？"
- **回看**：2020卷 Q2(1) 6分 = 用例数量(2分) + Actor正确(2分) + 交互流程(2分)

### Q28 · 需求分类辨析：功能需求 vs 数据需求
- **来源**：2020卷 Q2(2) + 02-01 §7
- **弱项**：🟡 第二句错判为"约束"——方向对但分类不精确
- **答案**：① "系统必须提示错误" = **功能需求**（描述了系统行为——做什么）；② "收入金额中不能含有非数字字符" = **数据需求**（只定义了数据格式规则，没说系统怎么响应）。判断口诀：**说系统"做什么"→功能需求；说数据"长什么样"→数据需求。**"约束"在软工分类中通常指技术/设计约束（如"必须用Java"），不指数据规则。
- **回看**：给一句话分类时先找动词——有"系统必须…"→功能需求；有"数据必须满足…"→数据需求

### Q29 · 概念类图：名词分析法 + 关联类型判断
- **来源**：2020卷 Q3 + 02-04 §3
- **弱项**：初次画概念类图·需逐个确认
- **答案**：7 个概念类（Employee/WarehouseManager/WarehouseKeeper + ReorderRule + Schedule + Inventory + SalesOrder + PurchaseInquiry + Product）。关联类型关键判断：① Inventory 是 Product 的**组合**（库存脱离产品无意义）② Schedule 读取/检查其他类 → **依赖**（虚线，临时使用不长期持有）③ 人员之间 = **泛化**（WarehouseManager/WarehouseKeeper 继承 Employee）④ 单据包含产品 = **聚合**（产品可脱离单据存在）。不画方法！只画属性和关系。
- **回看**：概念类图三步 = 名词提取→筛选→画图。筛选用五准则（排除纯属性/实现概念/外部系统/含糊名词/无状态无行为）。关联类型口诀：长期持有=关联·整体部分=聚合/组合·临时使用=依赖·is-a=泛化

### Q30 · 物理包图 vs 逻辑包图
- **来源**：2020卷 Q4(1) + 复习提纲第九章例题 + 教师答疑（期末相关.txt §包图要点）
- **弱项**：🔴 课 件没单独讲物理包图，不知道和逻辑包图的区别
- **答案**：逻辑包图 = 三层 + PO/VO + 接口 + 依赖方向（回答"代码怎么分模块"）。物理包图 = 逻辑包图 + **客户端/服务端分界** + **HTTP/REST 标注** + 前端 html/css/js 放客户端（回答"代码跑在哪台机器上"）。画法四步：① 画分界线标部署位置 ② 客户端画 view/ + 前端文件 ③ 服务端画逻辑层+数据层+VO/PO+接口 ④ 标 HTTP·REST API·JSON(VO)。接口符号：实现=实线空心三角，依赖=虚线鱼骨。
- **回看**：考试只说"画包图"默认画逻辑包图；明确说"物理包图"或"体现跨网络"才加客户端/服务端分界。4+1 View 对应：逻辑包图→逻辑视图，物理包图→开发+物理视图

### Q31 · 策略模式：变更应对 + 类图 + 顺序图
- **来源**：2020卷 Q5 + 补充-设计模式 §3
- **弱项**：首次做策略模式综合题
- **答案**：① **变更类型**说"业务规则/算法变更"而不是笼统的"需求变更"——旧规则是简单阈值判断，新规则是多区间映射+公式计算，且参数后续还会变。② **应对**=策略模式封装每种算法为独立策略类，调用方依赖接口不依赖具体类（DIP），阈值参数做成可配置（OCP：新增策略不改调用方）。③ **类图关键**：ReorderStrategy 接口 + DeliveryTimeStrategy（内部 List<RuleEntry> 循环匹配区间）+ ActivityBasedStrategy（公式：activityStock×scaleMultiplier+baseStock）+ OrderContext（传参）。④ **顺序图关键**：订货Service→策略接口（不直接到具体策略）→活动/销量获取数据→返回计算值→创建订货单。
- **回看**：策略模式 = DIP + OCP + 组合复用。策略模式类图必画接口在上、策略实现在下、调用方依赖接口（虚线箭头）

### Q32 · 印记耦合 vs 控制耦合
- **来源**：2020卷 Q6 + 教师答疑（期末相关.txt 控制耦合+印记耦合详解）
- **弱项**：首次独立识别耦合类型
- **答案**：① `valid_month(date d)` 只用了 `d.month` 却收整个 date 对象 → **印记耦合**。改法：参数改为 `int month`。② `valid(String s, int type)` 用 type 当 flag，switch-case 分支 → **控制耦合**。改法：拆成 `validString(s)` / `validDate(s)` 两个独立方法，消除开关参数。记忆：印记耦合=传多了（冰箱里只要鸡蛋），控制耦合=传 flag（遥控器一个按钮全靠按几次区分功能）。
- **回看**：2020 卷 Q6 共 10 分，每题 5 分 = 正确命名耦合类型(2分) + 说清原因(1分) + 给出修改代码(2分)。教师说了耦合不深考，但基本概念要会。

### Q33 · DAO + 抽象工厂（为什么不是策略模式？）
- **来源**：2020卷 Q7 + 补充-设计模式 §4
- **弱项**：🔴 认为 DAO 切换数据库可以用策略模式——混淆了两者的适用场景
- **答案**：**抽象工厂模式**。策略模式管**一个行为**有多种做法（如付款：支付宝 vs 微信，只换一个动作）。抽象工厂管**一族对象**需要配套创建——UserDAO + ProductDAO + OrderDAO 三个必须同一品牌（都连 MySQL 或都连 SQL Server），不能混搭。策略模式换数据库要手动改三行且容易漏一行→混搭炸了；抽象工厂只改一行 `new MySQLDAOFactory()` → `new SQLServerDAOFactory()`，所有 DAO 自动配套。**判断口诀**：换一个=策略，换一窝=抽象工厂。
- **设计原则**：DIP（业务层依赖 DAO 接口）+ OCP（切数据库不改业务层）+ 面向接口编程 + 单一职责
- **回看**：DAO 概念类图 = Factory 接口在上 → MySQL/SQLServer 工厂实现在下 → 每个工厂创建对应 DAO 实现。业务逻辑 Service → 依赖(虚线) → DAOFactory 接口

### Q34 · 策略模式 vs 表驱动：什么时候用哪个
- **来源**：2020卷 Q5 vs Q8 对比 + 补充-代码设计 §2
- **弱项**：🟡 同一套订货规则，Q5 用策略模式 Q8 用表驱动，为什么不统一？
- **答案**：策略模式 = 不同**算法/行为**（交货期计算 vs 活动公式计算，两套完全不同的计算逻辑）。表驱动 = 不同**数据/参数**（同一套查表逻辑，天数→备货量只是阈值不同）。判断口诀：**不同算法=策略模式，不同参数=表驱动。** Q8 本质上就是天数→销量的映射，查表就够了，策略模式是过度设计。表驱动核心 = 数组/Map 存阈值和对应行动，循环一次搞定，新增规则只加数据不改控制结构 → 见 Q24。
### Q35 · 人机交互点评答题模板
- **来源**：2020卷 Q9 + 03-04-人机交互设计 + 教师答疑（期末相关.txt · "有道理就得分"）
- **弱项**：初次做 HCI 点评题
- **答案**：十条可用的原则：① 一致性（同功能同位置）② 反馈（操作后有响应·>15s破坏性）③ 简洁性（不堆砌·7±2）④ 防止错误（灰显+禁非法输入+危险确认）⑤ 易恢复（撤销/重做）⑥ 减轻记忆负担（识别>回忆·有意义默认值）⑦ 用户控制 ⑧ 菲茨定律（大按钮+边缘放常用操作）⑨ 出错信息四原则（清晰+精炼+建设性+不责备）⑩ 差异化设计（新手vs专家）。答题模板：指出原则名→指页面具体元素→解释为什么好/不好。凑 3-5 条，有道理就得分。
- **回看**：教师原话"只要你能说有道理，它都是可以对的"。不背文字，用常识判断。2020 卷 Q9 卖价单点评 5 条示例：一致性✅ / 错误反馈⚠️ / 菜单导航✅ / 默认值✅ / 缺撤销❌

### 🔴🔴 最高重点：类设计原则（教师原话 "十来个都会考的"）

| # | 原则 | 一句话 | 违反示例 |
|---|------|--------|---------|
| 1 | **单一职责 SRP** | 一个类只干一件事 | 上帝类：`Employee` 既算工资又存数据库又发邮件 |
| 2 | **开闭原则 OCP** | 对扩展开放，对修改关闭 | 新增格式要改 `switch(type)` → 应新增类不改旧代码 |
| 3 | **里氏替换 LSP** | 子类必须能完全替换父类 | `Stack extends Vector` → Stack 暴露了不该有的 `insertElementAt` |
| 4 | **依赖倒置 DIP** | 依赖抽象不依赖具体 | `BookService` 直接 `new MySQLBookDAO()` → 应依赖 `BookDAO` 接口 |
| 5 | **接口隔离 ISP** | 接口小而精，拒绝肥接口 | `Worker` 接口有 `work()` `eat()` `sleep()` — 机器人被迫实现 `eat()` |
| 6 | **迪米特法则 LoD** | 只和直接朋友说话 | `a.getB().getC().doSomething()` → 链式调用穿透多层 |
| 7 | **合成复用 CARP** | 组合优先于继承 | 策略模式：`Context` 组合 `Strategy` 接口，不用继承每个具体策略 |
| 8 | **面向接口编程** | 变量声明用接口类型 | `ArrayList<Book> books` → 应 `List<Book> books = new ArrayList<>()` |
| 9 | **信息隐藏** | 隐藏实现细节，只暴露接口 | 所有字段 `public` → 应 `private` + getter/setter |
| 10 | **KISS** | Keep It Simple, Stupid | 5 行能搞定的写成 50 行抽象框架 |
| 11 | **DRY** | Don't Repeat Yourself | 3 个方法里都有相同的日期格式校验代码 |
| 12 | **YAGNI** | You Ain't Gonna Need It | 预留"未来可能用"的接口和方法 → 删掉 |

**记忆口诀**：S（SRP）O（OCP）L（LSP）I（ISP）D（DIP） + CARP + LoD + 接口编程 + 信息隐藏 + KISS + DRY + YAGNI

**SOLID 五兄弟**：SRP / OCP / LSP / ISP / DIP — 一定全会考到，可能考其一或组合考多选。考试常见问法："这段代码违反了什么原则？请修改。"

### 🔴 重点：GRASP 九模式

| # | 模式 | 解决的问题 | 一句话 |
|---|------|-----------|--------|
| 1 | **控制器** | 谁来处理系统事件？ | UI 层之外的第一层对象（如 `LoanController`），负责协调用例流程 |
| 2 | **信息专家** | 谁拥有完成职责所需的信息？ | 数据在哪，方法就在哪——`Book` 自己计算是否可借 |
| 3 | **创建者** | 谁负责创建对象？ | B 包含/聚合/记录/密切使用 A → B 创建 A（如 `Loan` 创建 `LoanItem`） |
| 4 | **低耦合** | 如何减少依赖？ | 类之间的依赖越少越好——改了 A 不需要改 B |
| 5 | **高内聚** | 如何让类职责聚焦？ | 一个类的所有方法都围绕同一个目标——不乱塞不相关的方法 |
| 6 | **多态** | 如何按类型变换行为？ | 用接口+多实现替代 if-else/switch 按类型分支 |
| 7 | **纯虚构** | 行为不属于任何实体类时怎么办？ | 创造一个人工类来装这个行为（如 `LoanService`） |
| 8 | **间接性** | 如何让两个模块解耦？ | 在它们之间加一个中介（如 `BookDAO` 隔离业务逻辑和数据库） |
| 9 | **保护变化** | 如何隔离不稳定的部分？ | 把预计会变的东西封装在一起，变化不扩散 |

> 课件重点讲前 5 种（控制器/信息专家/创建者/低耦合/高内聚），考试给场景→说该用哪个 GRASP + 为什么。

### 🟡 次重点：耦合完整概念（⚠️ 不深考，但基本概念要会 → 见 Q32）

| 耦合类型 | 一句话 | 举例 | 好坏 |
|----------|--------|------|------|
| **无耦合** | 两个模块没有任何关系 | 完全独立的两个工具类 | 🟢 最好 |
| **数据耦合** | 只通过简单参数（int/String）传递数据 | `calculate(int a, int b)` | 🟢 好 |
| **印记耦合** | 传了整个对象，但只用到其中一两个字段 | `validMonth(date d)` 只用 `d.month` | 🟡 可接受 |
| **控制耦合** | 传 flag/type 参数控制内部 switch-case 走不同分支 | `valid(String s, int type)` + `switch(type)` | 🟠 需改进 |
| **公共耦合** | 多个模块共享全局变量，一方改了另一方受影响 | 多个类共用一个 `public static int count` | 🔴 差 |
| **内容耦合** | 一个模块直接修改另一个模块的内部数据 | `a.b.field = 5` (a 直接改 b 的私有字段) | 🔴 最差 |

**印记耦合的改法**：参数从整个对象改为只传需要的字段（`validMonth(date d)` → `validMonth(int month)`）。

**控制耦合的改法**：拆成多个独立方法消除开关参数（`valid(s, type)` → `validString(s)` + `validDate(s)`），或用多态替代 switch。

> 耦合从好到差：无耦合 → 数据耦合 → 印记耦合 → 控制耦合 → 公共耦合 → 内容耦合
