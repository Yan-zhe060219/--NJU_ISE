## 三、各模块考点详析

### 模块一：软件工程基础

- 基本概念需要**明白**，但考试不会考太深
- 更多是理解层面，不太会出深入问答

### 模块二：需求工程 ⭐ 重点

| 考点 | 要点 | 重要度 |
|------|------|--------|
| **需求层次性** | 业务需求 → 用户需求 → 系统需求（三层递进） | 🔴 必考 |
| **需求分类** | 功能性需求 vs 非功能性需求 | 🔴 必考 |
| 需求获取 | 目的是什么，获取什么 | 🟡 |
| **用例建模** | 文本描述 + 用例图，都要会 | 🔴 必考 |
| 用户故事 | 表达用户需求的方式 | 🟡 |
| **系统顺序图** | Actor 与系统之间的交互 | 🔴 必考 |
| **概念类图** | 类 + 属性，**没有方法** | 🔴 必考 |
| 需求文档化 | 了解标准文档结构，不会让写完整规格说明 | 🟡 |

**关键理解**：
- 业务需求：从用户角度出发，可度量的业务指标（提升效率/节省成本/缩短时间/增加收益）
- 用户需求：用户能用系统做什么（用例、用户故事来表达）
- 系统需求：规格化，强调交互细节，比用户需求更详细明确，是迭代产生的交付唯一产物

### 模块三：体系结构设计 ⭐ 重点

| 考点 | 要点 | 重要度 |
|------|------|--------|
| 体系结构基本概念 | 构建、接口、连接件 | 🔴 |
| **体系结构风格** | 主程序/子程序、面向对象、**分层**、**MVC** | 🔴 必考 |
| **包图** | 分层表达，必须画出 PO/VO 和接口 | 🔴 必考 |
| 4+1 View | 逻辑视图（包图表达） | 🟡 |
| 构建接口 | 供接口（提供什么）+ 需接口（需要什么） | 🟡 |

**包图要点**：
- 画出展示层、逻辑层、数据层
- 展示层 ↔ 逻辑层接口（VO）
- 逻辑层 ↔ 数据层接口（PO）
- 层间依赖方向：上层依赖下层（依赖倒置后都依赖接口）
- 接口表示：实现用实线+空心三角，依赖用虚线+鱼骨箭头
- 层内可简化（考试时间有限），但要知道真正做项目时层内依赖也很重要

**VO vs PO**：
- **VO (Value Object)**：展示层与逻辑层交互，只返回所需内容（类似避免印记耦合的思想）
- **PO (Persistent Object)**：数据层与逻辑层交互，代表持久化对象
- **DAO**：ORM 映射，关系数据库记录 ↔ 面向对象

### 模块四：详细设计 ⭐ 重点

| 考点 | 要点 | 重要度 |
|------|------|--------|
| **GRASP 模式** | 控制器、信息专家、创建者、低耦合/高内聚、多态、纯虚构、间接性、保护变化 | 🔴 必考 |
| **类的设计原则** | 约10+个原则，**一定会考**（可能考其一，可能组合考多个） | 🔴🔴 最高 |
| 模块化与信息隐藏 | 基本概念 | 🟡 |
| 内聚和耦合 | **不是重点**（讲得弱），但需了解基本概念 | ⚪ 降级 |

**内聚和耦合补充**（老师特别讲解，理解即可，考试不考）：
- **控制耦合**：传入参数类似 flag，方法内部 switch-case 根据参数做不同事 → 上下游都需知道这个约定 → 耦合高。改进：用多态替代 if-else
- **印记耦合**：传入整个对象，但实际只需要其中少量字段（如 sendEmail 只需要 email address，却传了整个 Employee）
- 内聚：偶然内聚最差；逻辑/时间/过程内聚有时不可避免

## 四、设计模式 — 今年新考法 🔥

> 今年设计模式的考法做了重大调整，**不再是往年那种单独考某个设计模式**。

**新形式**：
- 分解为多个小问题
- 给出充分的引导材料
- 诱导学生根据学过的设计原则来回答
- 考察**扩展能力**：学了一些模式后，能否应用到新场景
- **不需要**提前背诵其他设计模式
- 甚至不要求写出具体是什么设计模式的名字
- 「考得活一些」

**核心能力**：用学过的设计原则（类的设计原则）去分析和设计，而非机械套用模式名。

## 五、图类总览 — 贯穿全流程

| 阶段 | 图名 | 关键要点 |
|------|------|----------|
| 需求 | **用例图** | Actor + 用例 |
| 需求 | **系统顺序图** | Actor 与系统的交互 |
| 需求 | **概念类图** | 类 + 属性，**无方法** |
| 体系结构 | **包图** | 分层 + PO/VO + 接口 + 层间依赖 |
| 详细设计 | **顺序图** | 类与类/对象之间的消息交互 |
| 详细设计 | **状态图** | 先确定主体，再画状态转移 |
| 详细设计 | **流程图** | 方法内部逻辑 |
| 数据库 | ER 图 | 参考数据库课内容，软工无特殊要求 |

### 图的消息箭头规范

| 类型 | 表示 | 含义 |
|------|------|------|
| 同步消息 | **实线 + 实心三角箭头** | 调用方等待返回 |
| 异步消息 | **虚线 + 鱼骨箭头** | 调用方不等待 |

### 状态图关键理解

1. **首先确定主体是什么** — 最重要的第一步（主体可以是单个红绿灯，也可以是整个十字路口）
2. 然后确定有哪些状态
3. 状态之间如何转移、条件是什么、动作是什么
4. 转化到代码的方式：switch/if-else / 数据驱动（状态表）/ **State 设计模式**

### 关联、聚合、组合区分

| 关系 | 特征 |
|------|------|
| **关联** (Association) | 长期持有对方引用作为成员变量 — 三者都属关联 |
| **聚合** (Aggregation) | 整体-部分关系，**无**生命周期约束 |
| **组合** (Composition) | 整体-部分关系，**有**生命周期约束 |

## 六、答题策略提示

1. **包图**：画出基本分层 + PO/VO + 主要接口即可，小错误不会扣光分，看整体
2. **人机交互原则**：有道理即得分，不要求精准背诵
3. **概念类图**：记得只有类和属性，没有方法
4. **体系结构风格**：分层和 MVC 最重要，要能画图
5. **类的设计原则**：至少10个，一定考，考试前必须全部过一遍
6. **用例**：文字表述和用例图都要会
7. **伪代码**：考的是概念理论，写伪代码也行
