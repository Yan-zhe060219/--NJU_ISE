## 一句话总结

多处理器编程面临三大挑战：**原子性丧失**（一条高级语句 ≠ 一条不可打断的指令）、**顺序性丧失**（编译器/CPU 会重排你的代码）、**全局一致性丧失**（不同 CPU 核看到的内存操作顺序可以不同）。

## 核心概念

### 1. 为什么要学并发？

**硬件现实**：单核性能已触达物理极限（功耗墙、散热墙），只能堆核心数。多核时代程序员不能再靠"等摩尔定律让程序变快"。但并发编程违反直觉——人类天生是线性思维。

**OS 视角**：操作系统本身就是世界上第一个并发程序。内核数据结构（进程列表、页表、文件系统）全都面临数据竞争。

### 2. Amdahl 定律

```
         speedup = 1 / (1-p + p/n)
```

- `p` = 可并行的指令比例，`1-p` = 必须串行的部分
- `n` = 并行线程数
- **核心约束**：即使 n → ∞，speedup → 1/(1-p)，串行部分是加速比上限

**启示**：光堆核心不够，必须减少串行部分（优化算法结构），并且处理好并发同步问题。

> 📝 **考点**：Amdahl 定律的公式必须牢记——`speedup = 1/(1-p + p/n)`。两类题型：① 给定 p 和 n，计算加速比；② 当 n→∞ 时，加速比上限 = 1/(1-p)，解释为什么串行部分是瓶颈。这是整门课少数需要记公式的考点之一。

### 3. 线程 (Thread) — 并发的基本单位

**线程 = 共享内存的执行流**：
- 独享：栈（调用帧）、寄存器上下文、TCB（线程控制块——ID、优先级…）
- 共享：堆、全局变量、代码段
- 线程间没有地址空间保护——同一进程的线程是"协作"关系

> 📝 **考点**：线程共享什么 vs 独享什么——选择题/填空题高频。重点记：共享（堆、全局变量、代码段）vs 独享（栈、寄存器）。"线程间无地址空间保护"是理解后续并发 bug 的关键——一个线程写坏另一个线程的栈数据，OS 不会拦。🔧 pthread API 具体函数属实践。

**POSIX pthread API：**

| 函数 | 作用 |
|------|------|
| `pthread_create(tid, attr, fn, arg)` | 创建线程，从 fn(arg) 开始执行 |
| `pthread_join(tid, &retval)` | 等待线程 tid 结束，取回返回值 |
| `pthread_exit(retval)` | 终止当前线程 |
| `pthread_detach(tid)` | 分离线程（"脱缰"，不被 join） |

**线程生命周期：** Init → Ready → Running → Waiting → Finished

### 4. 挑战一：原子性丧失

**原子性的两个属性：**
- **All-or-nothing**：要么全做，要么全不做，不暴露中间态
- **Isolation**：操作共享变量时不被其他操作干扰

**`sum++` 的真相：**
```c
// 即使一条 C 语句
sum++;
// 在 x86 上 = 三条指令
mov  $sum, %rax   // 读
add  $1,   %rax   // 改
mov  %rax, $sum   // 写
```

更糟糕的是，就算用 `incq sum`（一条汇编指令），在多处理器上依然不是原子的——不同 CPU 核可能同时执行 incq 闯入对方。

**两种场景下的原子性丧失：**
- 单处理器：线程被中断 → 切换到另一个线程 → 违背 All-or-nothing
- 多处理器：两个线程真正并行 → 同时读写 → 违背 All-or-nothing 和 Isolation

> 📝 **必考**：原子性的两个属性——All-or-nothing（不暴露中间态）+ Isolation（不被打扰）。能画出两个线程各执行一次 `sum++` 导致 sum=1 的指令交错序列（T1 读 0 → T2 读 0 → T1 写 1 → T2 写 1，覆盖）。理解"单处理器靠中断切换破坏原子性，多处理器靠真正并行破坏原子性"的两种场景区分。

### 5. 挑战二：顺序性丧失（编译器优化）

编译器在"不影响语义"的前提下重排代码。这在单线程下安全，多线程下就是灾难：

```c
// -O1: sum 被移出循环，最后一次性加回
for (int i = 0; i < N; i++) sum++;  // 等价于 sum += N;

// -O2: 循环被彻底求和优化
sum += 100000000;  // 直接！

// 更可怕的：
while (!done);  // 被优化为 if (!done) while(1);
```

**临时应对（本课不推荐）：**
- Barrier: `asm volatile ("" ::: "memory")` — 告诉编译器"这里可能读写任意内存"
- `volatile` 变量 — 每次 load/store 不可优化

**本课的方案：锁。**

> 📝 **考点**：编译器优化导致顺序性丧失的三个典型例子——① `-O1` 下循环被优化为 `sum += N`；② `-O2` 下直接编译期求值硬编码；③ `while(!done);` 被优化为死循环。核心理解：编译器以"单线程语义等价"为唯一判断标准，不知道其他线程的存在。能举出至少一个例子并解释为什么多线程下行为不同。`volatile` 和 `asm barrier` 只是临时应对，锁才是正确方案（同时解决原子性 + 顺序性）。

### 6. 挑战三：全局一致性丧失（内存模型）

现代处理器会乱序执行指令（如隐藏 cache miss 延迟），导致不同核心看到不一致的内存操作顺序。

**三种内存模型：**

| 模型 | 保证 | 代表 |
|------|------|------|
| **SC** (顺序一致性) | 所有操作有全局统一顺序，每核的程序顺序保持 | 早已淘汰 |
| **TSO** (Total Store Ordering) | 保证读读、读写、写写全局顺序；**不保证写读** | x86 |
| **Relaxed** (宽松) | 不保证任何不同地址操作的全局顺序 | ARM, RISC-V |

**为什么 x86 的 TSO 下 `(0,0)` 可能出现？**
```c
// T1:  x = 1; t = y;
// T2:  y = 1; t = x;
// 处理器觉得 x=1 和 t=y 无依赖，重排序为:
// T1:  t = y; x = 1;  → t=0
// T2:  t = x; y = 1;  → t=0  → (0,0)!
```
这是因为 TSO 允许"先读后写"被重排为"先写后读"。

**宽松模型更危险**：写写顺序也不保证。消息传递（先写 data 再写 flag）需要显式屏障 `__sync_synchronize()`。

> 📝 **必考**：三种内存模型——SC（顺序一致性，已淘汰）、TSO（x86，不保证写读顺序）、Relaxed（ARM/RISC-V，几乎不保证任何顺序）。重点掌握 TSO 下为什么 `(0,0)` 可能出现——因为 TSO 允许 store→load 被重排为 load→store。能画出导致 `(0,0)` 的重排序时间线。这是并发课程最经典的考题之一，"为什么 x86 上两个线程各自先写后读还会读到旧值"就是问这个。

## 难点突破

### 难点 1：为什么 `incq`（一条汇编指令）也不是原子的？

**因为 CPU 不是唯一在操作内存的**。`incq` 本质上在 CPU 内部仍然是"读→改→写"的微操作序列（load, add in ALU, store），而另一个核心可能在你 load 之后、store 之前也做了 load。**多处理器环境下，原子性必须靠硬件协议保证**（如锁总线、MESI 缓存一致性协议配合 LOCK 前缀）。

> 📝 **考点**：为什么一条汇编指令（如 `incq sum`）在多处理器上仍不是原子的——CPU 微架构层面仍是"读→改→写"三步，两个核心可能同时 load 同一个旧值。真正原子性需要 LOCK 前缀锁总线/cache line。这个知识点连接本章（并发挑战）和第 4 章（互斥/CAS 原子指令）。

### 难点 2：编译器优化 + CPU 乱序 + 内存模型 = 三重叠加

这三个挑战并非孤立——它们叠加在一起：
1. **编译器**把你写的 "sum++" 循环优化成了 `sum+=N`
2. **CPU** 把你的 store/load 顺序重排了
3. **内存模型**允许其他核心提前看到你的某些写操作

所以并发编程中，"凭直觉写出的代码"几乎一定有问题。这正是为什么需要互斥锁（第 4 章）和同步原语（第 6 章）——它们提供了"围栏"，把这三重挑战隔开。

> 📝 **考点**：三重挑战的叠加效应——编译器重排 + CPU 乱序 + 内存模型，三者并非孤立，而是层层叠加。理解"为什么并发编程不能凭直觉"是本章最核心的论述题方向。锁的作用——同时作为原子性边界（阻止其他线程闯入）和编译器 barrier（禁止优化穿越 lock/unlock），一石二鸟。

## 记忆卡片

**Q1: Amdahl 定律的公式和含义？**
A: speedup = 1/(1-p + p/n)，即使有无穷核心，加速比上限为 1/(1-p)，串行部分是瓶颈

**Q2: 线程共享什么、独享什么？**
A: 共享堆、全局变量、代码段；独享栈、寄存器上下文；线程间无地址空间保护

**Q3: 多处理器编程的三大挑战？**
A: 原子性丧失（非原子指令被中断/闯入）、顺序性丧失（编译器重排）、全局一致性丧失（CPU 乱序+内存模型）

**Q4: x86 TSO 模型不保证什么顺序？**
A: 不保证"写读"(store→load) 的全局可见顺序。ARM/RISC-V 的 Relaxed 模型完全不保证。

**Q5: 为什么 `while(!done);` 在多线程中可能死循环？**
A: 编译器优化为 `if(!done) while(1);`，因为它在单线程语义下"等价"——但它不知道 done 可以被其他线程修改。

## 💬 学习对话补充

### 2026-05-22：`sum++` 并发执行的具体交错过程与可能结果

**类型：** 深化

**背景：** 笔记中给出了 `sum++` 的三条汇编指令分解，但没有具体展开"两个线程各执行一次 sum++ 到底会发生什么"。用户想知道：代码的实际结果是什么？会不会是 1？会不会是 0？这些问题触及了原子性丧失的核心机制——不是抽象地知道"会出错"，而是具体地看到错误如何在指令交错的层面发生。

**讨论过程：** 首先构造了两个线程各执行一次 `sum++` 的最简场景（sum 初始为 0，正确预期为 2）。然后画出了一条导致 sum=1 的具体时间线：T1 读出 0 → T2 也读出 0（在 T1 写回之前）→ T1 加 1 写回 → T2 也基于旧值 0 加 1 写回，覆盖了 T1 的结果。两次 +1 只有一次"存活"。这解释了为何结果 < 预期值。

接着用户追问：有没有可能是 0？推导表明不可能——因为每次写回的值是"读到的值 + 1"，而初始值为 0，所以任何人写回的值 ≥ 1，没人会往 sum 写入 0。因此在两线程各执行一次的场景下，结果只能是 1（交错覆盖）或 2（串行不重叠）。推广到每个线程执行 N 次：结果范围是 [2, 2N]，每次 increment 都有一定概率被覆盖。

最后补充解释了为什么 `incq sum`（一条汇编指令）在多核上仍然不是原子的：CPU 微架构层面仍是"读→改→写"，两个核心可能同时 load 同一个值，各自 inc、各自 store，MESI 协议保证最终一致性但不阻止读到相同旧值。真正的原子性需要 LOCK 前缀锁总线/cache line，这直接通向第 4 章的 CAS 等原子指令。

**核心收获：** 从"知道 sum++ 不是原子的"进到"可以精确画出一条导致错误的具体指令交错序列"。理解了并发 bug 的"概率性"——不是每次都错，而是特定时序交错下才暴露，因此不能靠跑几次来验证并发代码正确性。也理解了单条汇编指令 ≠ 原子操作，原子性在多处理器上必须靠硬件协议（LOCK 前缀）保证。

**延伸思考：** 这个"两个人都读到旧值然后各自写回"的模式是几乎所有竞态条件的根源。后续学互斥锁（第 4 章）和条件变量（第 6 章）时，本质上都是在阻止这种"读旧值→改→写回"的交错——锁就是把这段序列包起来，让别人进不来。

### 2026-05-22：编译器优化级别 `-O1`/`-O2` 的含义与三个示例的具体解读

**类型：** 澄清

**背景：** 笔记中在"顺序性丧失"部分提到了 `-O1` 和 `-O2` 选项下的不同优化行为，但没有解释这些 flag 本身是什么、优化级别体系是怎样的。用户直接问"O1 选项和 O2 选项是啥？这几个例子说了什么？"——需要先解释编译器优化级别的基础知识，再逐一解读三个示例的递进逻辑。

**讨论过程：** 首先梳理了 GCC/Clang 的四级优化体系：`-O0` 无优化（调试用），`-O1` 保守优化（只做"显然安全"的变换），`-O2` 更激进（几乎所有不涉及空间换时间的优化），`-O3` 最激进。核心前提是：编译器以"单线程语义等价"为唯一判断标准，不知道其他线程的存在。

然后逐一解读三个示例。第一个（`-O1` 下 sum++ 循环被优化为 `sum += N`）：编译器认为循环 N 次加 1 和一次性加 N 等价，于是消灭循环体。但多线程下的意图可能是让其他线程看到 sum 的渐进变化——这个"中间态"被优化掉了。第二个（`-O2` 下直接被编译为 `sum += 100000000`）：编译器在编译期直接算出了结果并硬编码，循环体彻底消失。这展示了优化级别的递进——从"变换循环结构"到"直接求值"。第三个（`while (!done);` 变死循环）：编译器推理出循环体没修改 done，所以 done 不变，优化为 `if (!done) while(1);`。这个例子最直观——程序员一眼就能看出问题。

**核心收获：** 理解了"编译器优化"不是一个模糊的概念，而是一个有明确级别的体系。三个例子讲的同一件事——编译器以单线程语义做等价变换，多线程下可能完全改变程序行为——但各自展示了不同的"背叛"方式：变换循环、编译期求值、推理优化。"本课的方案是锁"——锁不仅阻止其他线程闯入（原子性），同时作为编译器 barrier，禁止优化穿越 lock/unlock 边界（顺序性）。

**延伸思考：** 这也是为什么并发编程中不能依赖"代码怎么写就怎么执行"——你的 `.c` 文件和最终二进制之间隔着一层编译器优化。`volatile` 和 `asm barrier` 只是临时方案，锁才是正确的抽象。后续第 6 章条件变量的 while 循环法则（必须用 while 而非 if）背后也有编译器优化的影子。

### 2026-05-22：课件彩蛋——线程共享/独享的 GDB 验证方法与"栈独享只是约定"

**类型：** 深化

**背景：** 课件末尾（第 45-46 页）有两页"彩蛋"内容，笔记完全没有覆盖。用户要求"将原本文档中彩蛋的部分整理一下"。这部分不是新知识点，而是教学生如何用 GDB 亲手验证线程模型——把"线程共享什么、独享什么"从记忆变成可操作的事实检查。

**讨论过程：** 彩蛋一列出了四个 GDB 验证实验，每一个都是对线程模型某一方面的直接证明：(1) `info registers` 在不同线程看到不同寄存器值 → 寄存器独享；(2) `backtrace` / `info stack` 在不同线程看到不同调用栈 → 栈空间独享；(3) 用 `setrlimit` 限制进程堆配额，一个线程消耗大部分后另一个线程 malloc 失败 → 堆空间共享；(4) `sum++` 的 bug 本身就是全局变量共享的证据——如果不共享就不会有竞态。这四个实验构成了一个完整的"亲自验证"工具包。

彩蛋二才是真正的洞察：栈空间虽然每个线程独享，但这种"独享"只是线程间的默契约定，不是操作系统强制隔离。课件原话："对于线程而言，其实是没有地址空间'保护'这个概念的。地址空间'保护'针对的对象是：进程！"任何线程只要拿到另一个线程栈上变量的地址（比如通过全局指针），就能自由读写。OS 不拦，因为同一进程的线程是"协作"关系，不应该互相恶意。这和进程间由 MMU 硬件强制兜底的隔离形成根本差异。

**核心收获：** 获得了验证线程模型的四个具体 GDB 实验方法，从"相信课本说的"进到"自己能证明"。最关键的是理解了线程"独享"的本质——它是一张君子协定，不是一道硬墙。这个区分（进程 = 硬隔离，线程 = 软约定）对于理解后续的并发 bug（一个线程误写另一个线程的栈数据）和内核设计（为什么内核线程需要更小心）至关重要。

**延伸思考：** 这个"协作而非敌对"的前提，解释了为什么并发编程如此容易出错——没有硬件帮你拦着，全靠程序员自己保证正确性。和第 9 章（进程）的地址空间保护形成对照：进程间通信需要专门的 IPC 机制（管道、共享内存、信号），而线程间通信只需要一个全局指针——方便，但危险。

## 期末简答题备考

> 以下为笔试可能出现的简答题及标准答案要点。按出题概率排序。

**Q1: 简述多处理器编程面临的三大挑战，并各举一个具体例子。**

A: ① 原子性丧失——`sum++` 在 x86 上编译为三条指令（mov, add, mov），两个线程可能同时读到旧值后各自写回，导致一次加操作被覆盖。② 顺序性丧失——编译器以单线程语义为准做优化，如 `-O1` 下循环 `for(i=0;i<N;i++) sum++` 被优化为 `sum+=N`，或 `while(!done);` 被优化为死循环。③ 全局一致性丧失——TSO 内存模型下，store→load 可能被 CPU 重排，导致两个线程各自"先写后读"却都读到旧值，出现 `(0,0)` 结果。

---

**Q2: 写出 Amdahl 定律的公式，并解释当 n→∞ 时的含义。**

A: 公式：`speedup = 1 / (1-p + p/n)`，其中 p 为可并行比例，n 为并行线程数。当 n→∞ 时，`p/n → 0`，speedup → `1/(1-p)`。含义：加速比存在理论上限，由串行部分 `1-p` 决定。即使有无限核心，程序也无法超越串行瓶颈。启示：光堆核心不够，必须减少串行部分。

---

**Q3: 线程共享哪些资源？独享哪些资源？线程间为什么没有地址空间保护？**

A: 共享：堆、全局变量、代码段。独享：栈（调用帧）、寄存器上下文。线程间无地址空间保护是因为同一进程的线程是"协作"关系——OS 的地址空间保护针对的是进程（由 MMU 硬件强制隔离），线程之间只是编程约定。一个线程拿到另一个线程栈变量的地址后可以自由读写，OS 不会拦截。这就是"进程 = 硬隔离，线程 = 君子协定"。

---

**Q4: 为什么 `incq sum`（一条 x86 汇编指令）在多处理器上仍不是原子的？如何实现真正的原子性？**

A: 在 CPU 微架构层面，`incq` 仍是"读→改→写"的微操作序列（load, add in ALU, store）。两个核心可能同时 load 同一个旧值，各自 inc，各自 store——MESI 缓存一致性协议保证最终一致性，但不阻止读到相同旧值。真正原子性需要 **LOCK 前缀**——锁住总线或 cache line，独占期间其他核心无法访问该内存地址。

---

**Q5: 画出两个线程各执行一次 `sum++`（sum 初始为 0）导致 sum=1 的指令交错序列。**

A: 时间线如下：
① T1 执行 `mov sum, %rax` → rax₁ = 0
② T2 执行 `mov sum, %rax` → rax₂ = 0（在 T1 写回之前读到旧值）
③ T1 执行 `add $1, %rax` → rax₁ = 1
④ T1 执行 `mov %rax, sum` → sum = 1
⑤ T2 执行 `add $1, %rax` → rax₂ = 1（基于旧值 0）
⑥ T2 执行 `mov %rax, sum` → sum = 1（覆盖 T1 的结果）
两次 +1，只有一次"存活"。结果 sum=1 而非预期值 2。sum=0 不可能——因为所有人写回的值 ≥ 旧值+1，初始为 0 则写回值 ≥ 1。

---

**Q6: 编译器优化在并发编程中可能造成什么问题？举两个例子说明。**

A: 编译器以"单线程语义等价"为优化前提，不知道其他线程的存在。例 1：`-O1` 下循环 `for(i=0;i<N;i++) sum++` 被优化为 `sum += N`，其他线程看不到 sum 的渐进变化。例 2：`while(!done);` 编译器推理 done 在循环体内不变，优化为 `if(!done) while(1);`——即使其他线程修改 done 为 true，该线程也永远困在死循环中。解决方案：锁——不仅保证原子性，同时作为编译器 barrier 禁止优化穿越 lock/unlock 边界。

---

**Q7: 对比 SC、TSO、Relaxed 三种内存模型，说明 x86 的 TSO 不保证什么顺序。**

A: SC（顺序一致性）：所有操作有全局统一顺序，每核程序顺序保持——已淘汰。TSO（Total Store Ordering）：保证读读、读写、写写的全局顺序；**不保证写读（store→load）的全局可见顺序**——x86 采用此模型。Relaxed（宽松模型）：几乎不保证任何不同地址操作间的全局顺序——ARM、RISC-V 采用。TSO 不保证写读顺序意味着：一个核心先 store x=1 再 load y，可能被重排为先 load y 再 store x=1，因为 CPU 认为两者无依赖。

---

**Q8: 在 TSO 模型下，为什么两个线程各自执行"先写后读"可能出现 `(0,0)` 的结果？**

A: TSO 不保证 store→load 的全局顺序。T1 执行 `x=1; t=y`，CPU 认为 x=1 和 t=y 无依赖，可重排为 `t=y; x=1` → 读到 y=0。T2 执行 `y=1; t=x`，同理重排为 `t=x; y=1` → 读到 x=0。两条线程都先读后写，结果 `(t₁, t₂) = (0,0)`。这在 SC 模型下不可能出现，在 TSO（x86）下却可能发生——是并发课程最经典的反直觉案例之一。

---

**Q9: 并发 bug 为什么是"概率性"的？为什么不能靠多跑几次来验证并发代码正确？**

A: 并发 bug 只在特定指令交错时序下暴露。两个线程的 `sum++` 要出错，需要 T2 恰好在 T1 读之后、写之前执行读操作——这种时序窗口极窄，跑 1000 次可能只触发 3 次。多跑几次没看到 bug 不意味着代码正确，只是恰好没踩中那个时序。验证并发正确性必须靠推理（静态分析）和锁/同步原语的正确使用，而非测试覆盖。
