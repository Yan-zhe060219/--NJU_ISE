## 一句话总结

进程 = 拥有独立地址空间的运行实体（含一个或多个线程），由 PCB 描述、由 fork 创建、由 execve 变身、由 exit 终结——操作系统通过这三个系统调用管理进程的完整生命周期。

## 知识地图

```
进程 (Process) = 拥有独立地址空间的运行实体

进程控制块 (PCB) — 内核维护的进程元信息
  ├── 内存信息、线程信息、打开文件、当前目录、ID、状态、父子关系...

进程树
  ├── init (PID=1): 所有用户进程的祖先
  ├── 僵尸进程: 已终止但 PCB 未被父进程回收
  └── 孤儿进程: 父进程先终止 → 被 init 接管

三大系统调用
  ├── fork()  : 完整复制当前进程 → 父子分道扬镳
  │     └── 优化: COW (写时复制) — 共享内存，写时才真正拷贝
  ├── execve(): 用新程序覆盖当前进程 → "变身"
  │     └── 保留: 文件描述符、环境变量（传递上下文）
  └── exit()  : 终止进程 → 通知父进程 → 回收资源

IPC 基础
  ├── 管道 (Pipe): fork + 文件描述符继承 → 父子/兄弟进程通信
  └── 信号 (Signal): 用户态中断模拟 → 异步通知机制
```

## 核心概念

### 1. 什么是进程？

没有统一定义，但可以理解为：**拥有独立地址空间的运行实体，包含一个或多个线程**。

```
进程 = 地址空间 (Code + Global Vars + Heap + Stack)
      + 一个或多个线程 (TCB: PC, SP, Registers, metadata)
      + 系统资源 (打开的文件, 信号处理, 当前目录...)
```

PCB（进程控制块）由内核维护，包含：内存映射、线程信息、打开文件描述符、当前目录、IO 状态、进程 ID、状态、父子指针等。

不同 OS 的实现差异：
- **Linux**：不刻意区分进程和线程，统一用 `task_struct`（共享地址空间的两个 `task_struct` = 同进程的两线程）
- **Solaris**：显式区分 `kthread_t`（内核线程）和 `klwp_t`（用户态轻量进程）
- **Windows**：`EPROCESS`（进程对象）+ `ETHREAD`（线程对象），另有 `PEB`/`TEB` 暴露给应用程序

### 2. 进程树

进程由进程创建 → 形成进程树。`init`（PID=1）是所有用户进程的祖先，由内核在启动时从零创建。之后的进程创建就是"鸡生蛋、蛋生鸡"的重复过程。

### 3. 进程生命周期

```
new ──→ Ready ──→ Running ──→ Finished
           ↑          │
           │    Process waits for event
           │          ↓
           └──── Waiting
              Event occurs
```

状态转换由调度器控制。多线程进程中，每个线程有自己的生命周期轨迹。

### 4. fork() — 进程的创建

**语义**：完整复制当前进程的状态机（内存、寄存器、PCB 信息），得到一份"双胞胎"。父子进程从 fork 之后各自独立运行。

```c
pid_t pid = fork();
if (pid == -1) {
    // fork 失败
} else if (pid == 0) {
    // 子进程：fork 返回 0
} else {
    // 父进程：fork 返回子进程的 PID
}
```

**关键细节**：
- 不仅复制地址空间，也复制 PCB 中打开的文件描述符表（父子共享相同的文件偏移量！）
- 多线程进程调用 fork 时，**只有调用 fork 的线程被复制**到子进程
- POSIX 列出了 fork 的 25 种特殊情形的处理方式

**fork 炸弹**：`while(1) fork();` — 指数增长，不要尝试。

**fork 的应用**：进程快照。主进程崩溃后从快照恢复，某些 Bug（如并发 Bug）可能在重放中消失（Rx, SOSP'05 最佳论文）。

### 5. execve() — 进程的改变

**语义**：将当前进程**重置**为一个新可执行文件的初始状态。

- 加载新的代码段、数据段
- 重新初始化堆和栈
- 重置 PCB 中的内存映射
- PC 设到新入口点 → 最终调用 `main()`

**注意**：`execve` **不改变**文件描述符表——打开的 fd 在 execve 后仍然打开。这很重要：
- Shell 启动的子进程继承了相同的 stdout → 打印到同一终端
- 管道的实现依赖于 fd 跨 execve 保持打开

**`FD_CLOEXEC`**：可设置在 execve 时自动关闭的 fd 标志，防止资源泄漏。

### 6. fork + execve = 创建新进程的组合拳

```c
// Shell 的简化原理
while (1) {
    read_command(&filename, &params);
    int pid = fork();
    if (pid == 0) {
        execve(filename, params, environ);  // 子进程变身
    } else {
        waitpid(pid, &status, 0);  // 父进程等待
    }
}
```

这就是所有 Shell 创建进程的方式：fork 一个自己，然后 execve 变成目标程序。

### 7. 写时复制（Copy-On-Write, COW）

**问题**：fork 要完整复制父进程内存，但 fork 后往往立刻 execve 加载新程序——之前的全量拷贝完全浪费了。

**COW 解决**：
1. 父子进程共享同一份物理内存
2. 将这些共享页标记为**只读**
3. 某个进程尝试写 → 触发页保护异常 → 内核识别为 COW 事件 → **此时才**在物理内存中复制一份副本给写入方

这样只读页（代码段、libc 共享库等）永远不复制，可写页只在真正需要时才复制。大幅降低 fork 开销。

### 8. 管道（Pipe）

一种特殊的"文件"，提供读者/写者共享的通信机制：

```c
int pipefd[2];
pipe(pipefd);   // pipefd[0]=读口, pipefd[1]=写口
```

**匿名管道的经典用法**（父子进程通信）：
1. 父进程 `pipe(pipefd)` → 同时持有读口和写口
2. `fork()` → 子进程也持有两端
3. 父进程 `close(pipefd[0])`（关读口），子进程 `close(pipefd[1])`（关写口）
4. 父写子读 → 单向管道通信

### 9. exit() — 进程的退出

Linux 5 种退出机制：
- **正常退出**：`return` from main、调用 `exit()`、调用 `_exit()`
- **异常退出**：调用 `abort()`、被信号终止

`exit(status)` 的完整流程：
1. 调用 `atexit()` 注册的清理函数（最多 32 个，逆序调用）
2. 关闭所有打开的 stdio 流（flush 缓冲区）
3. 移除临时文件
4. 调用 `_exit()` 真正终止

`_exit()` 的系统行为：
- 关闭所有文件描述符
- 子进程被 init 接管
- 向父进程发送 `SIGCHLD`
- 注意：`_exit()` 只终止当前线程，但 `exit()` 包装了 `exit_group()` 终止所有线程

**僵尸进程**：进程已终止，但 PCB 未被父进程回收（父进程还没 `wait`）。PCB 中的指针仍被父进程引用，不能释放。

**孤儿进程**：父进程先于子进程终止。Linux 中孤儿自动被 init（PID=1）接管，init 会在它们终止时调用 `wait` 回收 PCB。

### 10. 信号（Signal）

**本质**：对硬件中断的软件模拟——用户态程序也可以注册异步事件处理器。

| | 中断/异常 | 信号 |
|---|---|---|
| 定义者 | 硬件 | 内核 |
| 处理器 | 内核 | 用户态函数 |
| 栈 | 中断栈（内核） | 信号栈（用户） |
| 屏蔽 | 中断屏蔽 | 信号屏蔽 |

```c
signal(SIGCHLD, handler);  // 注册信号处理函数
signal(SIGCHLD, SIG_IGN);  // 忽略（子进程终止后直接回收，不变成僵尸）
signal(SIGCHLD, SIG_DFL);  // 使用默认处理
```

信号的用途：
- **SIGCHLD + handler**：异步回收子进程（父进程不用阻塞在 `wait`）
- **SIGIO**：异步 I/O 通知
- **IPC**：进程间通信的一种机制（此外还有消息传递、共享内存、管道等）

## 难点突破

### 难点 1：fork 后文件偏移量共享的怪异行为

```c
// 父子进程读取同一文件
int fd = open("test.txt", O_RDWR);
read(fd, str, 1);     // 读第 1 个字节
if (fork() == 0) {
    read(fd, str, 9); // 子进程从第 2 个字节开始读
} else {
    read(fd, str, 9); // 父进程也从第 2 个字节开始读
}
```

fork 复制了 fd 表，但 fd 指向的**内核文件对象是同一个**——偏移量共享！父子进程的读操作会互相影响文件偏移。这不是 Bug，是设计：fork 复制的是"对同一打开文件的引用"。

### 难点 2：COW 如何感知"写"操作？

"写自己的内存"是一个用户态指令（如 `mov [eax], 1`），内核如何知道的？

答案：用 MMU 的页保护机制。将共享的物理内存页标记为**只读**。任何写入尝试 → 触发 page fault → 陷入内核 → 内核检查这是 COW 页 → 分配新物理页、复制数据、更新页表、改为可写 → 返回用户态重新执行那条指令。整个过程对用户透明。

## 记忆卡片

**Q1: fork() 的返回值如何区分父子进程？**
A: 父进程返回子进程 PID（>0），子进程返回 0，失败返回 -1。

**Q2: execve() 做什么？为什么不需要返回值？**
A: 用新程序覆盖整个进程；成功则当前代码不再存在，返回值无意义。

**Q3: fork + execve 组合中，什么跨 execve 保持？什么不保持？**
A: 保持：文件描述符、环境变量；不保持：地址空间（代码/数据/堆/栈全部重置）。

**Q4: COW（写时复制）的原理？**
A: 父子共享物理内存并标为只读；写操作触发 page fault → 内核此时才真正拷贝一份。

**Q5: 僵尸进程和孤儿进程的区别？**
A: 僵尸 = 子进程终止但父进程未 wait（PCB 未回收）；孤儿 = 父进程先终止，子进程被 init 接管。

**Q6: 信号和中断的本质关系？**
A: 信号是中断的软件模拟——中断是硬件通知内核，信号是内核通知用户进程。

**Q7: fork() 为什么在父子进程中返回不同值？**
A: 父进程需要子进程 PID 来 wait/kill 管理；子进程拿到 0 知道自己是孩子即可。本质是角色分发机制。

**Q8: 为什么 `./a.out` 和 `./a.out | cat` 的输出行数可能不同？**
A: 终端默认行缓冲（逐行输出），管道默认全缓冲。fork 复制了全缓冲区中未 flush 的内容，导致每个进程退出时多输出已被父进程打印过的那一份。

**Q9: 两次 fork() 产生几个进程？三次呢？通式？**
A: 每次 fork 后直到的进程数翻倍。n 次顺序 fork（不在循环内条件分支）→ 2ⁿ 个进程。

**Q10: fork 后父子进程打开同一文件，read 行为为何互相影响？**
A: fork 复制 fd 表但指向同一内核文件对象 → 文件偏移量共享。父进程 read 后偏移量移动，子进程从新位置继续读。这是设计而非 Bug。
