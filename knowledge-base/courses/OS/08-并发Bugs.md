## 一句话总结

学了并发工具不等于能写好并发程序——97% 的非死锁并发 Bug 归为原子性违背（AV）和顺序性违背（OV）两类；死锁的应对策略分四级：忽略（鸵鸟算法）→ 预防（破坏四条件之一）→ 避免（银行家算法）→ 检测并恢复（lockdep/环检测）。

## 知识地图

```
并发 Bug 分类
  ├── 原子性违背 (AV, ~97%): 该原子化的代码段被插入 → 忘记/上错锁
  │     └── "ABA" 模式: check → 被插入 → use (TOCTOU)
  ├── 顺序性违背 (OV, ~97%): 事件未按预期顺序发生
  │     └── "BA" 模式: 依赖 A 先于 B，但 B 先执行了
  └── 死锁 (Deadlock, ~3%)
        ├── A-A 型: 同一个线程重复获取已持有的锁
        └── ABBA 型: 两个线程交叉等对方的锁

死锁应对策略（四级）
  ├── Level 0: 忽略（鸵鸟算法）— 发生概率低、重启代价小
  ├── Level 1: 预防（破坏四条件之一）
  │     ├── 破坏互斥 → 无锁算法 (CAS, RCU)
  │     ├── 破坏持有并等待 → 一次性申请或拿不到就全放
  │     ├── 破坏不可抢占 → 强行抢资源（有限制）
  │     └── 破坏循环等待 → Lock Ordering（最实用！）
  ├── Level 2: 避免（银行家算法）— 判断是否进入"不可挽回"状态
  │     └── 不实用: 需要预知最大需求矩阵
  ├── Level 3: 检测并恢复 → lockdep (Linux), 环检测
  └── 动态分析工具: ASan, TSan (happens-before)
```

## 核心概念

### 1. 真实世界的并发 Bug

**Therac-25 事故（1985-1987）**：软件锁被竞态条件绕过，患者接受百倍辐射剂量，至少 6 人死亡。

**2003 年美加大停电**：能源管理系统中的竞态条件触发，代码从 1990 年运行到 2003 年才首次触发 Bug——损失 250-300 亿美元。

**经验研究（Shan Lu et al., ASPLOS'08）**：调研 4 个大型软件，97% 的非死锁并发 Bug 归为两类。

### 2. 原子性违背（Atomicity Violation, AV）

一个应该**整体原子执行**的代码段被其他线程插入。

**"ABA" 模式**（MySQL 真实案例）：
```c
// Thread 1:                 // Thread 2:
if (thd->proc_info) {        thd->proc_info = NULL;
    fputs(thd->proc_info, ...);  // ← Boom! 悬空指针
}
```
单独看 check 和 use 可能各自有锁，但**整体不是原子的**。修复：给整个 check→use 加同一把锁。

**典型表现**：忘记上锁、上错了锁（锁 A 保护的数据用了锁 B）。

### 3. 顺序性违背（Order Violation, OV）

事件未按预期顺序发生。

**"BA" 模式**（Mozilla 真实案例）：
```c
// Thread 1:             // Thread 2 (callback):
S1: io_pending = TRUE;   S2: io_pending = FALSE;
...                       ...
while (io_pending) {...}  // 如果 S2 在 S1 之前执行
                          // → Thread 1 永远卡在循环里
```

**典型表现**：忘记同步、同步条件写错、依赖了未保证的执行顺序。

### 4. 死锁（Deadlock）

多线程形成的等待环，每个都在等环中另一个线程释放资源。

**A-A 型（自我死锁）**：同一线程重复获取已持有的锁。看起来傻，但在多层函数调用+隐藏控制流下很容易发生。xv6 防御性编程：`if(holding(lk)) panic("acquire");`

**ABBA 型（交叉死锁）**：
```c
T1: lock(A); lock(B); ...  // 持有 A，等 B
T2: lock(B); lock(A); ...  // 持有 B，等 A → 死锁！
```

### 5. 死锁四条件（Coffman, 1971）

| 条件 | 含义 |
|------|------|
| 互斥 (Mutual Exclusion) | 资源不能共享 |
| 持有并等待 (Hold and Wait) | 持有一部分资源，等另一部分 |
| 不可抢占 (No Preemption) | 不能强行抢夺 |
| 循环等待 (Circular Wait) | 存在等待环 |

四个条件是**必要的**（同时满足才可能死锁，但不一定发生——环外线程释放资源可解环）。

### 6. 死锁预防：破坏四条件

**破坏互斥** → 无锁算法。如 CAS 实现无锁递增、RCU。但编写无锁代码极其困难（指令顺序必须精确）。

**破坏持有并等待**：
- 方案 A：一次性获取所有锁。不现实（无法预知未来需要哪些锁），且降低并发度。
- 方案 B：拿不到下一把锁就释放所有已持锁。哲学家方案 2。注意：需要随机等待防**活锁（livelock）**。

**破坏不可抢占**：强行抢占资源。仅当被抢占线程能恢复状态时才可行（如 CPU 上下文切换、内存 swap）。不适用于所有资源（如打印机）。

**破坏循环等待 → Lock Ordering（最实用！）**：
```c
// 总是按地址从小到大的顺序获取锁
if (m1 > m2) {
    lock(m1); lock(m2);
} else {
    lock(m2); lock(m1);
}
```
**为什么正确？** 把锁编号成全序 → 每次申请锁都是从"小"到"大"的边 → 锁申请图是无环的 → 有拓扑序 → 不会死锁。Linux 内核广泛使用（`mm/rmap.c` 中有详细的锁顺序注释）。

**注意**：Lock Ordering 仍有局限——新增一把锁时，很难确定它在 5000 把锁的层级中排在哪。最佳实践是**封装锁**（锁不暴露到头文件，不跨文件持有）。

### 7. 银行家算法（Banker's Algorithm）

Dijkstra 提出的**死锁避免**策略——动态判断每个资源请求是否会引导系统进入"不可挽回"状态。

**核心判断**：假设接受该请求 → 逐个检查是否存在线程序列，使每个线程的未来最大需求都能被满足 → 如果存在 → 安全，接受；否则 → 不安全，拒绝。

**算法步骤**：
1. 找到线程 i，其剩余需求 ≤ 系统当前可用资源
2. 标记 i 为可终止，假设其运行完毕并回收其所有资源
3. 在更好的局面下重复，直到所有线程可终止（安全）或无人可满足（不安全）

**为什么不实用？** 无法预知线程未来最大需求矩阵；线程数和资源数动态变化。

### 8. 死锁检测：lockdep

与其预防，不如让死锁发生然后检测。Linux 的 **lockdep** 原理：
- 每次 `acquire`/`release` 记录 `(tid, lock_addr)`
- 动态构建锁有向图：当前持有锁 u 的线程尝试获取锁 v → 加边 (u, v)
- 对该图运行 DFS 环检测（有回边 = 有环 = 死锁风险）
- 注意：同类型多资源时，单纯环检测不够，需要类似银行家算法的检查

### 9. 动态分析工具

| 工具 | 检测目标 | 原理 |
|------|----------|------|
| **AddressSanitizer (ASan)** | 内存越界、use-after-free、double-free | 编译器插桩，在合法内存周围放置"毒区" |
| **ThreadSanitizer (TSan)** | 数据竞争 | 记录所有内存访问，构建 happens-before 图；不同线程、同地址、至少一写、无 happens-before 关系 → 竞态 |
| **MemorySanitizer (MSan)** | 未初始化读取 | 追踪每个字节的初始化状态 |
| **UBSanitizer** | 未定义行为（整数溢出等） | 编译器插桩检查 |

**低配版替代方案**（适用于自制 OS 等受限环境）：
- **Canary**：在栈/缓冲区边界放魔数，定期检查是否被覆盖
- **自旋计数器**：超过阈值（如 1 亿次）报 panic
- **内存分配器魔数**：分配时写魔数，释放时清零，检测 double-alloc/double-free
- **延迟放大法**：在读写之间加 `delay()`，放大竞态窗口便于检测

## 难点突破

### 难点 1：活锁（Livelock）vs 死锁

死锁：线程全阻塞，谁也动不了。活锁：线程没阻塞，但一直在做无用功。

哲学家方案 2 中，如果不加随机睡眠：5 人同时拿左筷、同时发现右筷不在、同时放下、同时再拿左筷……无限循环。线程是活跃的（反复拿放），但谁也吃不到饭。这就是活锁。

解法：引入随机性打破同步节奏。

### 难点 2：银行家算法中"不可挽回"区域的直观理解

用 2D 坐标系（横轴 = 线程 A 的进度，纵轴 = 线程 B 的进度）：
- 系统状态是一个点
- 点只能向右/向上移动（线程不可倒退）
- 死锁区域是某个矩形区域——一旦进入，无论怎么向右或向上，最终都会落入坐标轴的"死角"
- 银行家算法就是在这个点进入该区域前拦住

## 记忆卡片

**Q1: 97% 的非死锁并发 Bug 归为哪两类？**
A: 原子性违背（AV，该原子的代码段被插入）和顺序性违背（OV，事件未按预期顺序发生）。

**Q2: 死锁的四个必要条件（Coffman 条件）？**
A: 互斥、持有并等待、不可抢占、循环等待。破坏任意一个即可预防死锁。

**Q3: Lock Ordering 为什么能防止死锁？**
A: 强制按全局顺序获取锁 → 锁申请图的所有边都从小指向大 → 无环 → 有拓扑序 → 不会死锁。

**Q4: 银行家算法的核心思想？**
A: 判断接受一个资源请求后，是否存在一个线程执行序列使所有线程都能完成。存在 = 安全（接受），不存在 = 不安全（拒绝）。

**Q5: TSan 如何检测数据竞争？**
A: 记录所有内存访问，构建 happens-before 图。不同线程 + 同地址 + 至少一写 + 无 happens-before 关系 → 数据竞争。

**Q6: 活锁和死锁有什么区别？**
A: 死锁 = 线程全部阻塞；活锁 = 线程没阻塞但反复做无用功（如反复拿放筷子）。引入随机性可打破活锁。

### 简答题（期末笔试模拟）

**Q1: 97% 的非死锁并发 Bug 归为哪两类？各自的典型模式是什么？**

> 参考答案：① 原子性违背（AV）——该原子执行的代码段被其他线程插入，典型为"ABA"模式（check → 被插入 → use），如 TOCTOU。根因是忘记加锁或锁与数据未绑定（"上错锁"）。② 顺序性违背（OV）——事件未按预期顺序发生，典型为"BA"模式（依赖 A 先于 B，但 B 先执行了）。根因是忘记同步或同步条件写错。

**Q2: 死锁的四个必要条件是什么？破坏每个条件各对应什么策略？**

> 参考答案：
> - 互斥 → 无锁算法（CAS、RCU），最难实现
> - 持有并等待 → 一次性获取所有锁，或拿不到就全放（哲学家方案2，需防活锁）
> - 不可抢占 → 强行抢占资源，仅某些资源可行
> - 循环等待 → **Lock Ordering（最实用！）**：按全局顺序获取锁，保证锁申请图无环

**Q3: Lock Ordering 为什么能防止死锁？有什么局限？**

> 参考答案：强制所有线程按相同的全局顺序获取锁 → 锁申请图的所有边方向一致（从小到大）→ 图中不可能有环 → 有拓扑序 → 不会死锁。局限：新增锁时很难在已有 N 把锁的层级中确定位置；最佳实践是封装锁（不暴露到头文件，不跨文件持有）。

**Q4: 银行家算法的核心思想是什么？为什么实际系统中很少使用？**

> 参考答案：判断接受资源请求后，是否存在线程执行序列使所有线程都能完成——存在则安全（接受），不存在则不安全（拒绝）。不实用的原因：① 线程无法提前声明最大资源需求；② 线程数和资源数动态变化；③ 维护最大需求矩阵的开销过大。实际中更常用 Lock Ordering + lockdep。

**Q5: TSan 如何检测数据竞争？检测到的条件是什么？**

> 参考答案：记录所有内存访问，构建 happens-before 图。数据竞争判定条件——四个条件同时满足：① 不同线程 ② 访问同一内存地址 ③ 至少一个写操作 ④ 两次访问之间无 happens-before 关系。

**Q6: 死锁和活锁的区别是什么？各举一个实际场景。**

> 参考答案：死锁——线程全部阻塞，谁也动不了（如两个线程交叉等对方的锁）。活锁——线程没阻塞，但反复做无用功（如哲学家方案2中 5 人同时拿左筷、同时发现右筷不在、同时放下、同时再拿左筷……无随机延迟时无限循环）。解法：死锁用 Lock Ordering 预防，活锁引入随机性打破同步节奏。

## 🛠 工程实践注意

1. **AV 的修复不是"多加锁"，而是"锁对数据"。** 看到 AV Bug 第一反应是加锁——但如果锁和数据的绑定关系没理清，只会引入更多"上错锁"的问题。每把锁对应一组数据，画一张"锁→数据"映射表比盲目加锁有用得多。

2. **OV 的修复往往比 AV 更隐蔽。** AV 至少能在代码中看到"没加锁"，OV 的同步条件错误（如 `while (!done)` 中 `done` 的修改没有通知对方）运行时可能偶尔正常。排查 OV 时重点关注：这个变量在哪些线程中被写？写完有没有 `signal/broadcast/wakeup`？

3. **Lock Ordering 不是银弹。** 在大型项目中，你永远不知道"所有锁的全局顺序"是什么。实用替代：① 封装锁，锁不跨模块暴露；② 写注释"获取本模块锁时不能持有模块 X 的锁"；③ 用 lockdep 在测试环境自动检测。

4. **银行家算法可以面试时讲，不能上线用。** 它的价值在于让你理解"预判安全性"的思维——虽然算法本身不实用，但"在给资源之前先想能不能收回来"是每个做并发的人的本能。
