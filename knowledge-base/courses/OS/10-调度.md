## 一句话总结

调度 = 在 context-switch + 队列的机制上运行不同策略：批处理用 SJF/SRTF（最优平均等待），交互用 MFQ（多级反馈队列，Windows/macOS/Linux 均使用），实时用 EDF（最优动态优先级），所有策略在实际系统中面临优先级反转、负载均衡、亲和性等工程挑战。

## 知识地图

```
调度 = 机制 + 策略
  ├── 机制: context-switch + PCB/TCB 队列 + 时钟中断
  └── 策略: 三类场景
        │
        ├── 批处理任务 (周转时间)
        │     ├── FCFS/FIFO: 简单但有护航效应
        │     ├── SJF: 平均等待时间最优（需预知执行时间）
        │     ├── SRTF: SJF 的可抢占版本
        │     └── 时间预测: 指数移动平均 τ = α·t + (1-α)·τ
        │
        ├── 交互式任务 (响应时间)
        │     ├── RR (Round Robin): 时间片轮转
        │     ├── 优先级调度: I/O-bound 优先
        │     ├── MFQ (多级反馈队列): 动态优先级 ★Windows/macOS/Linux
        │     └── 乐透调度: 按比例概率调度
        │
        └── 实时任务 (截止日期)
              ├── 准入控制: Σ(Ci/Pi) ≤ 1
              ├── Rate Monotonic: 周期短→优先级高（静态最优）
              └── EDF: 截止日期近→优先级高（动态最优, 100%利用率界）

工程挑战
  ├── 多核: SMP + 负载均衡 (push/pull) + 处理器亲和性 + NUMA
  └── 优先级反转 → 优先级继承 / 优先权极限
```

## 核心概念

### 1. 机制与策略分离

操作系统的核心设计思想：**机制** = 怎么做（context-switch + 队列 + 时钟中断），**策略** = 选谁执行（FCFS/SJF/RR/...）。

同一套机制上可以换不同策略。但策略也可能需要新的机制支撑（如 SJF 需要预知执行时间）。

### 2. 调度指标

| 指标 | 含义 | 目标 |
|------|------|------|
| CPU 利用率 | CPU 忙碌时间占比 | 越大越好 |
| 公平性 | 同优先级进程获得相近的 CPU 时间 | — |
| 吞吐量 | 单位时间完成进程数 | 越大越好 |
| 周转时间 | 进程从到达到完成的总时间 | 越小越好 |
| 等待时间 | 在就绪队列中等待的总时间 | 越小越好 |
| 响应时间 | 从提交到第一次被执行的间隔 | 越小越好 |

等待时间 = 周转时间 - 获得 CPU 执行的时间。

### 3. 调度的时机

当 CPU 回到操作系统掌控时：
- 系统调用（fork, exit...）
- 运行进程阻塞（wait 子进程, I/O 等待）
- 中断发生（I/O 中断, 时钟中断）

### 4. 批处理调度策略

**FCFS (FIFO)**：先来先服务。最简单，但有**护航效应（Convoy Effect）**——短任务排在长任务后面，平均等待时间极差。

**SJF (最短任务优先)**：执行时间最短的优先。**就平均等待时间而言是最优的**（证明：冒泡排序过程每步减少等待时间）。

**SRTF (最短剩余时间优先)**：SJF 的可抢占版——新来一个剩余时间更短的任务时，抢占当前任务。

**SJF 的缺陷**：不公平（长任务可能饿死）、需预知执行时间、可被愚弄（把长任务拆成很多短任务骗调度器）。

**时间预测**：指数移动平均 `τ_{n+1} = α·t_n + (1-α)·τ_n`（最近的历史权重更大，α 一般取 0.5）。

### 5. 交互式调度策略

**CPU-bound vs I/O-bound**：
- CPU 密集型：长时间 CPU burst，少量 I/O
- I/O 密集型：短 CPU burst，频繁等待 I/O

**Round Robin (RR)**：每个任务获固定时间片，用完回队尾。时间片太大 → 退化为 FCFS；太小 → 上下文切换开销太高。通常 10ms-100ms。

RR 的问题：平均周转时间差（比 FCFS/SJF 差很多），但响应时间好。

**优先级调度**：给 I/O 密集型高优先级（它们很快就让出 CPU）。Linux: 实时优先级 0-99（`chrt`），普通优先级 100-139（`nice` -20 到 +19）。

**MFQ (多级反馈队列)**——现代 OS 的核心调度策略：
1. 多个优先级队列，高优先级 = 短时间片，低优先级 = 长时间片
2. 新进程进入最高优先级
3. 用完时间片 → 降一级；没用完（阻塞在 I/O）→ 保持当前级别
4. 效果：I/O 密集自动留在高优先级，CPU 密集自动沉到底层
5. 需定期**老化**（提升所有进程到最高优先级），防止饥饿
6. 可被愚弄（在时间片快用完时故意睡眠）→ 需追踪长期 CPU 使用

**乐透调度**：分配彩票票数，随机抽奖。高优先级多拿票，但不保证绝对顺序。至少给每个作业一张票防饿死。

### 6. 实时调度

**准入控制（Admission Control）**：周期性任务集可调度的必要条件 — `Σ(C_i/P_i) ≤ 1`。

**Rate Monotonic（单调速率）**：周期越短 → 优先级越高。**固定优先级最优**算法，利用率上界 `U = n(2^(1/n) - 1)`（n→∞ 时趋近 ln2 ≈ 69.3%）。超过此界可能调度失败。

**EDF（最早截止日期优先）**：截止日期越近 → 优先级越高。**动态优先级最优**算法，利用率可达 100%。动态调整意味着更高开销。

### 7. Linux CFS（完全公平调度器）

自 Linux 2.6.23 起使用。

**核心思想**：跟踪每个进程已获得的 CPU 时间，每次选**获得时间最少**的进程执行。

**数据结构**：红黑树按虚拟运行时间（vruntime）排序。最左叶 = 时间最少 = 下一个运行（O(1) 选取）。上下文切换时更新 vruntime 并重新插入（O(log n)）。

**权重**：高优先级 → vruntime 增长更慢 → 被调度更多。CPU 时间占比 = `w_i / Σw_j`。

**睡眠进程**：唤醒时将其 vruntime 设为红黑树中当前最小值（避免疯狂找补之前少用的时间）。

### 8. 多核调度

**SMP（对称多处理）**：每个核自我调度，不需中央调度器。几乎所有现代 OS 支持。

**就绪队列设计**：
- 统一队列 + 全局锁 → 简单但有竞争
- 每核私有队列 → 无竞争 + 缓存亲和性更好（主流做法）

**负载均衡**：
- Push migration：定期检查，过载 CPU 推送任务到空闲 CPU
- Pull migration：空闲 CPU 从繁忙 CPU 拉取任务

**处理器亲和性**：线程在某核上运行时，该核的缓存存有其内存访问数据。迁移会损失这些缓存。调度器需在负载均衡和亲和性间权衡。

**NUMA 感知**：应将线程调度到离它所用内存最近的 CPU 上。

### 9. 优先级反转（Priority Inversion）

**问题**：高优先级任务被中优先级任务间接阻塞——低优先级持有锁被中优先级抢占，高优先级需要锁。

**火星探路者（Mars Pathfinder, 1997）**：着陆器因优先级反转每隔几天自动重启。工程师远程打补丁修复。差点导致任务失败。

**解决方案**：
- **优先级继承**：有更高优先级任务等待锁时，临时将锁持有者优先级提升到等待者级别
- **优先权极限（Priority Ceiling）**：获取锁时立即提升到该锁关联的上限优先级

### 10. 调度算法评估

方法：确定标准 → 确定评估模型 → 在给定 workload 下计算性能。

- 确定性建模：给定具体 workload，计算各算法表现（简单但说服力弱）
- 排队模型（M/M/1）：按概率分布描述进程到达和服务时间 → 计算平均利用率、队列长度、等待时间

## 难点突破

### 难点 1：MFQ 为什么能被愚弄，怎么防？

**愚弄方法**：恶意进程在时间片用完前 100μs 故意做一个 I/O 操作（如 sleep 几毫秒）→ "没用完"时间片 → 不降级 → 永驻高优先级。

**防御**：追踪长期 CPU 使用，每个优先级队列关联一个最大 CPU 时间配额，超出就降级——不论单次时间片是否用完。

### 难点 2：为什么 Rate Monotonic 利用率上界是 69.3%？

直观理解：当 n→∞，`U = n(2^(1/n) - 1)` → `ln(2) ≈ 0.693`。这意味着在最坏情况下，即使总利用率 < 100%，Rate Monotonic 也可能调度失败（如两个任务的例子 `25/50 + 35/80 = 93.75% < 100%` 但调度失败）。而 EDF 能保证 100% 利用率下的可调度性——这是动态优先级（更高开销）换来的收益。

## 记忆卡片

**Q1: 护航效应（Convoy Effect）是什么？**
A: FCFS 下短任务排在长任务后面，导致所有任务的等待时间被长任务拖长。

**Q2: 为什么 SJF 对平均等待时间是最优的？**
A: 每将长任务与后面的短任务交换，平均等待时间减少（差值为 t_long - t_short > 0）。冒泡排序每步都在优化。

**Q3: MFQ 如何自然区分 I/O 密集和 CPU 密集型进程？**
A: I/O 密集频繁阻塞，没用完时间片 → 留在高优先级；CPU 密集用完时间片 → 逐级下沉到低优先级长时间片队列。

**Q4: Rate Monotonic 和 EDF 的核心区别？**
A: RM = 固定优先级（周期短→优先），利用率上界 69.3%；EDF = 动态优先级（截止日期近→优先），利用率可达 100%。

**Q5: 优先级反转怎么解决？**
A: 优先级继承（等锁时临时提升锁持有者优先级）或优先权极限（拿锁时直接提到天花板优先级）。

**Q6: CFS 为什么用红黑树而不是就绪队列？**
A: 红黑树按 vruntime 排序 → 选最左叶 O(1)；更新后重插入 O(log n)。队列只能 O(n) 找最小。

**Q7: 什么是护航效应？举例说明。**
A: FCFS 下长任务先到，短任务排在后面等——就像超市排在一个装满购物车的人后面。如 P1(100ms) → P2(10ms) → P3(10ms)，平均等待时间 = (0+100+110)/3 = 70ms；若先跑短任务 SJF 顺序：P2 → P3 → P1，平均等待 = (0+10+20)/3 = 10ms。

**Q8: MFQ 如何实现"自动分类"I/O密集和CPU密集进程？**
A: I/O密集频繁阻塞，没用完时间片 → 留在高优先级；CPU密集用完时间片 → 逐级下沉。无需显式分类，调度器从行为自动学习。类似优先级调度中给 I/O密集高优先级的逻辑，但 MFQ 是动态调整而非静态标注。

**Q9: 优先级反转的经典案例及解决方案？**
A: 火星探路者 1997——高优先级总线管理任务被中优先级气象任务阻塞，因为锁被低优先级持有且中优先级抢占了 CPU。解决：优先级继承（等锁者临时提升持有者优先级）或优先权极限（拿锁时直接提到天花板）。

**Q10: 为什么调度策略需要"老化"机制？**
A: 防止饥饿。MFQ 中 CPU 密集进程沉到底层后，若持续有新 I/O密集进程在高优先级，底层进程可能永远得不到 CPU。定期将所有进程提升到最高优先级，让底层进程有机会执行。

### 计算题

**T1: 给定进程集，计算 FCFS / SJF / SRTF / RR 的平均等待时间和平均周转时间。**
```
进程  到达时间  执行时间
P1      0         8
P2      1         4
P3      2         9
P4      3         5
```
解法要点：
- FCFS：按到达顺序，等前一个执行完
- SJF（非抢占）：当前执行完时选已到达中最短的
- SRTF（抢占）：每个时刻选剩余时间最短的（新进程到达时可能抢占）
- RR(q=4)：时间片4ms轮转，用完回队尾

**T2: 指数移动平均预测下一个 CPU burst。**
已知 τₙ=10, tₙ=6, α=0.5，求 τₙ₊₁。
A: τₙ₊₁ = 0.5×6 + 0.5×10 = 8

**T3: Rate Monotonic 可调度性判定。**
给定 P1(C=20, T=50), P2(C=35, T=80)，判定是否可调度。
A: U = 20/50 + 35/80 = 0.4 + 0.4375 = 0.8375。上界 2(2^(1/2)-1) ≈ 0.828。0.8375 > 0.828，RM 上界测试失败（但可逐个时间点检查，可能实际仍可调度）。

**T4: EDF 可调度性判定。**
同上任务集。EDF 条件：Σ(Ci/Ti) ≤ 1。0.8375 ≤ 1 → EDF 可调度。这是 EDF 相比 RM 的优势。
